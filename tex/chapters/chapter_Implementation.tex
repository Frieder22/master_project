\chapter{Implementations} \label{chap:Implementations}
Here the newly developed algorithms are described. As already mentioned in the introduction the goal is to efficiently calculate the union $U$
where every processor $r$  provides a subset $S_r\subseteq \tilde{S}$ from a known set $\tilde{S}$ of fixed size. After the execution of such a union operation
\begin{align*}
	U = \bigcup_{r=0}^{p-1} S_r
\end{align*}
must be available for every processor. The number of processes is again defined by $p$. \\
A straight forward approach to tackle this problem is to create a bitmap for each process, give the elements of $\tilde{S}$ an explicit ordering
and map each element to a bit of the bitmap. An element $e$ is then defined as being in the subset $S_r$, if the corresponding 
bit is set to 1 and set to 0 otherwise. The union can then easily be calculated by performing a bitwise OR-operation over all 
bitmaps from all processes as the union over all subset $S_r$ is defined as
\begin{align*}
	U = \{x \in \Tilde{S} | x \in S_0 \lor x \in S_1 \lor \cdots \lor x \in S_{p-1} \}.
\end{align*}
This can be done using an Allreduce function. This bitmap needs to cover all elements of the original set $\tilde{S}$. Therefore, the message size $m$ that is passed to the Allreduce is at least $N=|\tilde{S}|$ amount of data. As a word size of 64-bit integer is quite common on many architectures $\ceil{\frac{N}{64}}$ 64-bit integer are needed to represent a subset $S_r$. This can be wasteful, if the cardinality of these subsets $S_r$ is quite small and most bits of the bitmap are set to 0. To rake advantage of this case, we introduce here a simple sparse format to save memory and therefore the amount of data for communication. By using unsigned 32-bit integer one can represent subsets of $\tilde{S}$ as an explicit list of the selected integer. Using the sparse representation, one can only represent $2^{32}$ distinct elements so the cardinality of $\tilde{S}$ is bounded by $2^{32} \approx 4.2\cdot10^9$. The benefit is now that the size of the sparse representation only depends on the cardinality of the subset $S_r$. One can calculate the memory footprint $m_\mathrm{Sparse}$ of this representation as being 
\begin{align*}
	m_\mathrm{Sparse} = \varphi_r \cdot \qty{32}{\bit}
\end{align*}
where $\varphi_r = |S_r|$ is the cardinality of $S_r$. To calculate the set union $U$ one needs to concatenate all these distributed lists $S_r$ ($S_r$ is here represented as a list). This can be done by an Allgather. One needs to keep in mind that the result $U$ may contain elements twice. One can either decide that this not a problem (and allow duplicates) or change representation and convert the list into a bitmap. A bitmap can not contain elements twice and therefore duplicates are removed. \\
In this thesis, we consider algorithms that scale well for a large number of processors $p$ and for large set $\Tilde{S}$. Allreduce implementations that fulfill these properties are typically Reducescatter-Allgather algorithms. Moreover, one can identify that the communication pattern of the Reducescatter phase resembles in some cases that of an Allgather. This can easily be seen for the Butterfly and the Ring variants. There is also a Reducescatter and an Allgather implementation that both use the Approximate Halving pattern for communication. The idea is therefore to create an algorithm that works like an Allgather, if the sets are sparsely filled and sparsely represented and switch over to perform a Reducescatter on densely represented sets, if a certain threshold of the set filling is exceeded. If a switch to the dense representation happens and a Reducescatter is executed an Allgather phase on the reduced blocks is needed such that a complete Allreduce is done. To differentiate between the Allgather on the sparse elements and the Allgather that is done after the Reducescatter on the dense elements we refer to the later one only as the (dense) Allgather \emph{phase}. To emphasize that the first Allgather is of interest we will also refer to this as the \emph{sparse} Allgather.\\
In the next section we will present two different implementations that dynamically switch from a sparse to dense representation to perform a union operation. The first one only works for a setup where the number of processes $p$ is restricted to be a power of 2. This algorithm will be referred as \texttt{Union\_Butterfly}. The second one is not confined to this property and will be called \texttt{Union\_Shift}. The reason to also include \texttt{Union\_Butterfly} is that we expect and also measure better performance for machines that are built out of nodes with a power of two number of processors.

\section{An Algorithm for $2^k$-Number of Processes} \label{sec:UnionButterfly}
The algorithm that is presented in this section is based on the Reducescatter-Allgather Allreduce presented in Section \ref{sec:DisseminationAlgo} and the Allgather presented in Section \ref{sec:AllgatherButterfly}. In this thesis, these algorithms are called \texttt{Allreduce\_Butterfly} and \texttt{Allgather\_Butterfly}. These algorithms will be also referred as the \emph{foundation} algorithms for the algorithm that is presented in this section which will be called \texttt{Union\_Butterfly}. We start in the next subsection with explaining the functionality and the implementation of the proposed dynamic union algorithm.

\subsection{Concept and Explicit Implementation}
As the Butterfly communication scheme also the defining structure for the foundation algorithms is also used for this newly proposed union algorithm. As a reminder, this means that in each iteration there is communication between pairs of processors, meaning, if rank $r$ sends a message to its partner $\hat{r}$ then $\hat{r}$ sends in this iteration also a message to $r$. The communication partner is found by flipping the $i$-th bit where $i$ is the iteration. This is exactly the Butterfly communication scheme as it is also used for \texttt{Allreduce\_Butterfly} and \texttt{Allgather\_Butterfly}. Algorithm \ref{algo:SetUnionExactHalving} shows the rough structure of the newly proposed union algorithm. Here are some relevant details hidden behind function calls. This is done to get an overview of the control flow and the details of the used functions are explained later. 

\subsubsection{Requirements on the input parameter} \label{sec:requiremtsOnInputParameter}
Before we explain the algorithm in detail we state the requirements on the inputs. Especially the two arrays $I_d$ and $I_s$ that hold the input set respectively either as a dense bitmap or as sparse integer list. Which representation is used is defined by the flag '$isDense$'. If this flag is set to true the dense representation is used and therefore $I_d$ must be filled. In the other case a set in sparse representation is provided and $I_s$ must be filled and the number of sparse elements needs to be given by the variable '$sparseSize$'. It is also important that the dense array $I_d$ is empty (meaning all bits are set 0), if the sparse representation is used. The parameter '$critSize$' defines the threshold (also called \emph{critical size}) for the sparse filling to switch to the dense representation during the algorithm. Therefore, it is not allowed that $I_s$ holds more elements than the critical size, if the sparse variant is used.\\
In the original implementation these conditions are guaranteed as the sets are built object-oriented and no direct access to the arrays $I_d$ and $I_s$ is possible. This framework also handles the allocation of memory.\\
In the pseudocode we will address also to parts of $I_d$ and $I_s$. The significant part is here that $I_d$ is divided into $p$ blocks and indexing $I_d[j]$ corresponds to the $j$-th
block. Indexing $I_s[j]$ on the other hand refers to the $j$-th element of $I_s$. The array $I_d$ must have allocated enough memory to store the complete dense bitmap. The array $I_s$ needs to have enough memory allocated to store $2\cdot critSize$ elements. The same requirements and notation hold for the respective buffer arrays $\Tilde{I}_d$ and $\Tilde{I}_s$.\\
Another obvious requirement is that the number of processes $p$ must be a power of 2.

\subsubsection{Control flow of \texttt{Union\_Butterfly}}
Algorithm \ref{algo:SetUnionExactHalving} can be divided into two parts. The first one is the dynamic iterative phase where either dense Reducescatter-like or sparse Allgather-like iterations are executed. After that there is an Allgather phase, if the dense representation is currently used (i.e., '$isDense$' is \textbf{true}). As mentioned before during the dynamic phase the communication pattern is that of the Butterfly scheme regardless of the representation rank $r$ has of the current set.\\
The control flow for the sending procedure of the union algorithm is rather simple. If the sub result is currently densely represented blocks of the dense array $I_d$ are sent accordingly to the Reducescatter phase of the foundation Allreduce. If the flag '$isDense$' is set to \textbf{false} process $r$ holds currently sparse information in $I_s$ and all sparse elements are sent to the communication partner $\hat{r}$. The only difference to corresponding foundation Allgather is that the elements are not placed in rank order in array $I_s$. The sparse elements are just in some order in $I_s$ from index $0$ up to index $SparseSize-1$ and all sparse elements rank $r$ currently holds are sent to $\hat{r}$. This strategy is done as the order of sparse elements is not relevant for representing a set. Moreover, in this case it is not known how many elements will be provided by each rank and therefore it is not possible to calculate an explicit layout of $I_s$ in advance.\\
How receiving messages are combined with the current data is hidden by the functions $\Call{combine\_}$. There are four different possibilities as the own representation can either be dense or sparse and the received message can either be dense or sparse. Each case is handled differently and each will be described in detail in the later paragraphs. 


\begin{algorithm}
	\caption{Distributed set union using dense and sparse representations of sets and a Butterfly communication partner. Dense representations are handled like a Reducescatter-Allgather Allreduce and sparse ones like an Allgather.\\
		$r$: rank Id of the process\\
		$p$: number of processes\\
		$I_s$: input array with sparse representation of $S_r$\\
		$sparseSize$: length of sparse list\\
		$I_d$: input array with dense representation of $S_r$\\
		$isDense$: flag to indicate, which representation holds\\
		$critSize$: threshold to switch to dense variant} \label{algo:SetUnionExactHalving}
	\begin{algorithmic}[1]
		\Ensure $p = 2^k$ for some $k$ \Comment{Only works for power of 2 number of ranks}
		\Procedure{SetUnion}{$r, p, I_s, sparseSize, I_d, isDense$}
		\For{(shift $\gets p/2$, shift $\geq1$, shift $\gets$ shift/2)} \Comment{Reducescatter phase}
			\State commNeigh $\gets r$ BXOR shift  \Comment{BXOR is bitwise exclusive OR}
			\If{$isDense$} \Comment{Send Data}
				\State startBlock $\gets$ ($\floor{\text{commNeigh}/\text{shift}}$) $\cdot$ shift
				\State endBlock $\gets$ startBlock + shift
				\State Send($I_d$[startBlock, $\dots$, endBlock - 1], "dense") 
				\Statex\Comment{Send blocks. Mark message as "dense"}
			\Else
				\State Send($I_s$[0, $\dots$, $sizeSparse$-1], "sparse") 
				\Statex\Comment{Send whole sparse array. Mark message as sparse}
			\EndIf
			\State status $\gets$ \Call{Probe}{commNeigh} 
			\Statex\Comment{Get incoming message type and size information}
			\If{(status.tag = "dense")} 
			\Statex\Comment{Combine incoming message with own representation}
				\If{$isDense$}
				\State\Call{combineDenseDense}{ }
				\Else 
				\State\Call{combineDenseSparse}{ }
				\EndIf
			\ElsIf{(status.tag = "sparse")} 
				\If{($isDense$)}
				\State\Call{combineSparseDense}{ }
				\Else
				\State\Call{combineSparseSparse}{ }
				\EndIf
			\EndIf			
		\EndFor
		\If{($isDense$ = false)} \Comment{Return early, if variant is still sparse}
			\State \Return \label{SetUnionExactHalving:earlyReturn}
		\EndIf
		\State\Call{Allgather}{$I_d$} \Comment{Allgather phase}
		\EndProcedure
	\end{algorithmic}
\end{algorithm}

\subsubsection{Consequences of dynamic representation on the implementation}
The first addition of functionality that was not needed in the implementations from the introduction (Chapter \ref{chap:introduction}) is the usage of message tags. A receiving process $\hat{r}$ does generally not know, if a sparse or a dense array was sent to it. MPI allows marking messages using a tag. In the pseudocode we use the notation $\Call{Send}{I, tag}$ to show what marker is assigned to a sent message. On the receiving side this tag information is indirectly retrieved by the function $\Call{Probe}{}$ where it is saved into a status object. This procedure has another benefit as not only the tag is saved in the status object but also the size of the received message. Without this rank $\hat{r}$ would not be able to know how much data it needs to receive. The size information is saved by $\Call{Probe}{}$ in the attribute \texttt{status.count} and can be read from this location.\\
Another difference to the earlier explained algorithms is here that sending and receiving can not be handled by the same function anymore. The probing of a received message is required to be done between sending and receiving. To avoid a deadlock the sending functions are here non-blocking. This requires the usage of the function $\Call{Wait}{I}$ that assures that an array $I$ is again safe to use. The term 'save to use' means in this case that there is currently no message sent from array $I$ and therefore there is no outgoing message that would be altered by changing $I$. 

\subsubsection{Combination of the local dense array with a received dense message}
We already described which data is sent in each iteration $i$. We now explain how received data is combined with the local information to create a new sub result. The first case considered is where the receiving message as well the local representation is dense. In Algorithm \ref{helper:combineDenseDense} the corresponding procedure is depicted and one can identify that the receiving is handled nearly the same way as it is in the foundation Allreduce (compare to Algorithm \ref{algo:redScatterAndAllreduce}).
\begin{algorithm}
	\caption{– combine a received dense blocks into own dense array.\\
	Variable nomenclature is the same as in Algorithm \ref{algo:SetUnionExactHalving}. Changes of variables apply to the original ones.}
	\label{helper:combineDenseDense}
	\begin{algorithmic}[1]
		\Procedure{combineDenseDense}{ }
			\State startBlockR $\gets$ ($\floor{r/\text{shift}}$) $\cdot$ shift
			\State endBlockR $\gets$ startBlock + shift
			\State Recv($\tilde{I}_d$[0, $\dots$, endBlockR - startBlockR-1], "dense")\Comment{Receive in buffer}
			\State Wait($I_d$) \Comment{Wait until it is safe to use original array}
			\ForAll{i $\in$ \{startBlockR, $\dots$, endBlockR - 1\}}
			\State $I_d$[i] $\gets$ $I_d$[i] BOR  $\tilde{I}_d$[i - startBlock] \Comment{BOR is here bitwise OR}
			\EndFor
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
Here, the first difference is that the send and receive is not handled in the same function. As a reminder, the send functions are non-blocking. Therefore, it is necessary to check, if buffer $I_d$ is already safe to use and wait, if this is not the case. Therefore, an additional call to $\Call{Wait}{}$ is needed. The other difference is the reduce operation. It is now not a general associative operator $\oplus$ anymore, but instead the explicitly defined bitwise OR (BOR). As discussed earlier the bitwise OR performs logically the set union of two bitmaps. We can summarize that after an iteration where $\Call{combineDenseDense}{ }$ is executed a standard step of the Butterfly Reducescatter using a bitwise OR operator is performed.

\subsubsection{Combination of the local sparse array with a received dense message}
In the next scenario the considered rank $r$ receives again dense data blocks, but holds itself data in sparse representation. In this case $\Call{combineDenseSparse}{ }$ is executed. The corresponding procedure is shown in Algorithm \ref{helper:combineDenseSparse}. We see that the received dense blocks are put at the local dense array $I_d$ at positions [startBlockR, $\dots$, endBlockR-1]. The block indices are calculated the same way as they are for the purely dense case. After this the sparse elements that rank $r$ holds are also added to the dense array $I_d$. This is done by iterating over all elements of the sparse array and set the corresponding bits of $I_d$ to 1 using $\Call{BitmapSet}{ }$. The function $\Call{BitmapSet}{I, e}$ sets the $e$-th bit of the bitmap $I$ to 1. In this case it is not necessary to wait for a buffer to be safe to use. Array $I_d$ has not been touched as the flag '$isDense$' is set to \textbf{false} and array $I_s$ is not altered in this procedure (only reads from it are performed). 
\begin{algorithm}[h]
	\caption{– combine received dense blocks with own sparse representation.\\
	Variable nomenclature is the same as in Algorithm \ref{algo:SetUnionExactHalving}. Changes of variables apply to the original ones.}
	\label{helper:combineDenseSparse}
	\begin{algorithmic}[1]
		\Procedure{combineDenseSparse}{ }
			\State startBlockR $\gets$ ($\floor{r/\text{shift}}$) $\cdot$ shift
			\State endBlockR $\gets$ startBlock + shift
			\State Recv($I_d$[startBlockR, $\dots$, endBlockR - 1], "dense")
			\ForAll{element $\in I_s$} \Comment{Add all old sparse elements in new dense array}
			\State \Call{BitmapSet}{$I_d$, element}
			\EndFor	
			\State $isDense \gets$ true
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
Lastly the flag '$isDense$' is set to \textbf{true} to indicate that now the dense representation is used. \\
In summary, the dense blocks are put at $I_d$ in the same way as in the foundation Allreduce and the local sparse elements are also added to $I_d$ to obtain a combination of both representations as a dense format in $I_d$.

\subsubsection{Combination of the local dense array with a received sparse message}
The next case presented considers again a combination of a dense representation with a sparse one. The difference is that now the received array is now sparse and $r$ holds data  in dense format. The respective code is shown in Algorithm \ref{helper:combineSparseDense}. The aim is here nearly the same as in the case before. There are two different representations of subsets and they need to be combined into a dense one. This is simply done by putting the received message into a buffer $\Tilde{I}_s$, iterating over this array and use $\Call{BitmapSet}{ }$ to set the corresponding bits of $I_d$ to 1. Before any manipulations are performed on $I_d$ it is necessary to wait until $I_d$ is safe to use. As '$isDense$' is already set to true this flag keeps unaltered.
\begin{algorithm}
	\caption{– combine a received sparse list into own dense array.\\
		Variable nomenclature is the same as in Algorithm \ref{algo:SetUnionExactHalving}. Changes of variables apply to the original ones.}
	\label{helper:combineSparseDense}
	\begin{algorithmic}[1]
		\Procedure{combineSparseDense}{ }
			\State Recv($\tilde{I}_s$ [0, $\dots$, status.count-1], "sparse")
			\State \Call{Wait}{$I_d$}
			\ForAll{element $\in \tilde{I}_s$} 
			\Comment{Add all new sparse elements in old dense array}
				\State \Call{BitmapSet}{$I_d$, element}		
			\EndFor
		\EndProcedure
	\end{algorithmic}
\end{algorithm}

\subsubsection{Combination of the local sparse array with a received sparse message}
Considering the last case, rank $r$ receives a sparse array and also holds data in a sparse variant. The received sparse array is simply appended directly behind the data rank $r$ holds already in $I_s$ and the new size of the sparse array is updated. After this step $I_s$ of rank $r$ holds all sparse elements from $\hat{r}$ and $r$ joined together. Until here this could be seen as a pure Allgather step (although no rank order of the appended arrays is considered). The difference is here, that the number of sparse elements $I_s$ is restricted to not exceed the critical size '$critSize$'. Therefore, the sparse array must be converted into a dense bitmap, if the updated '$sparseSize$' is too big. In this case simply all elements of $I_d$ are added to the empty bitarray $I_d$. Of course the  flag '$isDense$' must then be set to \textbf{true}.\\
\begin{algorithm}
	\caption{– combine two sparse arrays. If the result is to large, switch representation to dense format.\\
		Variable nomenclature is the same as in Algorithm \ref{algo:SetUnionExactHalving}. Changes of variables apply to the original ones.}
	\label{helper:combineSparseSparse}
	\begin{algorithmic}[1]
		\Procedure{combineSparseSparse}{ }
			\State Recv($I_s$[$sizeSparse$, $\dots$, $sizeSparse~+$ status.count $- 1$], "sparse") \\ \Comment{Receive directly in sparse array behind the old elements}
			\State $sizeSparse \gets sizeSparse$ + status.count
			\If{($sizeSparse > critSize$)} \Comment{Transform into dense, if too big}
				\ForAll{element $\in I_s$} 
				\State \Call{BitmapSet}{$I_d$, element}		
				\EndFor
			\EndIf
			\State $isDense \gets $ true
		\EndProcedure
	\end{algorithmic}
\end{algorithm}


\subsubsection{A visual representation of all cases during the adaptive Reducescatter phase}
As a summary there are two different cases which data can be sent and four different cases for handling the receipt. The algorithm is build in a way that there are communication partners for each iteration, meaning, if $r$ sends a message to $\hat{r}$, it will also receive a message from $\hat{r}$. This implies that there are only 3 cases need to be considered. Either both ranks use the dense representation, both use the sparse one or they use different ones. To get a better understanding what happens in each iteration, we provide a visual example for these cases in Figure \ref{fig:3cases}.\\
Before we discuss the depicted possible cases we specify what we mean by the term \emph{correct sub result}. In general a considered rank holds a correct sub result, if it holds the same information as it would when performing its foundation Allgather or its foundation Allreduce in the same iteration. When speaking of a sparse representation $I_s$ needs to hold the same elements as array $O$ in Algorithm \ref{algo:recursiveDoublingAllgather} (\texttt{Allgather\_Butterfly}) does in the same iteration. Considering a dense representation, a rank with a correct subresult holds for all blocks $b$ of the relevant region (according to Definition \ref{def:groupsOfProcessesReducescatter}) the same information in $I_d[b]$ as it would when considering $I[b]$ of Algorithm \ref{algo:redScatterAndAllreduce} in the same iteration.\\
The first case (Figure \ref{3cases:densedense}) shows the behavior when both ranks hold the dense representation. We see that each rank sends half of the current correct subresult to the other process. This done in a way that $r$ and $\hat{r}$ send a different half. The received blocks are combined using the bitwise OR to the respective array $I_d$ which is indicated by overlaying the patterns. One can see that after the iteration each rank holds a smaller section of the new correct subresult. This case is equivalent to an iteration of the foundation Allreduce.

\subsubsection{Either a full Allreduce or just a sparse Allgather}
For now we only discussed the adapted Reducescatter phase which implementation is explicitly stated using point-to-point communication. When looking back at the control flow of the algorithm in Procedure \ref{algo:SetUnionExactHalving} one can see that after the adapted Reducescatter phase there is a check of the representation of the set. If it is sparse, the set union function simply returns. We will argue and show, that in this situation a complete Allgather of the sparse arrays is performed and therefore every process has all information of all provided input subsets. In the other case each rank holds only a block of the correct union set $U$ (i.e., a Reducescatter on the dense blocks was performed). Therefore, a dense Allgather phase is needed which is in this case performed as the last step. Here we do not provide the explicit implementation of $\Call{Allgather}{ }$ as this can be handled by some arbitrary Allgather implementation provided by MPI.\\



\subsection{Proof of Correctness}
For now we only the structure and ideas making this algorithm work are explained. We formalize these ideas and prove here that the proposed algorithm will perform a distributed union operation. Before this is possible we need to find some bookkeeping properties. Iterations are counted from $1$ to $q$. The variable 'shift' is set to $p/2$ in the first iteration and divided by two until it is $1$ in the last iteration. This makes it obvious why there are $q=\log_2(p)$ iterations in total ($p$ is required to be an exact power of 2) and one can describe 'shift' as $s_i=p/2^i$. \\
%This means in the binary representation it has only one bit set to 1. So when we perform an exclusive OR (BXOR) with some number $x$ we basically add or subtract $s_i$ to $x$. If an addition or a subtraction is performed is dependent on the bit that is effectively flipped. The index of this bit is now called $f$. One key insight is here that communication partners rank ID $\hat{r}$ is $s_i$ less or more than the rank ID $r$ one currently considers. We further want to state that ranks $r_a$ for which holds $r_a \mod{2\cdot s_i} < s_i$ have communication partner $\hat{r} = r_a + s_i$, while ranks $r_b$ with  $r_b \mod{2\cdot s_i} \geq s_i$ communicate with $\hat{r}= r_b - s_i$. This also quite obvious as one can see that $r_a$ must have the $f$-th bit set to 0 and $r_b$ must have set it to 1. We can therefore divide the ranks into groups of size $2\cdot s_i$. These groups can be split in half (of size $s_i$) and we can see that the lower half communicates with the upper half. We will also refer to them as the \emph{left} and \emph{right} half. We want to call these groups of ranks in iteration $i$ $g_0^i, \dots, g_{k-1}^i$. As there are $k$ groups of size $2 s_i$ and there are a total amount of $p$ ranks, we can identify $k=p/(2s_i)=2^{i-1}$. We also want label the split up groups $\tilde{g}_0^i, \dots, \tilde{g}_{2k-1}^i$. When $j$ is the index of the original group and $\tilde{j}$ is the index of a group half, then halved with index $\floor{\tilde{j}/2}$ belong to group $g_j$. One can also easily see that the group halves $\tilde{g}_j^i$ of iteration $i$ correspond to the groups of iteration $i+1$ $g_j^{i+1}$. \\
We consider different cases and prove them separately. For the first case, assume only sparse communication is used. This means all ranks submit a subset $S_r$ in sparse format and the critical size is no iteration exceeded. For this we define the \emph{set filling}:
\begin{definition}[Set filling]
	If rank $r$s set $S_r$ is represented sparsely then the \emph{set filling} $\varphi_r$ defines the number of sparse elements that are saved in some array. Multiples are counted multiple times. The \emph{total set filling} $\Phi$ is the sum over all set fillings $\Phi = \sum_r S_r$.
\end{definition}
Using this definition, the first statement lemma can be formalized that shows an inductive property for a special case.
\begin{lemma}
	Suppose all ranks provide a set in sparse format and the total set filling $\Phi$ is at most as big as the critical size (i.e., $\Phi \leq critSize$). Using Definition \ref{def:groupsOfProcessesReducescatter} for grouping processes, after each iteration $i$ each group of processes $g_k$ holds all sparse elements of the union $U=\bigcup_r S_r$ distributed  over the corresponding ranks in array $I_s$.
\end{lemma}
\begin{proof}
	The statement is proven by induction and holds before the first iteration ($i=0$). This is, as there is only one group of processes that holds all ranks and each rank $r$ holds the sparse elements of its set $S_r$.\\
	Consider iteration $i+1$ under the assumption the invariant hold in iteration $i$. The communication pattern is the same as in Algorithm \ref{algo:reduceScatter} and we showed in the proof of Lemma \ref{lemm:redScatButterflyInduction} how communication happens in each group $g_k^i$ of iteration $i$ in iteration $i+1$. Each group $g_k^i$ can be split into a left subgroup and a right one with both subgroups corresponding to consecutive groups $g_k^{i+1}$ of the next iteration $i+1$. Each rank of the left subgroup communicates with a rank of the right subgroup. As the invariant holds in iteration $i$ and each pair of ranks exchange their whole set of sparse elements both subgroups will hold all sparse elements of the union $U$. The exchange of sparse elements is guaranteed as all ranks will hold data in sparse representation before the iteration (under the assumption of the invariant) and only sparse data is sent. This guarantees the execution of $\Call{combineSparseSparse}{}$ on each rank. The upper limit of '$sizeSparse$' can be estimated by $\Phi$ and the sparse representation will be preserved. Therefore, the invariant holds also in iteration $i+1$.
\end{proof}
\begin{corollary} \label{cor:UnionButterflyAllgather}
	Suppose all ranks provide a set in sparse format and the total set filling $\Phi$ is at most as big as the critical size. In this case each rank holds a sparse representation of the set union and Algorithm \ref{algo:SetUnionExactHalving} returns in line \ref{SetUnionExactHalving:earlyReturn}.
\end{corollary}
\begin{proof}
	After $\log_2(p)$ iterations there are $p$ groups each holding one process. Each rank holds therefore the union $U$ in sparse representation and the check on the flag '$isDense$' leads to an early return of the algorithm on all ranks. 
\end{proof}
Algorithm \ref{algo:SetUnionExactHalving} therefore performs a Union operation, if the sets are sparsely filled. We now consider a more general case. For this we introduce the \emph{equivalent dense representation} of some sparse array.
\begin{definition}[Equivalent dense representation]
	The equivalent dense representation $\hat{I}_s$ is a bitmap of the same size as $I_d$ is where all bits are set accordingly to the sparse elements in $I_s$. If an element $e$ is listed in $I_s$ then the $e$-th bit in $\hat{I}_s$ is set to 1 and to 0 otherwise.
\end{definition}
The array $\hat{I}_s$ does not exist in the implementation and serves only the purpose of simplifying notation. Using this definition, another inductive property of Algorithm \ref{algo:SetUnionExactHalving} is shown in the next lemma.
\begin{lemma}
	Using Definition \ref{def:groupsOfProcessesReducescatter} for groups of processes, we label the starting rank by the variable $a$. We define $I$ as the dense array $I_d$, if rank $r$ holds data in dense representation, and as the equivalent dense representation $\hat{I}_s$, if rank $r$ holds sparsely represented data. Algorithm \ref{algo:reduceScatter} (Butterfly Reducescatter) performing a Reducescatter on the dense representations using a bitwise OR is defined as the reference algorithm and we label its array $I$ as $I_{\mathrm{ref}}$.\\
	Algorithm \ref{algo:SetUnionExactHalving} holds in iteration $i$ in blocks $b\in\{a, \dots, a+p\cdot2^{-i}+1\}$ of array $I$ the same data as the reference algorithm in the same iteration in the same blocks in $I_\mathrm{ref}$.
\end{lemma} \label{lemm:unionButterflyInductionDense}
\begin{proof}
	The statement is proven by induction. It holds before the first iteration ($i=0$). Each rank $r$ executing the union algorithm (Algorithm \ref{algo:SetUnionExactHalving}) holds either the input set information in dense or in sparse representation, which results in the same dense array $I$. The same rank $r$ executing the reference algorithm holds in $I_\mathrm{ref}$ also the dense representation of its input set.\\
	Assume the invariant holds in iteration $i$ and consider now iteration $i+1$. One can identify three different cases how communication between rank $r$ and its communication partner $\hat{r}$ looks like: 
	\begin{enumerate}
		\item Both ranks hold data in dense representation. Therefore, both ranks send dense data and execute $\Call{combineDenseDense}$ to combine the received message with their local data. One can see that in this case the exact same operations as in the reference Algorithm are executed and therefore the invariant holds.
		
		\item Both ranks hold data in sparse representation. Therefore, both ranks send their whole sparse array and execute $\Call{combineSparseSparse}$, which concatenates the received message to the local sparse array. One can see that the resulting equivalent sparse representation $\hat{I_s}$ is the same as combining the complete original equivalent sparse representations of both ranks with a bitwise OR operator. The reference Algorithm only combines the considered blocks ($b\in\{a, \dots, a+p\cdot2^{-i}+1\}$) using the bitwise OR operation. So the invariant holds also in this case.
		
		\item One of the ranks holds densely represented data and the other one holds data in sparse format. W.o.l.g. choose $r$ to hold sparse data. Rank $\hat{r}$ sends the same blocks as it does during the Butterfly Reducescatter. These dense blocks are received by process $r$, placed at the same position as in the Butterfly Reducescatter and combined with the local sparse array. The combination with the sparse array corresponds to a bitwise OR operation with the equivalent dense representation $\hat{I}_s$. So on the relevant blocks $b\in \{a, \cdots, a+p\cdot 2^{i-1}-1\}$ is a bitwise OR operation performed. For rank $r$ is the invariant fulfilled. \\
		Rank $\hat{r}$ receives the whole sparse representation of rank $r$, which is then added to the local dense array. Again this is done in a way that corresponds to the combination with the equivalent sparse representation $\hat{I}_s$ using a bitwise OR. Rank $\hat{r}$s new dense representation holds therefore the same subresult for blocks $b\in \{a, \cdots, a+p\cdot 2^{i-1}-1\}$ as it would in the reference algorithm. The invariant holds for both ranks.
	\end{enumerate}
	As all cases imply validity of the statement in iteration $i+1$ it holds for all iterations.
\end{proof}
\begin{corollary}
	Suppose at least one rank provides a set in dense format or the total set filling $\Phi$ is larger than the critical size. In this case each rank returns the total union in dense representation.
\end{corollary}\label{cor:UnionButterflyAllreduce}
\begin{proof}
	Firstly we show that each rank has after the dynamic Reducescatter phase data in dense representation. One can see by a trivial inductive argument that in each iteration all groups of processes (Definition \ref{def:groupsOfProcessesReducescatter}) need to have the same representation. This is, because a case analysis shows that a rank $r$ and its communication partner $\hat{r}$ have the same representation after each iteration. Algorithm \ref{algo:SetUnionExactHalving} allows only transitioning from sparse to dense. So if one rank provided a dense representation all ranks will eventually hold densely represented data. Considering the case that every rank provided a sparse array, but the set filling $\Phi$ is larger than the critical size: The variable 'sizeSparse' counts the number of currently saved sparse elements and will therefore eventually exceed $\Phi$. This parameter can only be increased in Procedure \ref{helper:combineSparseSparse} ($\Call{combineSparseSparse}{}$) where the sparse representation is transformed into a dense one, if the critical size is exceeded. With the same argument as before this must happen for all ranks eventually.\\
	Secondly Lemma \ref{lemm:unionButterflyInductionDense} tells that after $\log_2(p)$ iterations effectively a Reducescatter using a bitwise OR operation is executed. As after the last iteration all ranks hold data in dense representation this corresponds indeed to an actual Reducescatter. After that there is now an Allgather executed. This all together corresponds to an Allreduce using an bitwise OR operator on the dense representations which is equivalent to the distributed union operation.	
\end{proof}
\begin{theorem}
	Algorithm \ref{algo:SetUnionExactHalving} performs a union operation.
\end{theorem}
\begin{proof}
	Two cases need to considered. The first case covers setup where all ranks provide a set in dense representation and the total set filling $\Phi$ does not exceed the critical size. The other case covers the setup where at least one condition of the first setup is not fulfilled. Corollary \ref{cor:UnionButterflyAllgather} tells that for the first setup is a union operation performed and Corollary \ref{cor:UnionButterflyAllreduce} validates the statement for the second case.
\end{proof}

\subsection{Runtime Estimation}
In this section, we provide an estimation of the execution time of this algorithm using the linear cost model. Compared to the algorithms presented in the introductory chapter we do not expect to estimate the run time for a general case. The message size and even the structure of the algorithm depend now on the set fillings $\varphi_r$ of the submitted subsets. So we give an estimation for different setups.
\subsubsection{Only sparse communication} \label{sec:UnionButterflyOnlySparseRuntime}
The first configuration discussed here is the case where the sum of all set fillings $\Phi = \sum_r \varphi_r$ is smaller than the critical size. Moreover, it is assumes that each rank submitted data in sparse format. To keep things simple for this run time estimation we assume that each rank submitted an array of same size $\varphi$. With this the condition arises that the critical size must be at least as big as $\Phi=p\cdot \varphi$. \texttt{Union\_Butterfly} terminates after the adapted Reducescatter phase and effectively an Allgather over all sparse arrays is performed.
In each iteration each rank receives the whole sparse array of its communication partner which is then added to its own local sparse array. In each iteration the size of the sparse array is doubled. So in iteration $i$ (counting from 0) each process sends $\varphi\cdot 2^i$ amount of elements. Using the linear cost model, we expect that each iteration takes $\alpha + \beta \cdot \varphi \cdot 32 \mathrm{bit}$ amount of time. When summing over all iterations a total estimate of
\begin{align*}
	T_\mathrm{scen1} = \sum_{i=0}^{\log_2{p}-1} \cdot \alpha + \beta \cdot 2^i \cdot \varphi \cdot 32 \mathrm{bit}
	= \log_2(p) \alpha + (p-1)\varphi 32 \mathrm{bit} \cdot \beta
\end{align*}  
arises. This is the same run time estimation as the foundation Allgather algorithm (Algorithm \ref{algo:recursiveDoublingAllgather}). One needs to keep in mind that the $\varphi$ describes the size of one input. In the algorithms shown in the introduction the message size $m$ refers to the output message. 
\subsubsection{Only dense communication} \label{sec:UnionButterflyOnlyDenseRuntime}
The next scenario we analyze here requires that all processes propose an array in dense format. Therefore, an only dense communication is used in the first phase of the algorithm. In iteration $i$ (counting from 1) are $p/2^i$ blocks of roughly the size $|\tilde{S}|/p$ are sent. $\tilde{S}$ is here the total possible finite set from which the subsets $S_r$ are selected ($S_r \subseteq \tilde{S}$). Moreover, in each iteration there are $p/2^i$ blocks of data combined using the bitwise OR operator.  The duration of each iteration $i$ is estimated as $\alpha + |\tilde{S}| 2^{-i} \cdot \beta + |\tilde{S}| 2^{-i} \cdot \gamma_d$. The variable $\gamma_d$ is here the time per bit to apply the bitwise OR operator. So the Reducescatter phase needs therefore $\sum_{i=1}^{\log_2{p}} \alpha + |\tilde{S}| 2^{-i} \cdot (\beta +\gamma_d) = \log_2(p) \alpha + \frac{p-1}{p}|\tilde{S}| (\beta +\gamma_d)$ amount of time. We assume that standard library implemented $\Call{Allgather}{ }$ call uses also a Butterfly algorithm and therefore takes $\log_2(p) \alpha + \frac{p-1}{p}|\tilde{S}|\beta $ amount of time. In total, we estimate the runtime as being 
\begin{align*}
	T_\mathrm{scen2} = 2\log_2(p) \alpha + \frac{p-1}{p}|\tilde{S}| (2\beta +\gamma_d)
\end{align*}
which is on par with the foundation Allreduce implementation shown in the introduction (Section \ref{sec:DisseminationAlgo}).
\subsubsection{A worst case scenario} \label{sec:UnionButterflyWorstCase}
As last scenario we analyze a worst case situation in terms of communication cost. We construct a scenario where in each iteration but the last of the dynamic Reducescatter phase  sparse communication is used and in the last iteration 'sizeSparse' exceeds the critical size and therefore the dense Allgather phase is needed. The maximum total set filling where this can happen is $\Phi = 2c$ with $c$ being the critical size. In this case it is possible that before the last iteration of the dynamic Reducescatter phase each rank holds a sparse set with $\Phi/2$ elements and the critical size is exactly not exceeded.\\
The execution time of the dynamic reduction phase corresponds to the first scenario with a uniform set filling $\varphi=\frac{2c}{p}$. After that the Algorithm can not return early  and the dense Allgather phase is executed. Assuming that this Allgather phase is implemented by a Butterfly Allgather (Algorithm \ref{algo:recursiveDoublingAllgather}) the total execution time is estimated as
\begin{align*}
	T_\mathrm{scen3} = 2\log_2(p)\alpha 
	+ \frac{p-1}{p}\left(|\tilde{S}| + c\cdot 64\text{bit}\right)\beta.
\end{align*}
This worst case analysis allows bounding the execution time of \texttt{Union\_Butterfly}. 
For this we use a fixed critical size of $c=\frac{|\Tilde{S}|}{64\text{bit}}$. We use the estimated execution times of the foundation Allreduce $T_\mathrm{Allred}$ and of the foundation Allgather $T_\mathrm{Allgath}$ to bound the execution time $T_\mathrm{scen3}$.
Comparing against the foundation Allreduce one identifies that
\begin{align*}
	T_\mathrm{scen3} = 2\log_2(p)\alpha + \frac{p-1}{p}2|\tilde{S}|\beta
	\leq 2\log_2(p)\alpha + \frac{p-1}{p}(2|\tilde{S}| + \gamma_d)\beta
	\leq \kappa_1 T_\mathrm{Allred}.
\end{align*}
The boundary constant $\kappa_1$ is here required to be at least 1.\\
Using the condition $\varphi=2c/p$ and $c=\frac{|\Tilde{S}|}{64\text{bit}}$, the worst case scenario can also be compared against the foundation Allgather. One can bound
\begin{align*}
	T_\mathrm{scen3} = 2\log_2(p)\alpha + \frac{p-1}{p}2|\tilde{S}|\beta
	\leq \kappa_2 \left(\log_2(p)\alpha + \frac{p-1}{p}|\tilde{S}|\beta \right)
	\leq \kappa_2 T_\mathrm{Allgath}
\end{align*}
with a linear constant $\kappa_2 \geq 2$. One can see that increasing or decreasing the critical size $c$ changes the boundary constants $\kappa_1$ and $\kappa_2$ of this estimation. Nonetheless, it is apparent that for each $c$ there are such boundaries. As a worst case is considered this allows to estimate the execution time of \texttt{Union\_Butterfly} 
\begin{align*}
	T_\mathrm{Union\_Butterfly} \leq \kappa \min(T_\mathrm{Allgath}, T_\mathrm{Allred})
\end{align*}
with $\kappa$ being the larger value of $\kappa_1$ and $\kappa_2$. 

\subsubsection{A fine graded analysis}
As discussed in Section \ref{sec:DisseminationAlgo} the Butterfly scheme fits nicely for systems where the number of processors per node  is also a power of 2. The benefit is here that the rank IDs can be mapped to the processors in such a way that there are iterations where communication happens only inside the nodes. This intra-nodal communication is expected to be much faster than communication via the interconnect. \\
So the remapping of ranks is also considered for \texttt{Union\_Butterfly}. The communication volume per iteration, i.e., the amount of data sent in an iteration, is generally not the same for each iteration. So it is beneficial to perform a remapping of the ranks such that costly iterations are executed between ranks that are physically on the same node. This leads to a trade-off between two strategies. During the adaptive Reducescatter phase the data volume depends on the representation of the set. For a setup where only sparse communication is used the message size increases from each iteration to the next one. For a setup where only dense communication is used the message size decreases in each iteration to the next one. \\
The trad-off is therefore to either optimize for a dense/Allreduce-like setup or for a sparse/Allgather-like setup. A dense execution is guaranteed for a set filling $\Phi$ that is greater than twice the critical size. A good choice of the critical size $c$ is in the range between $\frac{|\Tilde{S}|}{64}$ and $\frac{|\Tilde{S}|}{32}$ (see Section \ref{sec:PerformanceCriticalSize}), i.e., between a relative set filling of $1.56\%$ and $3.1\%$. So it is expected that most of the time dense communication will be used. Moreover, the execution time of a pure dense execution of \texttt{Union\_Butterfly} does not depend on the set filling $\Phi$ and therefore marks an upper boundary of the run time. This is the reason why the rank IDs are  mapped in such a way that in the early iterations communication only happens inside of nodes and therefore dense execution is boosted. The remapping is done using bit reversal of rank IDs as it is described in Paragraph \ref{sec:remappingOfRanks}.

\section{An Algorithm for Arbitrary Number of Processes} \label{sec:irregularImpl}
In this section, we present an algorithm that works in a similarly to \texttt{Union\_Butterfly}, but is not confined to work only for a number of processes $p$ that is a power of two. Again the idea is to overlay an Allgather that uses a sparse representation of a subset $S_r$ over the Reducescatter phase of an Allreduce. The Allreduce basis is here given by the algorithm presented in Section \ref{sec:approxHalfRedScat}. Also in this section the approximate halving sequence $(s_k)_{k\in \{0,\dots, q-1\}}$ is introduced and used. It is defined by the recursive property $s_k = \ceil{s_{k+1}/2}$ and the boundary conditions $s_q=p$ and $s_0=1$. This sequence has obviously $q=\ceil{\log_2{p}}$ terms. This sequence defines the communication scheme. In iteration $i$ (counting from 0) rank $r$ sends data to $\hat{r}_t=(r-\bar{s}_i + p)\mod{p}$ and receives data from rank $\hat{r}_f=(r+\bar{s}_i)\mod(p)$. The skips $\bar{s}_i$ correspond to elements of the approximate halving sequence. It is important to keep in mind that during the Reducescatter phase (like it is shown in Algorithm \ref{algo:redScatterShift}) the skips are taken from the approximate halving sequence in reverse order, meaning it holds $\bar{s}_i = s_{q-1-i}$. Another important detail here is that this algorithm is not limited to the approximate halving sequence. The only conditions such a sequence has to meet is $s_{k+1} - s_k \leq s_k$, $s_q=p$ and $s_0=1$. To adapt the Reducescatter phase to also be able to handle the sparse representation a Allgather is needed that uses the same communication pattern. It seems like the algorithm presented in Section \ref{sec:approxHalfAllgather} provides such an Allgather. The problem is here that the skips $\bar{s}_i$ are here used in the same order as they are listed in the sequence $(s_k)_{k\in \{0,\dots, q-1\}}$, i.e., $\bar{s}_i = s_i$. In our research we did not find any Allgather algorithm that iterates such a sequence in reverse order to use the terms as skips. This is why we firstly present an Allgather that uses this communication pattern.


\subsection{An Allgather using the reverse order of $(s_k)_{k\in \{0,\dots, q-1\}}$ as skips}
As the problem statement to find an Allgather algorithm that uses skips $\bar{s}_i$ that are the reverse order terms of a sequence $(s_k)_{k\in \{0,\dots, q-1\}}$ with $s_{k+1} - s_k \leq s_k$, $s_q=p$ and $s_0=1$ is quite lengthy and complex, we firstly simplify this statement. For this we define $\bar{s}_i$ directly by stating the properties $\bar{s}_{i+1} - \bar{s}_i \geq \bar{s}_i$, $\bar{s}_0=p$ and $\bar{s}_q=1$. Therefore, these skips $\bar{s}_i$ indicate the distance to communication partners in iteration $i$ (counting from 1). \\
We also impose some conditions that regard performance and also usability as adaptation in a Reducescatter phase. Firstly there should be at most $\ceil{\log_2(p)}$ communication rounds. Secondly there should be always contiguous data sent in each iteration. If memory is not ordered in a contiguous way there are two sends per iteration needed which degrades performance. Thirdly the total communication cost (total data send over all iterations) should not exceed $(p-1)m$ where $m$ describes the message size of a ranks input. For this all input arrays are assumed to be of same size. Fourthly and lastly in iteration $i$ the sub results a process has access to should span the same processors as the sub results at block $O[0]$ of the Reducescatter from Section $\ref{sec:approxHalfRedScat}$.\\
The last condition gives a direct hint how such an Allgather could look like. For this we briefly recall the core idea of the Reducescatter from Section $\ref{sec:approxHalfRedScat}$. In this section it is shown that the problem is equivalent to summing up blocks of data of a single array. To show a sub sum in each iteration of this algorithm the summation of blocks is represented as plugging a root node of a tree to the root of another tree. For example, if a block holds  already the sum of block 1 and 5 and block 3 gets added to it, then node 3 is plugged into the root (node 1) of the tree $1\leftarrow 5$. To get a better understanding we present here the same example visualization of the Reducescatter from Section $\ref{sec:approxHalfRedScat}$ which is shown in Figure \ref{fig:arrayAddition}. The tree combination of the example of adding block $3$ to block $1$ which holds already the sum of block $1$ and 5 can be seen in the transition from iteration two to the third one.

We already argued in Section $\ref{sec:approxHalfRedScat}$ that the block indices correspond to the rank IDs that provided this block. We also argued that proving this behavior for one rank (in this example for rank 0) is sufficient to prove correctness for all ranks. This stems from the cyclical symmetry of the setup. By adding the rank ID $r$ (modulo $p$) to all indices one gets a description of what happens at rank $r$.\\
Therefore, we only use the perspective of rank 0 in this recap of the Reducescatter. Also, we only use the representation of trees which correspond to sub-results and plugging them together corresponds to summation of sub-results. The goal is to have one tree with root 0 that spans all other nodes, but each node only once, i.e., no circles are formed. This is done by plugging the roots with high labels to roots with low labels. Precisely the roots $s_k, \dots, s_{k+1}-1$ get plugged into roots $0, \dots, s_{k+1}-s_k-1$. In the example from Figure $\ref{fig:arrayAddition}$ is an approximate halving sequence used to find these $s_k$. But we will see that the condition $s_{k+1}-s_k \leq s_k$ is sufficient. Moreover, one needs to keep in mind that the sequence is used in reverse order. One can see quite easily that after each iteration trees with roots $0,\dots, s_k-1$ span in total all nodes as all trees with a higher node than $s_k-1$ get plugged onto roots that are lower or equal to $s_k-1$. This is because of the maximum index a root gets plugged into is $s_{k+1}-s_k-1$ which can be estimated using the condition $s_{k+1}-s_k \leq s_k$ to  $s_{k+1}-s_k-1\leq s_k-1$. This is also the reason why no node appears twice for roots up to index $s_k-1$. If the trees with roots up to $s_{k+1}$ hold distinct nodes after the iteration before, then trees with nodes up to $s_k$ will hold distinct nodes after the current iteration. Again this is due to the condition $s_{k+1}-s_k \leq s_k$  as there is no overlap between the range of roots that are plugged and roots which trees are extended. 

\subsubsection{Using a pile of data blocks to represent the state of data arrays}
The aim is to create an algorithm that achieves a similar behavior but now without adding sub results, but by concatenating them. For this we think about the input arrays from each rank as physical blocks that can be stacked upon each other. Before the first iteration each rank only holds its own input block and the global state can be represented as a row of blocks. In this representation each column corresponds to the buffer array of each rank. Data can be sent according to the skips $\bar{s}_i$ and processes append the data to their buffer array. Such an action corresponds to a copying of a row, rotating it by $\bar{s_i}$ and putting it on top of the pile. This can be done in one iteration also for multiple rows. One needs to keep in mind that this can be done only for rows that are directly stacked up on each other as we only allow for sends of contiguous data. To get a better understanding of this representation we provide an example in Figure \ref{fig:blockConcat} where actually an Allgather is performed in three iterations for $p=7$ processors.

In this example the Allgather works just fine using a rather simple strategy. A helper array $H$ is added which counts how many blocks are correctly stacked for each rank. Therefore, it is initialized with 1 at every entry. It is updated in each iteration by adding the values of $H[\bar{s}_i, \dots, \bar{s}_{i-1}-1]$ to $H[0,\dots, \bar{s}_{i-1}-\bar{s}_i-1]$ and after that setting values $H[\bar{s}_i, \dots, \bar{s}_{i-1}-1]$ to 0. Then it is possible to find the number of blocks that need to be sent in each iteration by simply looking at entry $H[\bar{s}_i]$. It is obvious that $H[0]-1$ counts for each iteration the total number of sent blocks. So the condition of the total amount data that is sent is met as in the last iteration $H[0]-1=p-1$. One can also see that this algorithm produces in each iteration sub-results that span the same processors as the Reducescatter showed before. It is most apparent when the visual examples from Figure \ref{fig:arrayCopy} and Figure \ref{fig:blockConcat} are compared. One can also identify the property that in the Reducescatter trees with root $\bar{s}_i, \dots \bar{s}_{i-1}-1$ are plugged into roots $0, \dots, \bar{s}_{i-1} - \bar{s}_i-1$. In the Allgather proposal blocks from rank $\bar{s}_i, \dots \bar{s}_{i-1}-1$ gets stacked upon blocks $0, \dots, \bar{s}_{i-1} - \bar{s}_i-1$. Therefore, both algorithms hold in iteration $i$ sub-results from the same processors.

\subsubsection{Limits of naively stacking data blocks}
But this simple scheme can not be applied for any number of processors and needs adaptations. The problem is that for the case considered in Figure \ref{fig:blockConcat} ($p=7$) the arrays from rank $0, \dots, \bar{s}_{i-1} - \bar{s}_i-1$ are all filled with needed blocks to the same height. This is not always the case. The smallest counter example can be found for 25 processors. It is sufficient to look at the helper array $H$ which is shown for the different iterations in Table \ref{table:helperArr25} for this case. One can see in iteration 3 there is $\bar{s}_{3-1}=4$ and $\bar{s}_{3}=2$. One needs to consider therefore the first two entries that will receive new correct blocks. $H_3[0]$ is 8 and $H_3[1]$ is 7.

\subsubsection{An explicit Allgather implementation that uses the reverse order of the mostly halving sequence as skips}
The communication pattern of the algorithm we introduce here is based on a sequence we call a \emph{mostly halving sequence} $(s_k)_{k\in \{0,\dots, q\}}$. We define this sequence by $s_q=p$, $s_{q-1}=2^{\floor{\log_2(p-1)}}$, $s_0=1$ and the recursive property $s_k = s_{k+1}/2$ for all $k=q-2, \dots, 0$. Moreover, the number of processors $p$ must be greater than 1. One can see that $s_{q-1}$ is always the next lowest power of two of the number processors $p$. If $p$ itself is already a power of two, it therefore holds $s_{q-1}=p/2$. After this first special step the next lowest sequence term can be found by exactly halving until $s_0=1$. One can therefore see that $q=\ceil{\log_2(p)}$ which will correspond to the number of iterations that the proposed Allgather will take. This sequence is also used for the Bruck Allgather (Section \ref{algo:bruckAllgather}), but in contrary to this known algorithm the Allgather proposed here uses the terms of this sequence in reverse order. It is apparent that this sequence fulfills the property $s_{k+1} - s_k \leq s_k$ for all $k=q-1, \dots, 0$, so this pattern works also for the Reducescatter algorithm mentioned before. Moreover, we expect this sequence to minimize the number of row reorders of the pile representation mentioned in the paragraph before. \\
To be more precise a strategy is found where in each iteration there is at most one block hold back or one block copied back on top of the pile. So in each iteration there is at most one copy operation of the size of one block. This strategy results in the algorithm shown in Procedure \ref{algo:mostlyHalvingAllgather}. 
\begin{algorithm}
	\caption{– Mostly Halving Allgather\\
		\textit{r}: rank Id\\
		\textit{p}: number of processes\\
		\textit{I}: Input array\\
		\textit{O}: Output array} \label{algo:mostlyHalvingAllgather}
	\begin{algorithmic}[1]
		\Ensure{$p>1$}
		\Procedure{Allgather}{$r, p, I, O$}
		\State shift $\gets 2^{\floor{\log_2(p-1)}}$
		\State tail $\gets p$
		\State inBuff, size $\gets$ \textbf{false}, 1
		\State $O[0] \gets I$
		\While{shift $\geq 1$}
		\State to, from $\gets$ ($r - $shift$+p)\mod{p}$, $(r+$shift$)\mod{p}$ 
		\If{tail > shift} 
			\If{inBuff} \Comment{Put tail on top of pile} \label{mostlyHalvingAllgather:OnPile}
				\State $O$[size] $\gets$ B
				\State inBuff, size $\gets$ \textbf{false}, size + 1
			\EndIf
			\State \Call{Send}{$O[0, \dots, $ size-1]} || \Call{Recv}{$O$[size, $\dots$, $2\cdot$size-1]}
			\State tail $\gets$ tail$ - $shift
			\State size $\gets 2\cdot$size
		\Else
			\If{\textbf{not} inBuff} \Comment{Put tail in buffer} \label{mostlyHalvingAllgather:InBuffer}
				\State B $\gets$ $O$[size]
				\State inBuff, size $\gets$ \textbf{true}, size - 1
			\EndIf
			\State \Call{Send}{$O[0, \dots, $ size-1]} || \Call{Recv}{$O$[size, $\dots$, $2\cdot$size-1]}
			\State size $\gets 2\cdot$size
		\EndIf
		\State shift $\gets$ shift/2
		\EndWhile
		\If{inBuff} \Comment{Put tail on top, if it is still in buffer} \label{mostlyHalvingAllgather:lastBlockCopy}
			\State $O$[size] $\gets$ B
		\EndIf
		\State \Call{Reorder}{$O$} \Comment{Reorder blocks s.t. block $i$ corresponds to rank $i$}
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
The pseudocode shows here a simplified variant where all input blocks $I_r$ from the different ranks have the same size. Indexing of the array $O$ refers to these blocks. Array $O$ is also the array that will hold the stacked blocks. The shift to communication partners is defined by variable 'shift' which is from now on called $\bar{s}_i$ for each iteration $i$ of the \textbf{while}-loop. It is initializes as $\bar{s}_0$ with $=2^{\floor{\log_2(p-1)}}$ and is in each iteration after that divided by 2. It therefore corresponds to the terms of the mostly halving sequence in reverse order. Rank $r$ receives data from rank $\hat{r}=(r+\bar{s}_i)\mod{p}$ which establishes the required circular communication pattern.\\
There are three helper variables that hold information about the current state of the block pile. 'tail' holds information how many blocks are in the incomplete row of the pile. 'inBuff' tells, if the blocks of this tail are currently saved in the buffer array $B$ or stacked on top of the pile (saved as last block of $O$). Lastly there is 'size' which represents the current height of the pile. The term height refers here to the number of correctly stacked blocks of the right half of the pile. When considering the helper array $H$ discussed in a previous paragraph it corresponds to the element $H[\bar{s}_i]$. There are two different main cases need to be considered. \\
Firstly the current tail length exceeds $\bar{s}_i$ and is therefore affected from the pile cutting. It therefore needs to be on top of the pile and the corresponding blocks must be saved as last block in $O$. If this is not already the case the buffered block is  copied at the end of $O$ and the height variable is adjusted to fit $H[\bar{s}_i]$. Considering the pile representation, when the pile gets sliced and the halves get stacked upon each other this also happens for the incomplete tail. So 'tail' gets updated by subtracting $\bar{s}_i$ in this case. After the stacking of the halves the 'size' variable is doubled as the pile height also did.\\
The second case describes the behavior, if the tail size is smaller or equal to the shift $\bar{s}_i$. In this case the tail is not cut and the right half of the pile has uniform height. The tail is therefore removed from the top of the pile (last block gets buffered in $B$) and the stacking of the pile halves results in a pile that does not have any holes.  Before the stacking (sending of data) the size needs to be adjusted accordingly by subtracting 1, if the block is not already in the buffer to fit again $H[\bar{s}_i]$.\\
The last blocks either need to be in the buffer or not depending on the length of the tail. The benefit is here that the blocks do not need to be copied if they are already saved in the correct buffer. This is why only at most one block is needed to be copied in each iteration.\\
Until now, we did not consider the labels of the blocks in the pile representation as the goal was to only accumulate all needed blocks to the first rank.  For a formally correct execution of an Allgather there must be the condition $O[r]=I_r$ fulfilled, meaning the block rank $r$ provided must be at the $r$-th position in the output array $O$. So if a block is still buffered in $B$ it needs to be copied to $O$ and the order of the blocks must be changed. The reordering is hidden behind the function $\Call{Reorder}{ }$. It is possible to find a function that performs such a reorder, but as this Allgather is only used for a union set operation this reordering is not necessary. This step will be omitted in the further usage and is therefore not explored.

\subsubsection{Correctness of the Mostly Halving Allgather}
We also provide a small set of proofs that formalize the correct behavior of the Mostly Halving Allgather. For this firstly some definitions are useful.
\begin{definition}[Pile representation of the Mostly Halving Allgather]
	This pile representation is always done out of the perspective of rank 0. It shows for each iteration $i$ the distribution of the blocks that are needed by rank 0. Each rank has a slot where the needed blocks are stacked upon. A slot represents therefore the blocks that are saved in array $O$ or in array $B$ of rank $r$ in iteration $i$ of the Mostly Halving Allgather. If the ranks hold a block in buffer $B$ these blocks are seen as sitting on top of the pile. The slots are labeled by the same numbers as their corresponding ranks.
\end{definition}
\begin{definition}[Pile representation of Algorithm \ref{algo:redScatterShift} (Reducescatter using approximate halving)]
	This pile representation is always done out of the perspective of rank 0. It shows the state of the array $B$ for the adapted Reducescatter version, where local copies are performed instead of sends to other ranks (see paragraph \ref{sec:redScatLocalSum}). Each block in array $B$ corresponds to a slot. It shows for each iteration $i$ which blocks are in the current sub sum at each block of the buffer $B$. It is assumed that a commutative operator $\oplus$ is used and therefore rows of the pile representation can be swapped freely. The slots have the same numbering as the blocks they correspond to.
\end{definition}
\begin{lemma}
	After each iteration $i$, the pile representation of the Mostly Halving Allgather is the same as the pile representation of Algorithm \ref{algo:redScatterShift} (Reducescatter) that uses the Mostly Halving sequence as skips. For both piles only the first $\bar{s}$ stacks are considered with $\bar{s}$ being the skip of the current iteration. 
\end{lemma}
\begin{proof}
	The statement is shown by induction. The statement holds before the first iteration. Here all ranks hold their own block in the Allgather and therefore the pile consists of a single row where each stack $j$ only holds block $j$. The same is true for the pile representation of the Reducescatter as each block $j$ in $B$ only holds its own input value.\\
    The first iteration needs to be considered separately as here the first skip $\bar{s}_0$ is calculated by $\bar{s}_0=2^{\floor{\log_2(p-1)}}$ and not by exactly halving the old skip value. After the first iteration the Reducescatter holds in each block at least their own value and the blocks [0, $\dots, p-\bar{s}_0-1$] have additionally the values from blocks [$\bar{s}_0, \dots, p-1$] added. Considering the Allgather,  ranks $r$ send in the first iteration their input array to a rank with ID $(r-\bar{s}_0) \mod (p)$. So the blocks from ranks [$\bar{s}_0, \dots, p-1$] are appended to the input blocks of [0, $\dots, p-\bar{s}_0-1$]. The piles representations are therefore the same.\\
	Considering the later iterations under the assumption the invariant holds in the iteration before. One can identify that variable 'shift' of the Allgather and variable '$s$' correspond to the same element of the mostly halving sequence in each iteration. We refer to this variable here as $\bar{s}_i$. During the Allgather ranks [0, \dots, $\bar{s}_i$] receive some subresult from ranks [$\bar{s}_i$, \dots, $2\cdot\bar{s}_i-1$]. If the top row (which size is indicated by 'tail') is greater than $\bar{s}_i$ the last element is included in the send. In this case the pile representation gets cut in half and the right half gets placed on top of the other one. If 'tail'$\leq \bar{s}_i$ than all blocks but the last are sent. This results in cutting the pile in half, storing the top row aside, placing the right half on top of the left one and adding the top row again on the very top.\\
    During the adapted Reducescatter blocks [$\bar{s}_i, \dots, \bar{s}_{i-1}$] get added to the blocks [$0, \dots, \bar{s}_{i-1}-\bar{s}_i-1$]. As the mostly halving sequence defines now the skips $\bar{s}$ the skip of the iteration before $\bar{s}_{i-1}$ can be expressed as $\bar{s}_{i-1}=2\cdot \bar{s}_i$. So the corresponding pile gets cut in half and the right half is simply put on top of the left half. This can in introduce some holes in the pile. This representation allows to rearranging the rows such that not only the holes are gone but also matches exactly the pile representation of the Allgather. So the invariant holds.
    \end{proof}
\begin{corollary}
	Block $B[0]$ of the Reducescatter (Algorithm \ref{algo:redScatterShift}) holds in each iteration a result that spans the same ranks as the Mostly Halving Allgather holds in its buffers $O$ and $B$.  
\end{corollary} \label{coro:mostlyHalvingSpansSameRanks}
\begin{proof}
	The blocks of the sub results of the adapted Reducescatter (only local copies no sending, see Paragraph \ref{sec:redScatLocalSum}) of block $B[0]$ corresponds to the ranks that the original Reducescatter (Algorithm \ref{algo:redScatterShift}) spans at this block. Stack 0 of its pile representation therefore indicates which ranks the original Reducescatter spans at block $B[0]$. As the Allgather has the same pile representation it spans the same ranks.
\end{proof}
\begin{corollary}
	The Mostly Halving Allgather performs a valid Allgather over all ranks.
\end{corollary}
\begin{proof}
	After the last iteration each rank holds a sub result that spans the same ranks as the block $B[0]$ of the Reducescatter does. The Reducescatter spans all ranks after the last iteration. So after fusion of the buffered block into the output array $O$ and a reordering a correct Allgather is performed.
\end{proof}


\subsubsection{Expected performance of this reversely ordered Mostly Halving Allgather} \label{sec:AllgatherShift performance}
The execution time are again estimated using the linear cost model. As this (Algorithm \ref{algo:mostlyHalvingAllgather}) round based algorithm takes $\ceil{\log_2(p)}$ iterations the  $\alpha$-term can be identified as $\ceil{\log_2(p)}$. The total amount of data that is sent can also be easily calculated. For this the size of the output of the Allgather is labeled $m$. Again we assume that each rank proposes an array of roughly the same size $m/p$. When considering the pile representation rank 0 receives in each iteration only blocks that it needs, i.e., blocks that are not already stacked in its array or buffer. So rank 0 does not receive any duplicates and holds all blocks after the Allgather. As every rank holds one block at the start of the Allgather  it must have received $p-1$ blocks. Because of the cyclical structure of the algorithm this must be true for all ranks. This gives a total communication cost for the $\beta$-term of $\beta\frac{p-1}{p}m$. There is no computation on the buffer arrays performed (like a bitwise OR operation) in this implementation, but there is memory copied which also takes time. For this the constant $\gamma_c$ is defined. It represents the time that it takes to copy one bit of memory from one buffer to another one. This is of course again a big simplification to model this behavior linearly, but this allows for a reasonable simple run time analysis. In each iteration there is at most one block copied to the "pile" buffer $O$ or to the side buffer $B$. Therefore, there is at most $\ceil{\log_2(p)} \frac{m}{p}$ amount of data copied during the Allgather. This allows for an estimation of an upper boundary of the execution time
\begin{align}
	T_\mathrm{MostHalfAllgather} \leq \ceil{\log_2(p)}\alpha
	+ \frac{p-1}{p}m\cdot \beta
	+ \ceil{\log_2(p)} \frac{m}{p} \cdot \gamma_c
\end{align} \label{eq:mostlyHalvingAllgatherCost}
for the optimal uniformly distributed case.

\subsubsection{Calculating the amount of memory copies} \label{sec:AllgatherShiftNumberOfCopies}
It is possible to explicitly calculate the amount of blocks that need to be copied. The amount of copies depends actually on the number of processors $p$. When looking at Procedure \ref{algo:mostlyHalvingAllgather} one can see that the logic of handling buffer copies only depends on the size of 'tail' with respect to 'size'. If the tail is bigger than 'shift' the last block needs to live on top of the pile and otherwise it needs to be in the spare buffer. \\
To be able to count the copies it is therefore relevant to see in which iteration the last block is on the pile or in the spare buffer. For this the control flow of the Mostly Halving Allgather is reduced to the part that is essential in this context and then the code is manipulated without changing the actual behavior. The code snippet and its transformations are shown in Figure \ref{fig:mostlyHalvingControlFlow}. Here the first code snippet shows the control flow identical to the Mostly Halving Algorithm. To simplify the code, only the \textbf{if}-brackets are stated and the actual logic  for copying blocks is omitted. The second code block is equivalent, but with a global transformation of the variable 'tail' to 'tail*$+1$'. This transformation does only affect the value of 'tail' (or rather 'tail' and 'tail*' do not have the same values) and the other variables behave the same. The control flow is also unchanged by this remapping.

In the last code snippet are additionally some algebraic changes applied that simplify the modified code. With this last code block in mind, we state that one can iterate the binary representation of $p-1$ starting from the leading 1 and the bits correspond to the executed brackets in iteration $i$. If the $i$-th bit is set to 1 then the \textbf{if}-bracket is executed and if the $i$-th bit is set to 0 then in this iteration $i$ the \textbf{else}-bracket is executed. To show why this statement is valid a small lemma is useful. For this we label the value of 'shift' after iteration $i$ as $s_i$ and the value of 'tail*' as $t_i$.
\begin{lemma}
	After each iteration 'tail*' is strictly smaller than $2\cdot$'shift'
\end{lemma} \label{lemm:TailShiftRelation}
\begin{proof}
	The statement is shown by induction. Keep in mind 'shift' holds therefore the value $2\cdot s_i$ at the start of the iteration $i$.\\
	The statement holds before the first iteration as 'shift' is initialized to the next lowest power of 2 of $p$ and we estimate $2\cdot s_0 \geq p > p-1 = t_0$.\\
	Assume the statement holds in iteration $i-1$ and consider now iteration $i$. There are two cases:
	\begin{enumerate}
	\item The \textbf{else}-bracket gets executed. Therefore, the condition of the \textbf{if}-clause allows the estimation be $t_i=t_{i-1} < s_{i-1} = 2\cdot s_i$ and the invariant holds.
	\item The \textbf{if}-bracket gets executed. As the invariant held in the iteration before we have $t_{i-1} < 2 \cdot s_{i-1}$. The new value of $t$ is updated and can be estimated by $t_i = t_{i-1}-s_{i-1} < 2\cdot s_{i-1}-s_{i-1} = s_{i-1} = 2\cdot s_{i}$ and the invariant holds. 
	\end{enumerate}
\end{proof}
We now argue that the \textbf{if}-condition ('tail* $\geq$ shift') is only true, if the leading bit of 'shift' coincides with the leading bit of 'tail*'.  This due to the fact that the \textbf{if}-condition and Lemma \ref{lemm:TailShiftRelation}  give the boundary '$s_{i-1}\geq t_{i-1} < 2\cdot s_{i-1}$. We know that $s_{i-1}$ is always a power of two and therefore $t_{i-1}$ can only take values between and including $s_{i-s}=(100\dots)_2$ and $2\cdot s_{i-s}-1=(111\dots)_2$. As the \textbf{if}-bracket is executed in this case one can also see that the leading bit of 'tail*' gets removed.\\
So conclusively the bits of 'tail*' gets scanned by the leading bit of 'shift' and removed if they coincide. As 'tail*' gets initialized with $p-1$ and the brackets correspond to the removal of bits the original statement is explained.

One can therefore look at the bit representation of $p-1$, scan the bits starting from the leading bit and count the switches from a 0 to a 1 and vice versa. If the last bit of $p-1$ is a 0 another extra block copy needs to be done to put the buffered block into the output array (see Line \ref{mostlyHalvingAllgather:lastBlockCopy} of Algorithm \ref{algo:mostlyHalvingAllgather}). The resulting sum corresponds to the number of copies.\\
The worst case is therefore a number of $p$ where the bit representation of $p-1$ is alternating between 1 and 0 (like $p=171$ with $p-1=170=(10101010)_2$). With this calculation one can also see that for $p$ being a power of 2 there are no block copies needed as the binary representation of any number $p=2^k-1$ will only consist out of 1s. 


\subsubsection{Further implementation details} \label{sec:reorderingMostlyHalvingAllgather}
The pseudocode for the Mostly Halving Allgather (Algorithm \ref{algo:mostlyHalvingAllgather}) assumes that the block sizes that are provided by each process are known by each rank. This will be not the case for the application the Allgather will be used for. As seen in the earlier proposed Union algorithm (Algorithm \ref{algo:SetUnionExactHalving}) the concatenation of blocks of unknown size is possible by extracting the size information of a received block via the 'count' attribute of the 'status' object. The challenge for the Mostly Halving Allgather is that sometimes the last block of the output array $O$ needs to be buffered in the array $B$. So the size information of the last block is also needed. One idea is to use the 'tag' attribute of the 'status' object to transfer this information. The MPI standard \cite{mpi} only guarantees a maximum value of 32767 for the attribute 'tag'. So this idea can break for larger block sizes. So instead the size information of the last block is put into the buffer $O$ after the current last block element. During the sends are not only the needed blocks transmitted, but also the number of elements of the last block. The blocks are also received one element behind the last element of the last block of the iteration before to avoid overwriting the size information of the last block. After the send has completed (checked by a call of $\Call{Wait}{}$) the output array is rearranged such that elements in the blocks are contiguous in memory without being interrupted by some size information element.

\subsection{Concept and Explicit Implementation of the Union algorithm}
In this section, the structure of the newly proposed Union algorithm \texttt{Union\_Shift} is described. The general idea is quite similar to the earlier proposed \texttt{Union\_Butterfly} algorithm (Algorithm \ref{algo:SetUnionExactHalving}). The goal is to overlay an Allgather over the Reducescatter phase of an Allreduce. If it is seen as beneficial to use the sparse representation the \texttt{Union\_Shift} algorithm should work like an Allgather and switch to a Reducescatter, if the dense representation is seen as more efficient. As this algorithm needs to work correctly for an arbitrary number of processes $p$ the foundation for the Allreduce is chosen to be the recursive halving Allreduce using a shift based communication pattern (see Algorithm \ref{algo:redScatterAndAllgatherShift}). This Allreduce will also be referred as \texttt{Allreduce\_Shift}.  The corresponding Reducescatter (for the Reducescatter phase of this Allreduce) is described in Algorithm \ref{algo:redScatterShift}. A fitting Allgather implementation is motivated and discussed in the section before and its pseudocode can be found in Algorithm \ref{algo:mostlyHalvingAllgather}. This Allgather will also be called \texttt{Allgather\_Shift}. \texttt{Allreduce\_Shift} and \texttt{Allgather\_Shift} will also be called the foundation Allreduce/Allgather respectively in the context of \texttt{Union\_Shift}.\\
The code skeleton for the control flow of \texttt{Union\_Shift} is shown in Algorithm \ref{algo:UnionShift} and is quite similar to the structure of \texttt{Union\_Butterfly} (Algorithm  \ref{algo:SetUnionExactHalving}). 
\begin{algorithm}
	\caption{Distributed set union using recursive exact halving Allreduce with sparse adaptation.\\
		$r$: rank Id of the process\\
		$p$: number of processes\\
		$I_s$: input array with sparse representation of $S_r$\\
		$sparseSize$: length of sparse list\\
		$I_d$: input array with dense representation of $S_r$\\
		$isDense$: flag to indicate, which representation holds} \label{algo:UnionShift}
	\begin{algorithmic}[1]
		\Procedure{UnionShift}{$r, p, I_s, sparseSize, I_d, isDense, critSize$}
		\State tail, inBuff, sizeBuff $\gets p,$ \textbf{false}, $0$
		\State shiftOld $\gets p$
		\For{(shift $\gets 2^{\floor{\log_2 (p-1)}}$, shift $\geq1$, shift $\gets$ shift/2)}
			\Statex\Comment{Use mostly halving scheme}
			\State to, from $\gets$ ($r +$shift)$\mod{p}$, $(r-$shift$+p)\mod{p}$ 
			\If{$isDense$} 
				\State\Call{sendDense}{~}
				\Else
				\State\Call{sendSparse}{~}
			\EndIf
			\State status $\gets$ \Call{Probe}{commNeigh} 
			\Statex\Comment{Get incoming message type and size information}
			\If{(status.tag = "dense")} 
			\Statex\Comment{Combine incoming message with own representation}
				\If{$isDense$}
					\State\Call{combineDenseDense}{ }
				\Else 
					\State\Call{combineDenseSparse}{ }
				\EndIf
			\ElsIf{(status.tag = "sparse")} 
				\If{($isDense$)}
					\State\Call{combineSparseDense}{ }
				\Else
					\State\Call{combineSparseSparse}{ }
				\EndIf
			\EndIf	
			\State shiftOld $\gets$ shift		
		\EndFor
		\If{($isDense$ = false)} \Comment{Return early, if variant is still sparse} \label{UnionShift:sparseCompleted}
			\State\Call{copyBuff}{$I_s$, $\Tilde{I}_s$, inBuff} \label{UnionShift:copyBuff}\Comment{Put buffered sparse block into sparse array}
			\State \Return
		\EndIf
		\State\Call{Allgather}{$I_d$} \Comment{Allgather phase}
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
One difference is that here the communication partners 'to' and 'from' are used which are determined according to the shift communication pattern using the Mostly Halving sequence. The other difference is apparent for the case that only the sparse representation was used (\textbf{if}-statement of line \ref{UnionShift:sparseCompleted} is fulfilled) where the buffered sparse block needs to be appended to the sparse array. Algorithm \ref{algo:UnionShift} hides  a lot of code behind the functions $\Call{sendSparse}{~}, \Call{sendDense}{~}, \Call{combineDenseDense}{~}, \Call{combineDenseSparse}{~}, \linebreak \Call{combineSparseDense}{~}$ and $\Call{combineSparseSparse}{~}$. They have access to all variables and change them globally for the procedure $\Call{unionShift}{~}$. These functions are shown and discussed in the later paragraphs. To keep things visually simple the passed parameter are not explicitly stated in this pseudocode.

\subsubsection{Requirements on input parameter}
Generally the requirements are the same as for \texttt{Union\_Butterfly} which are stated in Paragraph \ref{sec:requiremtsOnInputParameter}. For \texttt{Union\_Shift} is another property required. The dense bit array $I_d$ (and also its buffer  $\hat{I}_d$) are implicitly rotated. The arrays are filled in such a way that block $b$ actually corresponds to block $(b+r)\mod(p)$ with $r$ being the process rank ID. This is guaranteed by the framework which handles the set interface. Consider element $e$ is put into rank $r$s set $S_r$. This would correspond to setting the $k$-th (counting from the start of the block) bit of some block $b$ to 1. In the demanded implicit rotation of $I_d$ the $k$-th bit of block $(b-r+p)\mod(p)$ is set to 1. This is done out of performance reasons. Considering the foundation Allreduce (Algorithm \ref{algo:redScatterAndAllgatherShift}), the blocks of the input array are at the start of the algorithm explicitly rotated and before the end explicitly rotated back to restore the original order in the output. This procedure would also be required for \texttt{Union\_Shift} and is omitted by storing the elements implicitly rotated. To set bits in an implicit rotated way the function $\Call{setBitmapShifted}{I_d, e}$ is available which sets the correct bit in the dense buffer $I_d$ that would correspond to element $e$ after an explicit rotation. 
 
\subsubsection{Functionality of sparse send}
In this paragraph, we discuss the first helper function $\Call{sendSparse}{~}$. If the flag 'isDense' is set to \texttt{false} at the start of an iteration the considered process uses the sparse representation and $\Call{sendSparse}{~}$ is executed. This sparse data is stored in $I_s$ and needs to be distributed according to the foundation Allgather (Mostly Halving Allgather shown in Algorithm \ref{algo:mostlyHalvingAllgather}). 
\begin{algorithm}[htb]
	\caption{Send sparse representation.} \label{algo:UnionShiftSendSparse}
	\begin{algorithmic}[1]
		\Procedure{sendSparse}{~}
		\If{tail > shift} 
			\If{inBuff} \Comment{Put tail on top of pile} \label{UnionShiftSendSparse:OnPile}
				\State \Call{Wait}{$I_s$} \label{UnionShiftSendSparse:WaitCall}
				\State $I_s$[$sizeSparse, \dots, sizeSparse + $sizeBuff$ - 1$] $\gets$ $\Tilde{I}_s$
				\State inBuff, $sizeSparse \gets$ \textbf{false}, $sizeSparse$ + sizeBuff
				\State $I_s[sizeSparse] \gets $ sizeBuff 
				\State sizeBuff $\gets 0$ 
			\EndIf
			\State tail $\gets$ tail$ - $shift
		\Else
			\If{\textbf{not} inBuff} \Comment{Put tail in buffer} 
				\State sizeBuff $\gets I_s[sizeSparse]$			
				\State $\Tilde{I}_s$ $\gets$ $I_s$[$sizeSparse-$sizeBuff$, \dots,sizeSparse-1$]
				\State inBuff, $sizeSparse \gets$ \textbf{true},  $sizeSparse$ - sizeBuff
			\EndIf
		\EndIf
		\State \Call{Send}{$I_s[0, \dots, $ $sizeSparse$], "sparse"}
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
The pseudocode of the sparse send is shown in Algorithm \ref{algo:UnionShiftSendSparse} is very similar sending procedure of the Mostly Halving Allgather, but there are small but relevant differences. Firstly a different notation is used. Array $I_s$ which holds the sparse data is now indexed by its elements and not by blocks anymore. This allows to show how $sizeSparse$ represents the amount of current sparse elements. With this it is also apparent how the size information of the last block gets appended to the sparse array which is now explicitly stated. A difference in actual implementation (and not only notation) is that here the sending of data is handled by the non-blocking $\Call{Send}{~}$ function and no simultaneous send and receive is performed. This has the consequence that  a call to $\Call{Wait}{I_s}$ is necessary in line \ref{UnionShiftSendSparse:WaitCall}. Without the waiting procedure it could happen that the element $I_s[sizeSparse]$ (containing the size information of the last block) gets overwritten which is also part of the sending range of the iteration before. The rest of the implementation is directly analogous to the sending process of the Mostly Halving algorithm. The last important detail is that the message is labeled with the tag "sparse" such that a receiving rank can identify the type of message it received.

\subsubsection{Functionality of dense send} \label{sec:denseSendUnionShift}
If the flag 'isDense' is set to \textbf{true} the process uses in the current iteration the dense representation. The process holds valid data in the dense array $I_d$ which needs to be distributed according to the Reducescatter phase of the foundation Allreduce (Algorithm \ref{algo:redScatterShift}). The sending procedure can be seen in Algorithm \ref{algo:UnionShiftSendDense}.
\begin{algorithm}[htb]
	\caption{Send dense representation.} \label{algo:UnionShiftSendDense}
	\begin{algorithmic}[1]
		\Procedure{sendDense}{~}
		\State \Call{Send}{$I_d[$shift$, \dots, $shiftOld$-1]$}
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
The dense array $I_d$ is here again indexed by blocks of memory. There are $p$ blocks of roughly equal size. One needs to keep in mind that these blocks are implicitly rotated. The implementation of the sending of dense data is equivalent to the Reducescatter phase of the foundation Allreduce. One difference is here again the non-blocking $\Call{Send}{~}$-function instead of a combined send and receive. The reception is of course handled later in one of the dense receiving procedures. The other difference is that the message is labeled "dense" such that the type of the message can be identified. 

\subsubsection{Combination of a local dense array with a received dense message}
If the tag of the received message is dense and rank $r$ already holds set information in the dense format a combination of these arrays should be done according to the Reducescatter phase of Algorithm \ref{algo:redScatterAndAllgatherShift} performing a bitwise OR. This done directly equivalent to the foundation Allreduce which can be seen in Algorithm \ref{algo:UnionShiftCombineDenseDense}.
\begin{algorithm}[htb]
	\caption{Combine local dense array with a received dense array.} \label{algo:UnionShiftCombineDenseDense}
	\begin{algorithmic}[1]
		\Procedure{combineDenseDense}{~}
			\State  \Call{Recv}{$\Tilde{I}_d$[$0, \dots, $shiftOld$ - $shift$ -1$], from}
			\State \Call{Wait}{$I_d$}
			\ForAll{$b \in \{0, \dots, $ shiftOld$ - $shift$ -1\}$}
			\State $I_d[b]\gets I_d[b] $~BOR~$ \Tilde{I}_d[b]$
			\EndFor
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
The only adaptations that need to be done are to wait until it is safe to overwrite $I_d$ and to use the bitwise OR operator (BOR) for the combination of the blocks.

\subsubsection{Combination of a local sparse array with a received dense message}
If a message in dense representation is received and the local representation is sparse the set representations need to be combined into a dense one.  For this the dense message is directly received into the empty dense array $I_d$. Then the local sparse elements need to be added into the dense array. This is done for all elements saved in the sparse array $I_s$ and for all elements of the sparse buffer $\Tilde{I}_s$, if the buffer array is filled. The corresponding pseudocode is presented in Algorithm \ref{algo:UnionShiftCombineDenseSparse}.
\begin{algorithm}[htb]
	\caption{Combine local dense array with a received sparse array.} \label{algo:UnionShiftCombineDenseSparse}
	\begin{algorithmic}[1]
		\Procedure{combineDenseSparse}{~}
		\State  \Call{Recv}{$I_d$[$0, \dots, $shiftOld$ - $shift$ -1$], from}
		\ForAll{$e \in I_s[0, \dots, sizeSparse]$}
			\State \Call{setBitmapShifted}{$I_d, e$}
		\EndFor
		\If{inBuff}
			\ForAll{$e \in \Tilde{I}_s[0, \dots, $sizeBuff]}
			\State \Call{setBitmapShifted}{$I_d, e$}
			\EndFor
		\EndIf
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
The toggling of the correct bits of the implicitly rotated dense buffer $I_d$ is done via the earlier mentioned (Paragraph \ref{sec:requiremtsOnInputParameter}) function $\Call{setBitmapShifted}{I_d, e}$.


\subsubsection{Combination of a local dense array with a received sparse message}
If a message in sparse representation is received and the local representation is dense  the situation is quite analogous to the one described in the paragraph before. Again there are two different set representations that need to be combined into a dense one. The strategy is therefore similar to the one of $\Call{combineDenseSparse}{~}$, but now  sparse data is received and then these elements are added to the local dense array $I_d$. The pseudocode is shown in Figure \ref{algo:UnionShiftCombineSparseDense}.
\begin{algorithm}[htb]
	\caption{Combine local dense array with a received sparse array.} \label{algo:UnionShiftCombineSparseDense}
	\begin{algorithmic}[1]
		\Procedure{combineSparseDense}{~}
		\State  \Call{Recv}{$I_s$[$0, \dots, $status.count$-1$], from}
		\ForAll{$e \in I_s[0, \dots,$ status.count$-2$]}
			\State \Call{setBitmapShifted}{$I_d, e$}
		\EndFor
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
The process can not calculate implicitly how many elements it will receive from its communication partner. So the functionality 'status.count' is necessary to find the amount of received data.\\
As a remark one needs to keep in mind that the last element of a sparse message contains the size information of the last block. This is the reason why the last received element is not added to the dense representation and the upper index of valid elements is 'status.count$-2$'.

\subsubsection{Combination of a local sparse array with a received sparse message}
If both the received message and the local representation are in the sparse format the "preferred" format for the result is also a sparse array. So in general a foundation Allgather step is executed. Only if the number of elements it exceeds the critical size 'sizeCrit' the result must be transformed into the dense representation. The procedure is shown in Algorithm \ref{algo:UnionShiftCombineSparseSparse}. \\
The first part is therefore analogous to a Mostly Halving Allgather iteration. The received sparse message is appended to the local one. After that a reordering of some elements is necessary which is motivated and explained in Paragraph \ref{sec:reorderingMostlyHalvingAllgather}. This reordering of the sparse array $I_d$ is executed by the function $\Call{Reorder}{~}$. Before this reordering it is necessary to check via $\Call{Wait}$, if it save to manipulate $I_s$ as the element $I_s[sizeSparse]$ is part of the sending range of the iteration before. Then the size of sparse elements is updated. It is increased only by 'status.count$-1$' as the last element of the received message holds not a valid sparse element, but the size information of the last block.
\begin{algorithm}[htb]
	\caption{Combine local sparse array with a received sparse array.} \label{algo:UnionShiftCombineSparseSparse}
	\begin{algorithmic}[1]
	\Procedure{combineSparseSparse}{~}
	\State  \Call{Recv}{$I_s$[$sizeSparse + 1, \dots, sizeSparse+$status.count], from}
	\State \Call{Wait}{$I_s$}
	\State lastBlockSize $\gets I_s[sizeSparse+status.count$] 
	\Statex\Comment{size of last block of received message}
	\State\Call{Reorder}{$I_s, sizeSparse$, status.count, lastBlocksize}
	\State $sizeSparse \gets sizeSparse + $ status.count $-1$
	\If{$sizeSparse + $ sizeBuff > $sizeCrit$}\label{UnionShiftCombineSparseSparse:addSizeBuff}
		\ForAll{$e \in I_s[0, \dots, sizeSparse]$}
			\State \Call{setBitmapShifted}{$I_d, e$}
		\EndFor
		\If{inBuff}
			\ForAll{$e \in \Tilde{I}_s[0, \dots, $sizeBuff]}
				\State \Call{setBitmapShifted}{$I_d, e$}
			\EndFor
		\EndIf	
		\State $isDense \gets$ \textbf{true}	
	\EndIf
	\EndProcedure
	\end{algorithmic}
\end{algorithm} 
\\After the correct receipt of the new sparse data it is then checked, if the process holds more sparse elements than 'sizeCrit'. The total amount of sparse elements equals to '$sizeSparse$' plus the amount of elements in the buffer ('sizeBuff' is set to 0, if the buffer is not used). If 'critSize' is reached or exceeded the sparse representation is transformed into the dense one. For this all sparse elements (including the buffered ones) are filled into the dense array $I_d$ using the implicit rotation and the flag indicating the dense representation is set to \textbf{true}.

\subsubsection{An implementation improvement regarding sparse buffered blocks}
In the actual implementation  some small improvement is done for the concatenation logic of two sparse arrays. The size information of the last block is only relevant, if the last block is eventually buffered. So if the sparse buffer $\Tilde{I}_s$ is already filled and 'inBuff' is true it is not necessary to send this information. Therefore, it is only sent, if it is needed. One small benefit is here that the message size is one element (one 32-bit unsigned integer) shorter. The maybe more important improvement is that the receiver can append the message directly behind its sparse array $I_s$ as the size information of the last block of its old sparse array is not needed anymore (of course only relevant, if the receiver holds currently data in the sparse representation). So no rearrangement of sparse elements is needed. This means in the function $\Call{combineSparseSparse}{~}$ the call to $\Call{Reorder}{~}$ is omitted and in these iterations the receiver does not have to wait for $I_s$ being safe to use. 

\subsubsection{Procedure after the Reducescatter phase}
The functionality of the adapted Reducescatter phase is now explained. If the sparse representation is used up until the hole dynamic Reducescatter phase an Allgather of the sparse input arrays is performed and the algorithm can return early. In this case the buffered sparse elements need to be appended to the sparse array $I_s$. This conditional copy is performed by the function $\Call{copyBuff}{~}$ (line \ref{UnionShift:copyBuff} of Algorithm \ref{algo:UnionShift}). \\
If the representation is not sparse after the last iteration a Reducescatter on the dense array $I_d$ is performed. To get a complete Allreduce an Allgather needs to be performed on the dense array $I_d$. This Allgather phase is implemented in the same way as it is for the foundation Allreduce shown in Algorithm \ref{algo:redScatterAndAllgatherShift}. This Allgather phase is hidden behind the function $\Call{Allgather}{~}$. After this no re-rotating of the dense array is performed. The implicit rotation of $I_d$ is kept and it is checked for elements by using the interface function $\Call{checkBitmapShifted}{~}$.

\subsection{Proof of Correctness}
This algorithm uses quite similar ideas as \texttt{Union\_Butterfly}. Therefore, the ideas to prove that \texttt{Union\_Shift} also calculates a correct set union are also quite similar. For this firstly is only the case considered that only the sparse variant is used.
\begin{lemma}
	Considering \texttt{Union\_Shift} (Algorithm \ref{algo:UnionShift}): If all ranks $r$ propose a sparse array and the sum over all set fillings $\sum_r\varphi_r=\Phi$ does not exceed the critical size 'sizeCrit', then each iteration $i$ of the Reducescatter phase is equivalent to the $i$-th iteration of the Mostly Halving Allgather (Algorithm \ref{algo:mostlyHalvingAllgather}).
\end{lemma}
\begin{proof}
	Let us call the value 'sizeCrit' $c$, the value 'sizeBuff' $b$ and the value 'sizeSparse' $s$. One can quite easily see that, if only the sparse send is executed and only $\Call{combineSparseSparse}{~}$ is used the union algorithm is exactly the same as the mostly Halving Allgather. We therefore argue inductively that each iteration of these two Algorithms is equivalent.\\
	This is quite obvious for the first iteration as every rank proposed a sparse array and therefore every rank has set the flag 'isDense' to \textbf{false}. So the sparse send as well as the function to combine of two sparse arrays is executed. In $\Call{combineSparseSparse}{~}$ $s$ gets increased by the amount of received elements which corresponds to the amount of elements $\varphi_{\hat{r}}$ of the 'from'-rank $\hat{r}$. With the condition $\sum_j\varphi_j\leq c$ and  $\varphi_j \geq 0$ one can see that the sparse size $s_r$  of rank $r$ is after the first iteration bounded by $c$ (using the estimation $s_r = \varphi_r + \varphi_{\hat{r}} \leq\sum_j\varphi_j<c$). Therefore, the sparse representation is kept and 'isdense' is still set to \textbf{false}.\\
	The argument for the following iterations is the same using the assumption that the statement holds in the iteration before. As at the start of the iteration 'isdense' is set to \textbf{false} on all ranks the sparse send is executed for all of them. This leads to the combination of a received sparse array with the local sparse array. The total amount of saved sparse elements is the sum of $s$ with the number of buffered elements $b$. As the iterations before performed a subresult of an Allgather the total amount of buffered elements is bounded by the total sum of sizes of the proposed sparse arrays ($s+b\leq \sum_i \varphi_i$). So again the \textbf{if}-condition in line \ref{UnionShiftCombineSparseSparse:addSizeBuff} of $\Call{combineSparseSparse}{~}$ (Algorithm \ref{algo:UnionShiftCombineSparseSparse}) is fulfilled, because one can estimate $s+b\leq \sum_i \varphi_i \leq c$. The sparse format is therefore kept and 'isdense' is still set to \textbf{false}.
\end{proof}
\begin{corollary}\label{coro:UnionSparse}
	If all ranks $r$ propose a sparse array and the sum over all set fillings $\sum_r\varphi_r=\Phi$ is less than the critical size 'sizeCrit' \texttt{Union\_Shift} performs an unordered Mostly Halving Allgather.
\end{corollary}
\begin{proof}
	Under the condition $\Phi<c$ all iterations of the Mostly Halving Algorithms are executed and the flag 'isDense' is still set to \textbf{false}. Therefore, the \textbf{if}-statement in line \ref{UnionShift:sparseCompleted} is fulfilled and eventually buffered elements are put into the sparse array. At this point all steps of the Mostly Halving Algorithms are performed, but the reordering. \texttt{Union\_Shift} returns after the copy of eventually buffered elements.
\end{proof}
\begin{corollary}
	Consider that the sum over all set fillings $\sum_r\varphi_r=\Phi$ is greater than the critical size 'sizeCrit'. The flag 'isDense' will be \textbf{true} for all ranks after all iterations are executed (line \ref{UnionShift:sparseCompleted}).
\end{corollary}
\begin{proof}
	Suppose not. Then there is one rank $r$ that is still using the sparse representation. Therefore, it has never received an array in dense representation as this would lead to setting 'isDense' to true. Then in each iteration it holds a subresult of the Mostly Halving Allgather. The total size of sparse elements $(s + b)$ has to be at some point at least $\Phi$. Therefore, there is some iteration where $(s + b) > c$. This leads to a transformation into the dense format. This is a contradiction.
\end{proof}
\begin{lemma}
	Considering \texttt{Union\_Shift}: Suppose $I_d$ is empty, if the sparse representation is provided and $I_d$ is implicitly rotated, if the dense representation is used. We define the reference Reducescatter as Algorithm \ref{algo:redScatterShift} performing a bitwise OR on the dense representation and using the same Mostly Halving sequence as skips. Then for each rank the blocks $I_d[0,\dots, shift-1]$ of \texttt{Union\_Shift} are in iteration $i$ at least the same as the blocks $O[0,\dots, shift-1]$ of the reference Reducescatter, if rank $r$ uses the dense representation. "At least the same" means here that bits that are set to 1 for $O$ need also be set for $I_d$. If a rank uses the sparse representation this statement holds for an imaginary dense array $I_d$  after all elements of the sparse array $I_d$ are added using the implicit rotation.
\end{lemma}
\begin{proof}
	The statement is showed by induction. It holds before the first iteration. For the Reducescatter every rank holds only its provided input array. This is also true for \texttt{Union\_Shift} as every rank holds the whole information of the set in either the dense or the sparse representation.\\
	Assume the statement holds for the iteration before. We consider w.l.o.g. some rank $r$. There are 3 different cases. 
	\begin{enumerate}
		\item Receive dense array while holding the dense representation: \\
		Here the code is equivalent to an iteration of the reference Reducescatter. If both (received and local) arrays hold "at least the same" sub-results then the combination via the bitwise OR operator also results in an "at least the same" new dense bitarray $I_d$. The bitwise OR operation guarantees that bits that are set to 1 in either of the arrays will also be set to 1 in the resulting array.
		
		\item Receive sparse array while holding the sparse representation: \\
		As shown before rank $r$ has up until this iteration performed the Mostly Halving Allgather. According to Corollary \ref{coro:mostlyHalvingSpansSameRanks}, the Mostly Halving Allgather is constructed in a way that its sub results span the same ranks as block $O[0]$ of the reference Reducescatter. As the blocks  $O[j]$ with $j>0$ span the same or fewer ranks one can see that the Mostly Halving Allgather subresult holds again "at least the same" elements as the reference Reducescatter does.
		
		\item Combination of a sparse array with a dense representation:\\
		The sparse array holds "at least the same" subresult as the reference Reducescatter of the iteration before. The same is true for the sparse array. It does not matter which of the both arrays is received and which one is the local one. Array $I_d$ takes the dense data and the elements of the sparse data are added using the implicit rotation. This is the same as transforming the sparse array to the dense representation first and then performing a bitwise OR with the dense array. The result is the same as the combination of two dense arrays which both fulfill the invariant in the iteration before. So the procedure is equivalent to a step of the reference Reducescatter and it is shown in the case analysis of the first case that this leads to a valid statement for the current iteration.
	\end{enumerate}
	The case analysis shows that the statement holds also for the current iteration which proves the statement for all iterations.
\end{proof}
\begin{corollary}\label{coro:UnionSubset}
	If the total set filling $\Phi$ is larger than 'sizeCrit' \texttt{Union\_Shift} calculates a set $R\supseteq \bigcup_r S_r = U$ with $U$ being the union on all provided sets $S_r$ from the different ranks.
\end{corollary}
\begin{proof}
	After all iterations have completed each rank holds at block $I_d[0]$ an array that holds has at least all bits set to 1  that are also set to 1 for the reference Reducescatter. These blocks are then concatenated and distributed in the Allgather phase. The resulting array at $I_d$ has therefore at least all 1s set that an Allreduce would perform on just dense representations using the bitwise OR operator. The Allreduce would have calculated a union on all sets and setting extra bits to 1 only extends the resulting set.
\end{proof}
\begin{lemma} \label{lemma:UnionSupset}
	If the total set filling $\Phi$ larger than 'sizeCrit' \texttt{Union\_Shift} calculates a set $R \subseteq \bigcup_r S_r = U$ with $U$ being the union on all provided sets $S_r$ from the different ranks.	
\end{lemma}
\begin{proof}
	For each iteration one can state the following: If two dense arrays are combined the same blocks (of different ranks) get combined. If two sparse arrays are combined the resulting imaginary dense array holds also some subresult at each block from some ranks. If a sparse array is combined with a dense one the implicit rotated setting of bits guarantees here also that only the same blocks get combined. This results in each rank $r$ holding after the Reducescatter phase at $I_d[0]$ a bitmap that represents the set $R[r] = \bigcup_{i\in L} S_i[r]$. The  notation $S_a[b]$ represents all elements of the provided set by rank $a$ that are in block $b$ of the not implicitly rotated dense representation. The index list $L$ holds some ranks and is allowed to hold some ranks multiple times. As the union operation is idempotent this index list equivalent to a set that only holds each rank at most once.\\
	As the result blocks $R[r]$ of the Reducescatter are then concatenated and distributed over all ranks via the Allgather phase one can see that the total result of \texttt{Union\_Shift} in $I_d$ represents a set that is at most the union of all sets provided by the ranks.
\end{proof}
\begin{theorem}
	\texttt{Union\_Shift} calculates the union over all sets by the different ranks. I.e.,  after its execution each ranks holds a set representation of $U=\bigcup_{r=0}^{p-1} S_r$ with $S_r$ being the sets provided by the ranks and $p$ the number of ranks.
\end{theorem}
\begin{proof}
	Corollary \ref{coro:UnionSparse} states that an Allgather of all provided sparse arrays is performed, if the total set filling $\Phi$ is less than or equal the critical size. This corresponds to a union over all provided sets. For $\Phi$ larger than the critical size Corollary \ref{coro:UnionSubset} shows that \texttt{Union\_Shift} calculates a resulting set $R$ with $R\subseteq \cup_r S_r = U$ and Lemma \ref{lemma:UnionSupset} shows that $R\supseteq \cup_r S_r = U$. So in this case also the union over all provided sets is calculated.
\end{proof}

\subsection{Runtime estimation}
\texttt{Union\_Shift} is analyzed the same way as \texttt{Union\_Butterfly} was to get run time estimations. For this again three different scenarios are considered. For the first one only a setup is chosen where the total set filling $\Phi$ does not exceed the critical size. In this case only sparse communication is used. The second setup considers the performance where in each iteration only dense communication is used. The last and third scenario considers a setup where in each iteration of the dynamic Reducescatter phase sparse communication is used, but the critical size is exceeded after the last iteration.

\subsubsection{Purely sparse and purely dense communication}
These cases are straight forward to analyze. Considering these cases for \texttt{Union\_Butterfly} (see Paragraphs \ref{sec:UnionButterflyOnlySparseRuntime} and \ref{sec:UnionButterflyOnlyDenseRuntime}), the run behavior for these cases correspond to the foundation algorithms. This is also true for \texttt{Union\_Shift}. During the only sparse scenario \texttt{Union\_Shift} therefore executes the Mostly Halving Allgather and the execution time can be estimated as
\begin{align*}
	T_\mathrm{scen1} = \ceil{\log_2(p)}\alpha
	+ (p-1) 32 \mathrm{bit} \varphi \cdot \beta
	+ \eta \cdot \varphi \cdot 32 \mathrm{bit} \cdot \gamma_c.
\end{align*}
Here, again a uniformly set filling of size $\varphi$ is assumed. The constants $\alpha$ and $\beta$ stem from the linear cost model. Constant $\gamma_c$ describes the time to copy one bit of memory locally which is also modeled linearly. The number of iterations which execute a local copy is  denoted by $\eta$ and is bound to be at most $\ceil{\log_2(p)}$. Its exact value depends on the number of processors $p$ and Section \ref{sec:AllgatherShiftNumberOfCopies} describes how $\eta$ is calculated explicitly. As \texttt{Union\_Shift} effectively performs its foundation Allgather in this scenario the cost can directly be determined by using Equation \ref{eq:mostlyHalvingAllgatherCost} which predicts the cost of the Mostly Halving Allgather. Only the total message size $m$ needs to be replaced by the total set filling $\Phi=\varphi \cdot p$.\\
Similarly the execution time for the second scenario can be estimated. In this case the foundation Allreduce is effectively executed. One identifies that the message size $m$ of the Allreduce corresponds to the size of the underlying set $|\Tilde{S}|$. Using the cost analysis of the foundation Allreduce (Equation \ref{eq:allreduceShiftCost}) the cost is estimate as being
\begin{align*}
	T_\mathrm{scen2} = 2\ceil{\log_2{p}} \alpha + \frac{p-1}{p}|\Tilde{S}|(2\beta + \gamma). 
\end{align*}
The constant $\gamma$ refers here to the amount of time to perform a bitwise OR on one bit of memory.

\subsubsection{A worst case scenario}
As discussed in the run time analysis of \texttt{Union\_Butterfly} scenario 3 poses as a worst case scenario. Due to the same reasons mentioned in Section \ref{sec:UnionButterflyWorstCase} this also holds for \texttt{Union\_Shift}. Again the setup is that the total set filling $\Phi$ is twice the critical size $c$ in this scenario. The result is that the adaptive Reducescatter phase executes an Allgather on sparse inputs and changes after the last iteration to the dense format. \texttt{Union\_Shift} therefore does not return early and the Allgather phase for the dense blocks is required. The total run time corresponds therefore to an execution of the Mostly Halving Allgather with input blocks of size $\varphi=\frac{2c}{p}$ and the Allgather phase of Algorithm \ref{algo:redScatterAndAllreduce} with dense blocks of size $\frac{|\Tilde{S}|}{p}$. With that in mind a total estimated execution time of 
\begin{align*}
	T_\mathrm{scen3} = 2 \ceil{\log_2(p)}\alpha 
	+ \frac{p-1}{p}\left(|\tilde{S}| + c\cdot 64\text{bit}\right)\beta
	+ \eta \cdot \frac{c}{p} \cdot 64 \mathrm{bit} \cdot \gamma_c
\end{align*}
arises. For this again a uniform distribution of the sparse elements over the ranks is assumed. This worst case analysis can be used to estimate the execution time against reference implementations that only use an Allreduce or an Allgather to perform a union operation. For this again the explicit critical size $c=\frac{|\Tilde{S}|}{64\text{bit}}$ is chosen exemplarily. Using Algorithm \ref{algo:redScatterAndAllreduce} as reference for the Allreduce we estimate 
\begin{align*}
	T_\mathrm{scen3} &= 2 \ceil{\log_2(p)}\alpha 
	+ \frac{p-1}{p}\cdot 2 |\tilde{S}| \beta
	+ \eta \cdot \frac{|\Tilde{S}|}{p} \cdot \gamma_c \\
	&\leq T_\mathrm{Allred} + \eta \cdot \frac{|\Tilde{S}|}{p} \cdot \gamma_c 
	\leq \kappa_1 \cdot T_\mathrm{Allred}.
\end{align*}
The constant $\kappa_1$ is dependent on the number of processors and an lower boundary of $\kappa_1 \geq 1 + \frac{\eta \gamma_c}{2\beta(p-1)}$ is determined. With this one can see that for large $p$ constant $\kappa_1$ tends to be 1.\\
As reference for the Allgather the estimated performance Algorithm \ref{algo:circulantAllgather} is used. With this we estimate 
\begin{align*}
	T_\mathrm{scen3} &= 2 \ceil{\log_2(p)}\alpha 
	+ \frac{p-1}{p}\cdot 2 |\tilde{S}| \beta
	+ \eta \cdot \frac{|\Tilde{S}|}{p} \cdot \gamma_c \\
	&= 2 \cdot T_\mathrm{Allgath} + \eta \cdot \frac{|\Tilde{S}|}{p} \cdot \gamma_c \\
	&\leq \kappa_2 \cdot T_\mathrm{Allgath}.
\end{align*}
In this case, the constant $\kappa_2$ is bounded from below by $\kappa_2 \geq 2 + \frac{\eta \gamma_c}{\beta(p-1)}$. With a high umber of processors $\kappa_2$ tends go to $2$.\\
With the same argument discussed in Paragraph \ref{sec:UnionButterflyWorstCase} it is possible to find such constants $\kappa_1$ and $\kappa_2$ for other critical sizes $c$. As a worst case is discussed the execution time of \texttt{Union\_Shift} is therefore bound by 
\begin{align*}
	T_\mathrm{Union\_Shift} \leq \kappa \min(T_\mathrm{Allred}, T_\mathrm{Allgath})
\end{align*}
with $\kappa$ being the larger value of $\kappa_1$ and $\kappa_2$.

\section{Naive Approaches} \label{sec:NaiveApproaches}
We also propose three naive approaches that partially will be used to give a reference for the performance benchmark. These approaches are solely built out of native collective communication blocks provided by MPI. The first one uses only the dense representation and a call to MPIs native \texttt{MPI\_Allreduce} with a logic OR operator to calculate the union over all ranks.\\
As second option we propose an Allgather that only uses the sparse representation. MPI provides for this problem only the function \texttt{MPI\_Allgatherv} which needs to know in advance how long the messages are that each rank proposes. To get the size information of the messages of the other ranks a call to \texttt{MPI\_Allgather} is needed. The naive approach for combining sparse arrays of unknown size is shown in Procedure \ref{algo:naiveAllgather}. 
\begin{algorithm}[h]
	\caption{Implementation of the naive Allgather set union.\\
	$I_s$: input array with sparse representation of $S_r$\\
	$sparseSize$: length of sparse list} \label{algo:naiveAllgather}
	\begin{algorithmic}[1]
		\Procedure{NaiveAllgather}{$I_s, sizeSparse$}
			\State sizes $\gets$ \Call{MPI\_Allgather}{$sizeSparse$}
			\Comment{Find sizes of other ranks}
			\State $\Call{MPI\_Allgatherv}{I_s, \text{sizes}}$
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
\\Both these approaches need to guarantee that either all ranks use the sparse or all ranks use the dense format. We propose Algorithm \ref{algo:naiveMixed} as a mixed method which only uses native collective communication provided by MPI. 
\begin{algorithm}
	\caption{Implementation of the naive mixed method set union.\\
		$I_s$: input array with sparse representation of $S_r$\\
		$sparseSize$: length of sparse list\\
		$I_d$: input array with dense representation of $S_r$\\
		$isDense$: bool to indicate, which representation holds} 
	\label{algo:naiveMixed}
	\begin{algorithmic}[1]
		\Procedure{NaiveAllgather}{$I_s, sizeSparse$}
		\State critSize $\gets$ \Call{getCritSize}{~}
		\If{$isDense$}
			\State $sizeSparse \gets$ critSize $+ 1$
		\EndIf
		\State sizes $\gets$ \Call{MPI\_Allgather}{$sizeSparse$} \label{naiveMixed:algatherSize}
		\Comment{Find sizes of other ranks}
		\State totalSize $\gets \sum_{i=0}^{p-1}$ sizes[$i$]
		\If{totalSize $\leq$ critSize}
			\State $\Call{MPI\_Allgatherv}{I_s, \text{sizes}}$
		\Else
			\If {\textbf{not} $isDense$}
				\State $\Call{TransformToDense}{I_d, I_s, sparseSize}$
			\EndIf
			\State $\Call{MPI\_Allreduce}{I_d, BOR}$
			\State $isDense \gets$ \textbf{true}
		\EndIf
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
Here one can see that the strategy is selected beforehand and either an Allgather is executed on the sparse representation or the dense representation is used which is then combined using an Allreduce. The selection is done by finding the set fillings $\varphi_r$ of all ranks $r$ by performing an Allgather on '$sizeSparse$' and then calculating the sum of all sizes. This is the same as the total set filling $\Phi$ which is then compared against the critical size. If the total set filling does not exceed the critical size the sparse variant is used and in the other case the dense Allreduce is executed. If one rank proposes a set in the dense format it sets its sparse size to 'critSize$+1$' so the total set filling $\Phi=\sum_{i=0}^{p-1}\varphi_i$ is guaranteed to exceed the critical size and all ranks will use the dense format. Ranks holding the sparse format need to transform to the dense one, if the Allreduce is used. This is indicated by the function $\Call{TransformToDense}{~}$.\\
%The interface of the native MPI functions is heavily simplified for this pseudocode. The Allgather in line \ref{naiveMixed:algatherSize} returns a new array which holds the sparse sizes of all ranks. The original MPI-interface for the C language requires here actually an pointer to allocated memory that can be filled alongside with size information on the allocated output array, input array, datatype information and which ranks are going to participate (via a communicator struct). This additional information is technically also required for the later call on $\Call{MPI\_Allgatherv}{~}$ or $\Call{MPI\_Allreduce}$. On these calls the result of the Allgather/Allreduce is directly saved on the input array. \\
The methods where only the sparse or only the dense variant are used are later used as a reference for the performance evaluation. The mixed variant is not used as the pure variants provide already a lower limit on the performance that can be achieved using only native collective communication provided by MPI.

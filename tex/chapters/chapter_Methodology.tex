\chapter{Methodology} \label{chap:methodology}
In this chapter, the general strategies and methods that are used to develop and evaluate the proposed implementations are presented. We clarify how decisions are made for both of these processes. Moreover, we specify what exactly this thesis tries to achieve and therefore formulate a distinct set of research questions. Details on how these strategies and goals are fulfilled are not part of this chapter, so one should only get an overview here.\\
The first goal is to find an algorithm that can calculate the set union of sets that are distributed over different processors. This algorithm should take advantage  of different representations of a subset and therefore be built like a mix of an Allreduce and an Allgather. As communication patterns differ for Allreduce/Allgather implementations where the number of processors $p$ needs to be a power of two compared to general $p$ implementations, we have to find two different variants of the algorithm. One needs to work correctly for the case if $p$ is a power of two and the other one should work for $p$ being any number. The reason to include the variant that is constrained to $p$ being a power of 2 is that we expect this variant to perform better. These algorithms should scale well for large sets $\tilde{S}$. Precisely, the execution time of these algorithms should scale at most linearly with the size $|\tilde{S}|$. These algorithms should use the different representations efficiently. The newly proposed algorithms are oriented at known Allreduce/Allgather algorithms. We choose Allreduce/Allgather implementations as a foundation where one expects the most (performance) benefits by switching between both representations.\\
These newly built Algorithms as well as their corresponding Allgather and Allreduce implementation will be tested experimentally in regard to performance. For testing the performance, different MPI-libraries (i.e., OpenMPI, MPICH and IntelMPI) will be used. Algorithms will then always be tested using their respective best performing library. This benchmarking will be done while varying different problem parameters like the universe set size $|\Tilde{S}|$, the total set filling $\Phi$ or the distribution of set elements to the processors. All benchmarking measurement will be done on the same cluster. For this a small variety of layouts of used processors will be used. We are aware that this can lead to optimizing to a specific setup, but this is unavoidable, and we still expect similar performance on similar setups. To evaluate the performance of the newly proposed algorithms they are compared against their respective Allreduce and Allgather implementations. \\
To get better estimates for time measurements experiments are executed multiple times. There is a strategy of only considering the best run times for evaluation \cite{traeff2025}. This strategy could avoid the skewing of data due to outliers. In this thesis we chose to use the mean as the decisive statistic to evaluate performance. This also allows doing some error estimation using the standard deviation. To reduce the influence of outliers we prune the data and remove some of the highest and lowest values (symmetrically). Details on the data (pre-)processing are explained in Section \ref{sec:benchmarkingProcess}. In the case that calculated values depend on observables with statistical variation Gauss error propagation is used to get an estimate for their standard deviation.\\
Correctness of the implementations is also explicitly considered. For all produced algorithms there are theoretical proofs of correctness or at least a sketch of it. To verify them there is also empirical testing done. Precisely, there are unit tests executed and the union set operation is tested  in a BFS (Breadth First Search) implementation to validate correctness.\\
This BFS implementation also serves the purpose to test the performance of the newly proposed algorithms in a real world example.
Lastly we define here the research questions that this thesis should cover. These are stated as separate questions in the following listing:
\begin{itemize}
	\item Can we find regimes where our proposed algorithms outperform procedures that are only an Allgather or only an Allreduce?
	\item How close are our proposed algorithms to the best native variant? 
	\item How do different setups influence the execution time? We vary number and distribution of processors on the cluster and the sizes of the original subsets.
	\item What is the influence of the tunable parameter 'critSize' (Description of 'critSize' in Section \ref{sec:requiremtsOnInputParameter})? Is there an optimal strategy?
	\item Are the new union algorithms applicable to a BFS implementation? Are there performance gains visible?
\end{itemize}

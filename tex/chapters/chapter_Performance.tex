\chapter{Performance of the Proposed Algorithms}
In this section the performance of the algorithms is tested. It is evaluated which MPI libraries produce the best results, which foundation algorithms are the fastest and how the newly proposed algorithms compare to implementations only using native MPI collective functions. Moreover the newly proposed algorithms are tested in a use case to perform a \gls{bfs}. Before the actual results are presented the setup and the benchmarking process is described.

\section{Setup}
All implementations are tested on the same machine. They are run on the \emph{Hydra} cluster of the Parallel Computing Department of TU Wien. The cluster consists of 36 compute nodes and each node is equipped with two Intel\textsuperscript{\textregistered} Xeon\textsuperscript{\textregistered} Gold 6130F 16-Core CPUs. Each compute node has therefore 32 cores available. The nodes are connected via dual Intel\textsuperscript{\textregistered} Omni-Path interconnect with an upper boundary of 100 Gbytes/s bandwidth \cite{traeff2025}. The code for all experiments is written in C using \gls{mpi} as message passing framework. The code is always compiled using the \texttt{-O3} flag. Three different MPI-libraries are considered for benchmarking the algorithms (OpenMPI, MPICH and IntelMPI). The available version of the OpenMPI library as well as the MPICH library use GCC 12.1.0 as compiler. The available IntelMPI framework uses GCC 10.2.1.\\
Different setups of the number of used processes and their distribution on the nodes are tested. As the new algorithms are designed to be optimal for a large amount of processors, the configurations will cover the most available number of processors $p$. One needs to keep in mind that some algorithms will only work for $p$ being a power of 2. So for the power of two case there are $32\times 32 = 1024$. As one node was not available the general case is chosen to be $34\times32=1088$. To use 34 nodes instead of all 35 remaining nodes is done, because this arises a more regular and therefore more realistic scenario. We also test the algorithms with only one process on each node to allow only communication via the interconnect. In this setup the linear communication cost model may apply best.
\section{Measurement of the different algorithms} \label{sec:benchmarkingProcess}
Benchmarking algorithms on distributed systems is not a trivial task and is there are many caveats that need to be considered. To get a fair, reliable and reproducible results the methodology is closely oriented at the work of Hunold and Carpen-Amerie \cite{HunoldBench}. A major problem in timing executions is that clocks of the different processes are not necessarily synchronized. Moreover the clocks can drift out of sync over a period of time. A simple but sufficient strategy is to synchronize all processors using \Call{MPI\_Barrier}{ } . This function guarantees that no process proceeds its execution until every process called it. This of corse does not directly imply that all processes continue execution at the same time, but it is shown to be sufficient, if larger execution times are measured \cite{HunoldBarrier}. This condition is in our setup fulfilled as the newly proposed algorithms are build to optimize the union set operation for large sets which result in large execution times.\\
\begin{algorithm}
	\caption{– Measurement run of a function\\
		\textit{params}: Experiment parameter\\
		\textit{func}: Tested function\\
		\textit{nrep}: Number of executions}
	\label{algo:timingProcedure}
	\begin{algorithmic}[1]
		\Procedure{experimentRun}{$params, func, nrep$}
		\State initialize arrays $t_\mathrm{loc}$ and $t$ with $nrep$ entries
		\State\Call{SetExperiment}{$params$}
		\For{$obs \in [0, \dots, nrep-1]$}
		\Comment{Do measurements}
		\State \Call{MPI\_Barrier}{ }
		\State  $t_\mathrm{start\_loc} \gets \Call{MPI\_Wtime}{~}$
		\State execute $func$
		\State  $t_\mathrm{end\_loc} \gets \Call{MPI\_Wtime}{~}$
		\State $t_\mathrm{loc}[obs] \gets t_\mathrm{end\_loc} - \mathrm{start\_loc}$
		\EndFor
		\State \Call{Reduce}{$t_\mathrm{loc}[obs]$, $t$, $nrep$, \texttt{Max}}
		\Comment{Find execution time of slowest process}
		\State $t\gets \Call{RemoveOutliers}{t, nrep}$
		\State $mean \gets \Call{Mean}{t}$ 
		safe $mean$ in file
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
Algorithm \ref{algo:timingProcedure} shows the procedure how the execution times of the functions are measured for one experiment run. One experiment run consists out of '$nrep$' measurements of the to evaluate function, finding the slowest process, removing statistical outliers and calculating the mean of the pruned data. We now explain all of the steps and their justification.\\
The iterative measurement of the execution time is to produce statistical relevant data. Under the assumption of normally distributed data one only needs to collect a number of data points in the order of around 30 to get a good approximation of the underlying distribution. Hunold and Carpen-Amerie \cite{HunoldBarrier} showed that this distribution is generally not normally distributed so the number of iterations need to be way higher (and therefore $nrep$ needs to be bigger) to get a good representation of the underlying distribution. We orient us here on their proposed value of 300 iterations. For execution times of setups that have a relatively long execution time (in the order of tens of milliseconds) we only iterate 10 times as the relative statistical spread is expected to be quite low. This makes the total process of benchmarking more time efficient.\\
The next step is to only select for each iteration only the slowest process. This is justified as an estimation of the total execution time is needed. Precisely this time starts when the first process calls the tested function and end when the last thread returns from it. As all threads are assumed to enter the test function at the same time (due to the Barrier-synchronization) the execution time of the slowest process is needed. In the pseudocode from Procedure \ref{algo:timingProcedure} this is done by the \Call{Reduce}{ } call using the \texttt{Max} flag. This puts for each entry of '$t_\mathrm{loc}$' the maximum value of all processes (i.e. the slowest execution time over all processes) into the array '$t$' of the master process.\\
So after that there is an array $t$ with $nrep$ data points of the slowest processes. This data is usually sprinkled with statistical outliers. These outliers can have different reasons of existence. One reason is the scheduling of the operating system that can introduce noise. Another processes that introduces unwanted statistical invariance is that big parallel machines need some iterations to warm up. This means  that after a few iterations the execution time will be faster and will reach then a steady state. It is hard to estimate when a setup is warmed up so this will also handled by the pruning of the data. The removal is done according to Turkeys filter \cite[p.126]{TurkyRule}. For this the first quartile $Q_1$ and third quartile $Q_3$ of the measured execution times of one experiment run are relevant. With these the interquartile range $IQR = Q_3 - Q_1$ is calculated. Then only values $t_i$ are accepted which fulfill
\begin{align*}
	Q_1 - 1.5\cdot IQR < t_i < Q_3 + 1.5 \cdot IQR.
\end{align*} 
The remaining data points (which can be expected to be the majority for an fairly bell shaped distribution) are used to calculated the arithmetic mean $\bar{t}_r = \frac{1}{n} \sum_{i=0}^n t_i $ of one single run. Another good estimator for comparing the execution times of two experiment runs would be the median. The restriction to only calculating the mean is mostly to keep evaluation as simple as possible. As this calculation is done consistently for all experiment runs we can guarantee fairness in comparisons. 

One experiment usually consists out of multiple experiment runs. If the execution time  is examined in dependency of some parameter, then multiple data points are needed (i.e. a data point for each variation of the parameter). To avoid any bias that could arise due to the order of execution the experiment runs are shuffled randomly.\\
The typical entry points to a MPI-program running on a distributed memory machine are usually \texttt{mpirun}/\texttt{srun}. Hunold and Carpen-Amerie \cite{HunoldBench} showed that the benchmark of an function is not necessarily  independent of its execution by \texttt{mpirun}/\texttt{srun} \todo{change text to only use srun}. In their data it is apparent that the standard deviations of  multiple executed experiments can be significantly smaller than the standard deviation of the means of these experiments. So when executing the same experiment twice (with different calls to \texttt{mpirun}/\texttt{srun}) the results of the second run can lie reliably and significantly outside of the standard deviation range of the first run. This is the reason why we do not rely on calculating the standard deviations in each experiment run. Instead each experiment run is executed multiple times using different calls of  \texttt{mpirun}/\texttt{srun}. Hunold and Carpen-Amarie state a number of 30 iterations as sufficient which we therefore also use in this benchmark. A sketch on how the experimentation runs are executed is shown in Algorithm \ref{algo:benchmark}.
\begin{algorithm}
	\caption{– Benchmark of a experiment\\
		\textit{l\_setup}: List of setup parameter}
	\label{algo:benchmark}
	\begin{algorithmic}[1]
		\Procedure{benchmarkExperiment}{$l\_setup$}
		\State \Call{setupProcessors}{$l\_setup$} \Comment{Set number and distribution of processors}
		\For{$i \in \{1,\dots, 30\}$}
		\State mpirun/srun \Call{executeExperiment}{$l\_setup$}
		\EndFor
		\EndProcedure			
		\Procedure{executeExperiment}{$l\_setup$}
		\State $l\_setup \gets \Call{shuffle}{l\_setup}$
		\ForAll{$setup \in \{l\_setup\}$}
		\State $params, func, nrep \Call{getSetup}{setup}$
		\State \Call{experimentRun}{$params, func, nrep$}
		\EndFor
		\EndProcedure
	\end{algorithmic}
\end{algorithm}
After that we have for each data point 30 values. Each value corresponds to a different call of \texttt{mpirun}/\texttt{srun} and is the mean $\bar{t}_r$ of preprocessed data from (at most) 300 measurement. From these values is then the total mean
\begin{align*}
	\bar{t} = \frac{1}{30} \sum_{r=1}^{30} \bar{t}_r
\end{align*}
and as an error estimation the 95\% confidence interval
\begin{align*}
	CI_\mathrm{95\%}
	\approx 2\cdot s_t = \frac{2\sigma}{\sqrt{30}} 
	=  2\sqrt{\frac{1}{30\cdot 29}\sum_{r=1}^{30}(\bar{t}_r - \bar{t})^2}
\end{align*}
calculated. The estimation of the confidence interval is done via the standard deviation of the mean $s_t$ (also standard error) which itself is calculated by the standard deviation $\sigma$ of the sample. This approximation of $CI_\mathrm{95\%}$ is justified with simple scaling by a factor of 2 as this is the upper bound for a sample size bigger than 15 \cite{CIs}. The lower bound for this factor approaches 1.96 if the sample size is very large. This identity only holds for normally distributed data which we assume to apply here reasonably.\\
Confidence intervals are not quite common in representing error bars, but arise to good intuitive properties for visual representation \cite{touchingErrorbars}. For a 95\% confidence interval the touching of error bars correspond to a p value of 0.01 for a small sample size to a p value of 0.006 for large samples (under the condition that the sample sizes of both data points must be the same). With this setup one can identify easily if one execution time is smaller than the other by simply looking at the overlap of the error bars. This of course is not directly the same as a proper statistical test (like a t-test or U-test) but is seen to be sufficient for our evaluation. 


\section{Methodology and general information of the benchmarking process}
How a measurement of run times of some setup is executed and processed is explained in the section before. We now give an insight in the reasoning why specific experiments and setups are chosen. One needs to keep in mind that there are quite a lot of free parameter that can be explored. There are three different MPI libraries, at least 4 different processor layouts ($32\times 32,~ 34\times 32,~ 32\times 1 \text{ and } 34\times 1$), different set sizes and different set fillings that need to be explored. Moreover there are different variants of the same functions and the parameter '\textit{critSize}' that need to be considered. We search especially for parameter ranges where the implementations work best or show their weaknesses.\\
So the strategy is as follows: Firstly we get an insight into which MPI library performs the best. This is only done for the MPI native Allreduce and Allgather and the foundation algorithms that build the basis of our newly proposed algorithms. In doing so we also evaluate which of the foundation algorithms will perform best. Here we only show results of one processor layout if they can be representative for all. The remaining plots are only shown in the appendix. As the sparse set representation only depends on the set filling and a set union is achieved by an Allgather only the set filling is varied for benchmarking Allgather implementation. The same is true for Allreduce implementations but with only varying the set size. Performance of these algorithms is normally plotted against message size. \\
The second step is then to compare the newly proposed algorithms against the native sparse and dense implementations. As reference the foundation algorithms are used. Again there will be plots put into the appendix if necessary.\\
As last step the performance of the proposed algorithms are tested in a use case  example. Here we use the new set union operation functions to calculate a \gls{bfs} on different graph instances. The reference algorithm will have the same structure but using a only dense representation of the subsets and an Allreduce to calculate the set union.

In this thesis message sizes are always represented as the number of elements of a set. This allows for consistent comparisons between the different set representations. 
As a reminder: A sparse representation uses 32-bit Integer, is dependent on the set filling and therefore a set filled with $n$ elements corresponds to an array using $32n \textbf{bit}$ of memory. A dense representation uses a bitmap and is dependent on the size of the underlying set $\Tilde{S}$. This dense representation for subsets of $\Tilde{S}$ therefore take $|\Tilde{S}| \text{bit}$ amount of memory. The message size (set filling) of Allgather(-like) algorithms refers always to the size of the resulting array. If not stated otherwise, the set fillings of the input arrays are in  roughly equal over all processes and therefore roughly $n/p$.\\
Most plots are showing direct execution times are mostly using a log-log scale. The run time on the y-axis allows therefore an easy visual inspection how much faster different functions are relative to each other. The choice of a logarithmic scale on the x-axis is usually due to the range of parameter that need to be presented. With a logarithmic scale details for small parameter choice can be visualized without omitting the general trend for large parameter choices.

\section{Testing foundation Allreduce against MPI libraries} \label{sec:baseAllreduce}
\subsection{Allreduce of different MPI libraries}
The first objective is to find the best MPI library to perform a Allreduce. For this the Allreduce implementations of openMPI, intelMPI and MPICH are tested. The selection of the actual algorithm is completely handled by the libraries itself. The execution time is of corse expected to grow with the message size of the Allreduce which is itself proportional to the set size $|\Tilde{S}|$ of the underlying set $\Tilde{S}$. 
As a reasonable parameter range it is chosen to test set sizes from 1000 up until 1.000.000.000 which corresponds directly to the message size in bits. The results are presented on a log-log-scale so a 1-2-5 spacing is chosen for each power of 10. As execution times are quite long for large set sizes the number of measurements for these experiment runs is reduces. In each run with a set size over $10^7$ there are only 10 measurements taken (there are still 30 runs per data point executed). 
The results for different processor layouts are shown in Figure \ref{fig:AllreduceMPIlibs}. It is apparent that MPICH performs for set sizes over 50.000.000 way worse than the other libraries. IntelMPI and openMPI perform quite equally well, but is apparent that in nearly all situations IntelMPI is faster. Only for the processor layout $p=(32\times1)$ the results show (Figure \ref{fig:AllreduceMPIlibs32x1}) that openMPI can be faster for some set sizes |$\Tilde{S}$|.  IntelMPI is therefore chosen to be the best performing library to perform a Allreduce.

\subsection{Foundation Allreduce algorithms}
Here the foundation Allreduce algorithms are tested. There are three different implementations to test. The first two are based on the butterfly communication scheme and can therefore only work a number of processors that is a power of 2. These two implementations only differ in the rank ID mapping. The first one implements Algorithm \ref{algo:redScatterAndAllreduce} and is from now on referred as \texttt{Allreduce\_Butterfly}. 
The second one is the same algorithm but with a rank ID mapping where the ID is mapped to its bit reversal. This algorithm is from now on referred as \texttt{Allreduce\_Butterfly\_Reversed}. The third algorithm uses a shift based communication pattern, is the implementation of Algorithm \ref{algo:redScatterAndAllgatherShift} and is from now on called \texttt{Allreduce\_Shift}. This algorithm works correctly for an arbitrary number of processors. 

The Allreduce implementations that are tested here are build of point-to-point MPI calls. These MPI-functions are expected to be implemented quite similarly and therefore one should only see minor influences of the chosen MPI library on the execution time. Nonetheless all three foundation Allreduce procedures are tested using all three available libraries. 
The Butterfly variants are of course only tested for the $p=(32\times32)$ and $p=(32\times1)$ setups. \texttt{Allreduce\_Shift} is tested only using $p=(34\times32)$ and $p=(34\times1)$. The result of \texttt{Allreduce\_Butterfly} using the $p=(32\times1)$ processor distribution represents all results quite well and is shown in Figure \ref{fig:AllreduceFoundationLibs}.

As a general trend it is clearly apparent that for larger set sizes all foundation algorithms perform better relative to the native Allreduce.

The run time of the Allgather is expected to be only dependent on the set filling $\Phi$ of the resulting set. The set size of the underlying set $|\Tilde{S}|$ does not have any influence here. What can have an influence on the run time is how the set elements are distributed over the processors before the union operation (aka the Allgather in this case). 
We are mostly interested in a equal distribution of these elements. In this case the set fillings $\varphi_r$ of the different ranks are more or less equal. The reason for this is that we expect this setup to be common for the motivational use case of the \gls{bfs}. So to find the best performing native Allgather of the different MPI libraries the set elements will be uniformly distributed over all processors. Other cases will be considered when the native variant is compared against the foundation algorithms.\\
The tested processor layouts are again the same combinations as in the testing of the Allreduce algorithms ($p=(32\times32),~(32\times1),~(34\times32)$ and ($34\times1$)). The range of set fillings is chosen to be 1 up to 1.000.000. Again a logarithmic scale and a 1-2-5 spacing for each magnitude is used. The result of the benchmarks is shown in Figure \ref{fig:AllgatherMPIlibs}.
It is apparent that the best MPI library for a native Allgather is not so clearly given for all setups. Even in the individual processor layouts the best performing library varies for different set fillings. Only the $p=(32\times32)$ layout gives a definite result as fastest MPI library which is IntelMPI. For $p=(34\times32)$ intelMPI is faster for set fillings above 500. Set fillings below this threshold are computed faster by MPICH and openMPI. The results of setups where only one process is used at each node are nearly identical(compare Figure \ref{fig:AllgatherLibs32x1} and \ref{fig:AllgatherLibs34x1}). In both graphs one can see clearly that intelMPI performs very differently compared to MPICH and openMPI. For set fillings up to 10 intelMPI delivers benchmark results that are more than twice as slow than the other libraries. In the range of fillings between 10 and 5000 it then clearly outperforms the contenders. For larger fillings above 5000 intelMPI is then again consistently but only slightly slower than the other MPI libraries.

As summary there can not be a general best performing MPI library identified. As we consider the processor layouts with full nodal occupation as more important and relevant IntelMPI is chosen to deliver the reference benchmark for Allgather. This is also keeps consistency with the library used for the native Allreduce. It is important to keep in mind for the further analysis that there are cases where the other libraries performs better.

\subsection{Foundation Allgather algorithms}
Here the foundation Allgather algorithms are tested. There are again three different implementations to test. The first two are based on the butterfly communication scheme and can therefore only work a number of processors that is a power of 2. These two implementations only differ in the rank ID mapping. The first one implements Algorithm roughly \ref{algo:recursiveDoublingAllgather} but is slightly adapted to work without knowing the sizes of the provided input arrays from other ranks. It is from now on referred as \texttt{Allgather\_Butterfly}. The second one is the same algorithm but with a rank ID mapping where the ID is mapped to its bit reversal. This algorithm is from now on referred as \texttt{Allgather\_Butterfly\_Reversed}. The third algorithm uses a shift based communication pattern, is the implementation of Algorithm \ref{algo:mostlyHalfingAllgather} and is from now on called \texttt{Allgather\_Shift}. This algorithm works correctly for an arbitrary number of processors. It uses a mostly halfing scheme as communication and needs to buffer some data in a separate array. Due to this extra moving of data this algorithm is expected to perform worse than a native Allgather.

\section{Comparison of Proposed Algorithms Against Their Base Variant}
In this section the newly proposed set union algorithms are tested. As reference for our new implementation the foundation algorithms, which give the basis of our new algorithms, are used. Moreover the goal is to find which of the newly proposed set union algorithms perform best depending on the setup. In this section there are now new free parameter available that need to be considered. Here the set size $|\Tilde{S}|$ and the set filling $\Phi$, which each just have an influence on either the Allreduce or the Allgather implementations, will have both an influence on the run time of the union set algorithms. Moreover there is now the parameter '$critSize$', which sets the threshold of the sparse filling to switch the representation to the dense format. Combined with the different processor layouts and different set filling distributions the parameter space is quite large. So in this section we only able to evaluate the performance for some setups.\\
The first restriction that is done is to only test the bit-reversed implementation for the Butterfly union algorithm. This Algorithm will be called \texttt{Union\_Butterfly}. As discussed before there is a trade-off in using a bit-reversed communication pattern to favor either the Allreduce or the Allgather. As the newly proposed algorithm is a mix of both a decision needs to be done, which variant should be preferred. In some way the performance of the Allreduce gives the upper limit our new algorithms should take for a given set size. To not exceed this upper limit ( or rather exceed it as less as possible) the performance of the Allreduce is more important and therefore only the bit-reversed variant is tested. The version that works for an arbitrary number of processors $p$ is here called \texttt{Union\_Shift}.\\
Next some settings for the parameter '$critSize$' are analyzed and it is decided which setting is going to be used in the further evaluation.

\subsection{Different settings for the parameter '$critSize$'} \label{sec:PerformanceCriticalSize}
The parameter '$critSize$', which we now also refer to as the critical size, indicates when a set is filled too much to justify a sparse representation of it. When just considering the bare memory footprint this threshold would be at $\frac{1}{32}\approx3.1\%$ of the set size |$\Tilde{S}$| as we use 32-bit integer for the sparse representation. This may be not such a good choice for this parameter as the goal is to minimize communication cost and not overall memory footprint. The caveat of this strategy is that the sparse format is used until the last iteration of the Reducescatter phase. In the last iterations it could be that the sparse representation is a longer message than the blocks that would be sent using the dense representation. The Allreduce implementations send in each iteration $i$ approximately $2^i$ blocks of the dense array. Each dense block is approximately of size $\frac{|\Tilde{S}|}{p}$ with $p$ being the number of processors. One can therefore choose the critical size to be set such that the sparse variant is only used for set fillings that never exceed the memory footprint of one such block. It is therefore guaranteed that the sparse variant uses less time for communication in each iteration. This would equate to a critical size of $\frac{1}{32p}\approx\frac{3.1\%}{p}$ of the set size. The problem is here that for large processor numbers $p$ the sets need to be very sparsely filled to even take advantage of the sparse format. When using all $p=(36\times32)=1152$ processors of the available cluster the critical size would equate to around 0.0027\% of the  set size $|\Tilde{S}|$. The idea is therefore to also test a middle ground for the parameter '$critSize$'. For this is the average amount of data estimated that is sent during the Reducescatter phase of the Allreduce implementations. As mentioned before in each iteration $i$ there are $2^i$ dense blocks sent. In $\log_2(p)$ iterations there are therefore $\frac{p-1}{\log_2(p)}$ blocks on average sent. If the sparse array size should be limited by the mean data that is send in the Reducescatter phase, then the critical size needs to  $\frac{p-1}{32p\log_2(p)} |\Tilde{S}|$. In the following benchmark are therefor the strategies \texttt{max}, \texttt{min} and \texttt{mean} with the critical sizes 
\begin{align*}
	c_\texttt{max} = \frac{|\Tilde{S}|}{32}, && c_\texttt{min}= \frac{|\Tilde{S}|}{32p},
	&& c_\texttt{mean} = \frac{p-1}{32 p \log_2(p)} |\Tilde{S}|
\end{align*}
tested. The algorithms are designed to work more efficiently for large set sizes so for the experiments a set size |$\Tilde{S}$| of $10.000.000=10^7$ is chosen. The set filling is varied in 1-2-5 steps for each power of 10. The sets are filled uniformly over the processors. The Butterfly variant is tested for the power of two setups and the Shift variant is tested for the setups on 34 nodes. The result of the experiments is shown in Figure \ref{fig:UnionCritSize}.\\

\section{Performance Testing Using \gls{bfs} as Benchmark}
The performance of the union operation algorithms is also tested in a use case application for a BFS. For this the parallel BFS procedure shown in Algorithm \ref{algo:BFSparallel} is used. Here the union algorithms define the implementation for the placeholder function \Call{unionAll}{$S_r$} that calculated the union of all subsets $S_r$ over all participating ranks $r$. The benchmarking process is done in a similar way as it was done for the individual testing of the functions like it is described in Section \ref{sec:benchmarkingProcess}. Again there are 30 different calls to \texttt{mpirun} to execute an experiment. On the other hand the number of iterations for one experiment run is reduced to only 60 iterations by default and reduced to only 6 for long execution times. Another difference is here that the allocation process of needed memory is taken out of the measurement loop to create a faster benchmarking process. The memory for the sets '$visited$', '$frontier\_old$' and '$frontier\_new$' are therefore allocated in advance. We do not expect to skew the benchmark results with this decision as the allocation process needs to be done for all BFS implementations.

\subsection{Description of used graphs}
Although the graph500 \cite{graph500} benchmark framework is used for validating the BFS and set union implementations it lacks on flexibility. The generated graphs are constrained to only consist out of nodes that count to a power of two and the number of edges can only be set to a integer multiple of the number of nodes. Most importantly there is no influence on the actual topology of the graphs possible. This is the reason why two graphs from the \newacronym{snap}{SNAP}{Stanford Network Analysis Project} \gls{snap} are chosen to build example graphs to test the different implementations. The first one is \texttt{ego-twitter} describing a social network graph of the social media platform \textit{Twitter}. It consist out of around 81 thousand nodes and around 1.8 million edges. The longest shortest path is 7 and the effective diameter is 4.5. The other graph is called \texttt{com-LiveJournal} and describes the relationship of users that declared to be 'friends' on a online blog website called \textit{LiveJournal}. This graph holds nearly 4 million nodes which are connected by around 35 million edges. It has an diameter of 17 and an effective diameter of 6.5.

Using these both graphs three different example graphs are build. The first one is solely built from from \texttt{ego-twitter}. The goal for this first example graph is to build a graph with a long topology such that the frontier during the \gls{bfs} is quite small and the performance increase of the sparse representation can be exploited. The graph \texttt{ego-twitter} is available as a list of edges which is distributed over 973 files. Each of these files is now interpreted as a disjoint graph. These disjoint graphs are then connected in order of the filename ordering resulting in a long extended graph. Each connection is done by just two newly added edges. This results in a graph that has approximately the same number of edges as \texttt{ego-twitter} but now with a diameter over 1200. This graph is from now on called \texttt{example\_long}. To get a BFS traversal that propagates from one side to the other a root node will chosen that stems from the first file.\\
The second graph should show the behavior for an unmodified larger graph. Therefore just the graph  \texttt{com-LiveJournal} with around 4 million nodes is used. This graph is from now on called \texttt{example\_big}.\\
The last graph should show the behavior of disjoint graphs. Therefor the disjoint graphs from  \texttt{com-LiveJournal} and \texttt{ego-twitter} are all put together but without adding connection edges. This graph is called \texttt{example\_disjoint}. This graph is tested for two different root nodes. One is part of a \texttt{ego-twitter} subgraph and the other is originally held by \texttt{com-LiveJournal}.\\
All graphs are interpreted as undirected graphs.

\subsection{BFS on $p=(32\times 32)$ setup}
The \gls{bfs} implementations are here on 32 nodes using 32 processors each tested. In total there 5 different implementations to test. Firstly the newly proposed algorithms  \texttt{Union\_Butterfly} and \texttt{Union\_Shift} are used to calculate the set union of the newly explored frontier. This frontier can here either be represented in the sparse or the dense representation. Then the corresponding foundation algorithms  \texttt{Allreduce\_Butterfly\_Reverse} and \texttt{Allreduce\_Shift} are tested. For this only the dense representation is used. This is also true for the standard MPI Allreduce implementation provided by IntelMPI which is here called \texttt{MPI\_Allreduce}. The general structure of the BFS is in all implementations identical. Only the calculation of the union operation over all ranks for '$frontier\_new$' is adapted.\\

The main conclusions from this testing are that \texttt{Union\_Butterfly} is preferred over \texttt{Union\_Shift} in this setup and this union operation algorithm can indeed bring performance benefits compared to a BFS that uses a native MPI Allreduce.

\chapter{Implementation} \label{Implementation}
   6
Here we want to describe the developed algorithms. As already mentioned in the introduction the goal is to efficiently calculate the union $U$
   7
where every processor $r$ provides a subset $S_r\subset \tilde{S}$ from a known set $\tilde{S}$ of fixed size. The union
   8
\begin{align*}
   9
U = \bigcup_{r=0}^{p-1} S_r
  10
\end{align*}
  11
should be available for every processor. $p$ is here the number of processes. \\
  12
A straight forward approach to tackle this problem is to create a bitmap for each process, give the elements of $\tilde{S}$ an explicit ordering
  13
and map each element to a bit of the bitmap. An element $e$ is then defined as being in the subset $S_r$, if the the corresponding
  14
bit is set to 1 and set to 0 otherwise. The union can then easily be calculated by performing a bitwise OR-operation over all
  15
bitmaps from all processes as the union over all subset $S_r$ is defined as
  16
\begin{align*}
  17
U = \{x \in C | x \in S_0 \lor x \in S_1 \lor \cdots \lor x \in S_{p-1} \}.
  18
\end{align*}
  19
This can be done using an Allreduce function. This bitmap needs to cover all elements of the original set $\tilde{S}$. Therefore it needs to take at least $N=|\tilde{S}|$ amount of data. As a word size of 64-bit integer is quite common on many architectures, we need $\ceil{\frac{N}{64}}$ 64-bit integer to represent a subset $S_r$. This can be wasteful, if the cardinality of these subsets $S_r$ is quite small and most bits of the bitmap are set to 0. We introduce here a simple sparse format to save memory and therefore the amount of data for communication. By using unsigned 32-bit integer, we can represent subsets of $\tilde{S}$ as an explicit list of the selected integer. Here we only can represent $2^{32}$ distinct elements so the cardinality of $\tilde{S}$ is bounded by $2^{32} \approx 4.2\cdot10^9$. The benefit is now that the size of the sparse representation only depends on the cardinality of the subset $S_r$. We can calculate the memory footprint $m_\mathrm{Sparse}$ of this representation as being
  20
\begin{align*}
  21
m_\mathrm{Sparse} = \varphi_r \cdot \qty{32}{\bit},
  22
\end{align*}
  23
where $\varphi_r = |S_r|$ is the cardinality of $S_r$. To calculate the set union $U$ one needs to concatenate all these distributed lists $S_r$ ($S_r$ is here represented as a list). This can be done by an Allgather. One needs to keep in mind that the result $U$ may contain elements twice. One can either decide that this not a problem or change representation and convert the list into a bitmap. A bitmap can not contain elements twice and therefore duplicates are removed. \\
  24
We chose algorithms that scale well for a large number of processors $p$ and large number of elements of the base set $N$. For the Allreduce these properties are best fulfilled by any of the Reducescatter-Allgather algorithms. We moreover can identify that the communication pattern of the Reducescatter phase always resembles that of an Allgather. This can easily be seen for the Butterfly algorithm and the Ring algorithm. For the approximate halfing pattern there is also an Allgather known \cite{allgatherTraeffOld}.\todo{Add section for this Allgather implementation in Introduction chapter.} The problem here is that the skip sequence is used in reversed order compared to the one used in the Reducescatter phase from Section \ref{sec:approxHalfRedScat}. For this pattern is a new adaptation found which is shown in Section \ref{sec:irregularImpl}. \\
  25
The general idea is therefore to overlay an Allgather using the sparse representation over the Reducescatter phase of the corresponding Allreduce algorithm. When it is more efficient to use the bitmap variant one switches to this representation and finishes the Allreduce algorithm. This is possible as the subsolutions of the Allgather span the same processes as the subsolutions of the Reducescatter do. As the sparse representation holds the complete information of a ranks input and the dense representation uses only blocks of it, one does not lose any information, if we switch from sparse to dense. This implies of course that a switch from the bitmap variant back to the sparse one is not permitted. How and why these ideas work is proved and explained in the upcoming respective sections.\\
  26
If the sparse variant is still used for the last iteration of the Reducescatter phase the algorithm performed de facto an Allgather and therefore the second phase (Allgather phase of the Allreduce) is not necessary. Moreover the sparse variant may be shorter in message size than the blocks send in Reducescatter phase of the dense representation. So here it is also possible that the total amount of sent data can be reduced.\\
  27
This is also relevant in choosing the foundation Allreduce algorithms for the newly developed ones. The Ring algorithm sends in each iteration only one block of data. The algorithms that are based on recursive (approximately) halfing send in iteration $i$ (roughly) $p/2^i$ blocks. Sending a sparse representation is therefore more efficient in the later algorithms compared to the Ring algorithm. We here replace the message size of multiple blocks instead of only one. This is the reason we chose recursive (approximately) halfing algorithms as base Allreduce algorithms over the Ring algorithm.\\
  28
Moreover we chose two different approaches in communication schemes. One is chosen to be the Butterfly scheme as we may expect better performance of this scheme as it can be arranged in a way that possibly faster intra nodal communication can be exploited in some situations (see run time estimation in Section \ref{sec:DisseminationAlgo}). A big drawback of this scheme is of course that it is limited to only work correctly on a setup where $p$ is a power of two. So on the other hand we want to propose an adaption of the approximate halfing scheme to create an algorithm for arbitrary number of processes. These two adaptations are shown in the next sections.

\subsection{Concept and Explicit Implementation}
  32
As mentioned before the base communication scheme is the Butterfly scheme. In each iteration there is communication between pairs of processors, meaning, if rank $r$ sends a message to its partner $\hat{r}$, then $\hat{r}$ sends in this iteration also a message to $r$. The communication partner is found by flipping the $i$-th bit where $i$ is the iteration. The difference between IDs of communicating ranks is from now on called 'shift'. 'shift' also used as variable name in the according pseudocode \ref{algo:SetUnionExactHalfing}. As this variable is set to $p/2$ in the first iteration ($i=1$) and is halved every iteration, we can identify its value as being $p/2^i$. Moreover we see in the implementation that the algorithm consist out of an adapted Reducescatter phase and an Allgather with the exact same communication scheme like Algorithm \ref{algo:redScatterAndAllreduce}. To be precise it is identical, if the own representation as well as the received representation is always dense. The receiving part for this situation is hidden behind the function $\Call{combineDenseDense}{ }$. This is done for all possible combinations to get a better overview of the control flow. The functionality of all cases is explained a little bit later in this section. Firstly we want to describe the control flow to get a better understanding of the general ideas.\\
  33
We see that in the adapted Reducescatter phase there are two different possibilities which kind of data is send. If variable $isDense$ is true, process $r$ holds currently data in dense representation and therefore sends dense data blocks accordingly to the recursive halfing scheme. An add-on is here that the message is also marked with an label "dense". If variable $isDense$ is false, process $r$ holds currently data in sparse representation and sends its whole array of sparse elements. In this case the message gets obviously tagged with "sparse". After rank $r$ has posted a send it is ready to receive some data. This is done in one of the "combine" functions depending on the state of $S_r$ and the representation of the received message.

\\We also want to mention here that these sends differ from the $\Call{Send}{ }||\Call{Recv}{ }$ procedure used in all algorithms before. The sending and receiving is now not done by the same function where everything is handled by an already implemented library. When called separately the send obviously needs to be called before the receive and usually is
  85
\emph{blocking}. Blocking means here the function only returns after the message is completely send. To complete a send another process needs to expect some data from the sending rank. This can lead to a deadlock situation. If process $r$ sends a message to process $\hat{r}$ and process $\hat{r}$ wants to do the same the other way around, both of them can not return from the $\Call{Send}{ }$ function as none of them is already ready to expect a message. So in this implementation we use non-blocking sends. For this some extra handling is needed. As the send function returns immediately one does not want to change the buffer array that needs to be send until the message is completely sent. To guarantee safe usage of the send array the function $\Call{Wait}{ }$ is used. It blocks further execution of the program until the corresponding buffer is safe to use again. In \gls{mpi} this actually handled by an extra request object, but we want to keep notation simple and define the input parameter of $\Call{Wait}{ }$ as the corresponding input array. \\
  86
Looking at the input arrays $I_s$ and $I_d$ we want to give some requirements about them. Firstly one of them is (needs to be) valid. $I_s$ is used to hold information of subset $S_r$ in the sparse format. It is valid and needs to be filled, if $isDense$ is set to false. It consists out of 32-bit integer and holds $sparseSize$ elements that correspond to the elements of $S_r$. The array needs have enough memory allocated to hold two times 'critSize' elements. When indexing this array we refer to single elements of this array. The same conditions holds for the extra buffer array $\Tilde{I}_s$. $I_d$ holds the bitarray representation of $S_r$ and needs to be filled, if $isDense$ is true. It is assumed to be empty (filled with only zeros), if the sparse variant is used as input. Its size is given by $bitarraySize$. The corresponding extra buffer $\Tilde{I}_d$ needs to be able to hold half of the biggest blocks of $I_d$. Both $I_d$ and $\Tilde{I}_d$ are assumed to be divided into $p$ blocks. These blocks are assumed to be roughly equally sized and hold approximately $bitarraySize/p$ amount of data. Indexing these arrays therefore refers to blocks of data. To assure these conditions the initialization of the arrays, calculation of the blocks and adding of elements to $S_r$ is hidden from the user in the original implementation.\\
  87
Another function that needs to be explained is $\Call{Probe}{ }$. This function returns a status object for messages that rank $r$ receives from rank $\hat{r}$. This status object holds information about the tag that was added by the sending rank and how long the message is. The tag is needed to identify, if data received in a dense or a sparse variant. The size information is only needed, if a sparse array is received. In this case a processor does not know how many elements are added to the subset $S_{\hat{r}}$ it is receiving and therefore the message size is unknown. This problem does not arise in the dense variant as here are always a known amount of blocks of the array sent by $\hat{r}$ which can also be calculated by $r$ using $\hat{r}$ rank ID.\\
  88
The next important feature we want to mention is the variable 'critSize'. It defines the boundary which decides, if $r$ should use the dense or sparse representation for its subset $S_r$. 'critSize' is compared against the size of $S_r$ $\varphi$. If $\varphi$ is bigger than 'critSize' process $r$ uses the dense variant and if it is smaller the sparse format is used. There can be different strategies on how to chose 'critSize' which is for now hidden behind $\Call{getCritSize}{ }$ and explained later.\\

As we see there are four different possibilities depending on the representation of the received message (identified by 'status.tag') and on the representation rank $r$ currently uses (identified by $isDense$). In all cases we somehow want to combine the (possible) different representation into a definitive one. We start with the case where the receiving message as well rank $r$s representation is dense. In Algorithm \ref{helper:combineDenseDense} we see the procedure for this case and can identify that it is nearly the same as the receive handling of the Reducescatter phase in the Butterfly recursive halfing Allreduce algorithm (compare to Algorithm \ref{algo:redScatterAndAllreduce}).

One small difference is here that the send and receive is not handled in the same function. The sending rank $\hat{r}$ used a non-blocking send and maybe also rank $r$ did and used $I_d$ in the same iteration for sending a message. Therefore we need to check, if buffer $I_d$ is already safe to use and wait, if this is not the case. The other difference is the reduce operation. It is now not a general associative operator $\oplus$ anymore, but instead the explicitly defined bitwise OR ($\lor$). This is of corse done as the bitwise OR performs a logically the set union of two bitmaps. Calculations of the block indices for the receiving block range are still exactly the same as in Algorithm \ref{algo:redScatterAndAllreduce}. Also the received blocks are "added" to the same range of blocks of $I_d$. We can summarize that after an iteration where $\Call{combineDenseDense}{ }$ is used a standard step of the Butterfly Reducescatter phase is performed.\\

After this the marker $isDense$ is set to true. As we only want allow a switch from sparse to dense it only makes sense that after the combination of a sparse and dense representation the resulting format needs to be dense. What this procedure effectively does is creating the correct subresult for blocks $I_d[\text{startBlockR}, \dots, \text{endBlockR}-1]$ of ranks that contributed to a subresult to $\hat{r}$ or to a subresult to $r$. That the subresult of $\hat{r}$ for these blocks are now correctly in place is obvious as they where directly copied into $I_d$. The integration of the correct blocks of the subresult of $r$ is also straight forward. In the sparse representation array $I_s$ holds information of all blocks and not just of a subset. But the algorithm is build in a way that there are communication partners for each iteration, meaning, if $r$ sends a message to $\hat{r}$, it will also receive a message from $\hat{r}$. This implies that when considering such a pairwise communication round, there only 3 cases to be considered. Either both are using the dense representation, both use the sparse one or they use different ones. \subsection{Proof of Correctness}
 313
For now we only explained the structure and ideas making this algorithm work. We want to formalize these ideas into a proof of correctness. For this we firstly want to find an invariant that describes the state of each iteration in the adapted Reducescatter phase. Before this is possible we need to find some bookeeping properties. We want to count iterations from $1$ to $\log_2(p)$. The variable 'shift' is set to $p/2$ in the first iteration and divided by two until it is $1$ in the last iteration. This makes it obvious why there are $q=\log_2(p)$ iterations in total ($p$ is required to be an exact power of 2). In this section we going to use the symbol $s_i=p/2^i$ for the variable 'shift'. One can easily see that $s_i$ is also always a power of two. This means in the binary representation it has only one bit set to 1. So when we perform an exclusive OR (XOR) with some number $x$ we basically add or subtract $s_i$ to $x$. If an addition or a subtraction is performed is dependent on the bit that is effectively flipped. The index of this bit is now called $f$. One key insight is here that communication partners rank ID $\hat{r}$ is $s_i$ less or more than the rank ID $r$ one currently considers. We further want to state that ranks $r_a$ for which holds $r_a \mod{2\cdot s_i} < s_i$ have communication partner $\hat{r} = r_a + s_i$, while ranks $r_b$ with $r_b \mod{2\cdot s_i} \geq s_i$ communicate with $\hat{r}= r_b - s_i$. This also quite obvious as one can see that $r_a$ must have the $f$-th bit set to 0 and $r_b$ must have set it to 1. We can therefore divide the ranks into groups of size $2\cdot s_i$. These groups can be split in half (of size $s_i$) and we can see that the lower half communicates with the upper half. We will also refer to them as the \emph{left} and \emph{right} half. We want to call these groups of ranks in iteration $i$ $g_0^i, \dots, g_{k-1}^i$. As there are $k$ groups of size $2 s_i$ and there are a total amount of $p$ ranks, we can identify $k=p/(2s_i)=2^{i-1}$. We also want label the split up groups $\tilde{g}_0^i, \dots, \tilde{g}_{2k-1}^i$. When $j$ is the index of the original group and $\tilde{j}$ is the index of a group half, then halved with index $\floor{\tilde{j}/2}$ belong to group $g_j$. One can also easily see that the group halves $\tilde{g}_j^i$ of iteration $i$ correspond to the groups of iteration $i+1$ $g_j^{i+1}$. \\
 314
We firstly want to consider a simple case and prove correctness for it. Assume only sparse communication is used. This means all ranks submitted its subset $S_r$ in sparse format and the critical size is never exceeded. Then we can state the invariant that each group half $\tilde{g}_0^i, \dots, \tilde{g}_{2k-1}^i$ contains the total unified set $U$ distributed over all ranks of $\tilde{g}_j$. This means if we would concatenate all sparse arrays $I_s$ of ranks that are in the same group half we get the sparse representation of $U$. The invariant holds quite trivially before the first iteration. Here there is only one group "half" and it spans all processors $p$. As all processors hold here only their sparse representations of their input sets $S_r$, a concatenation of all these sparse arrays is clearly the total set union $U$ in sparse representation. Now we do the induction step and assume that the invariant holds in iteration $i$. We see that now in iteration $i+1$ there are groups $g_0^{i+1}, \dots, g_{2^{i}-1}^{i+1}$ which correspond to the group halves of the iteration before. In each of these groups the left half communicates with the right half. As we only allow for sparse communication in this case, we know that sparse arrays from the left half get appended to sparse arrays of the right half and vice versa. As there is a one-to-one communication pattern between ranks one can see that each half contains now the total information that the whole group had before. This proves the invariant. So after $\log_2(p)$ iterations $k=p/2$ and there are therefore $p$ group halves. Each contain obviously only one rank. So now each rank holds indeed all sparse input arrays from all ranks concatenated in $I_s$. So in this case the algorithm stops early and the set union is calculated correctly.\\
 315
Now we want to show that this is indeed the only case where the algorithm can be stopped after the adapted Reducescatter phase. There are two extra conditions that are assumed for the case before. Firstly that the critical size is never exceeded. Suppose this not true in at least one iteration. The communication partner and the rank itself would therefore switch to the dense format. Every following communication partners would also be transformed to the dense format. But this may not include every process as they may not be aware that some ranks exceeded the critical size so they would continue normally. As their communication is independent at some point from the other ranks the proof from before still holds for them. So they will concatenate all sparse arrays together in the sparse format. This means they have to exceed the critical size at least in the last iteration as a smaller subresult already did for another rank. So the algorithm will not return early for any rank, if the critical size is exceeded. The second condition was that only sparse arrays are submitted by the ranks. Suppose only at least one rank committed its $S_r$ in dense representation. When remembering the case discrimination from Figure \ref{fig:3cases}, we see that only two sparsely fitted ranks can (but do not need to) keep the representations in sparse format. We now that in each iteration there is communication between one half of the group with the other. So when there is at least one dense rank in one of the halves then there will be one in both halves after the iteration has completed. One can see easily that an induction of this property leads to all ranks being dense. So if this condition is not met, all ranks will be in dense representation mode and the algorithm will not stop early.\\
 316
We still need to prove that when a rank (and therefore later all ranks) switch to the dense representation one still gets a correct calculation of the set union $U$. For this case we want to formulate a weaker invariant as before. We state that after iteration $i$ each group half $\tilde{g}_j^i$ with $j\in \{0, 2k-1\} = \{0, 2^i-1\}$ contains at blocks $I_d[js_i, \cdots, (j+1)s_i-1]$ the blocks of the total unified set $U[js_i, \cdots, (j+1)s_i-1]$ distributed over all ranks of $\tilde{g}_j$. If rank $r$ holds a sparse array the block notation holds for the corresponding hypothetical transformed dense array. We can formalize this invariant for iteration $i$ as
 317
\begin{align*}
 318
\forall j\in\{0, \dots, 2^{i}-1\} ~~ &\exists \tilde{g}_j^i~ \text{ such that }\\
 319
U_d[js_i, \cdots, (j+1)s_i-1] &= \bigcup_{r \in \tilde{g}_j^i} I_d^r[js_i, \cdots, (j+1)s_i-1].
 320
\end{align*}
 321
One can also replace here the union set symbol $\cup$ by the bitwise OR operator $\lor$ as they are equivalent for the dense representation. One can quite easily see that this invariant holds before the first iteration ($i=0$). Here there is only one $j$ possible and it is 0. The corresponding group half $\tilde{g}_0^0$ spans all processes and the equality must hold for all blocks. If ranks hold a sparse array, we transform it hypothetically into the dense one and it is obvious that the union above all ranks is the definition of $U$. Lets suppose the invariant holds in iteration $i$ and we do the induction step. In iteration $i+1$ there is communication within groups $g_0^{i+1}, \dots, g_{2^{i+1}-1}^{i+1}$ which correspond to the group halves from the iteration before. When looking at group $g_j^{i+1}$ we therefore know it holds
 322
\begin{align*}
 323
U_d[js_i, \cdots, (j+1)s_i-1] = \bigcup_{r \in g_j^{i+1}} I_d^r[js_i, \cdots, (j+1)s_i-1].
 324
\end{align*}
 325
The left half sends data to the right half and vice versa. The left half can be found by indices $\{j\cdot s_{i+1}, \dots, (j + 1)\cdot s_{i+1}-1\}$ and the right half has indices $\{(j + 1)\cdot s_{i+1}, \dots, (j + 2)\cdot s_{i+1}-1\}$. We firstly want to consider the case where two ranks are in dense representation. When looking at Algorithm \ref{helper:combineDenseDense} we see that 'startBlockR' is calculated by $\floor{r/s_{i+1}}\cdot s_{i+1}$ and exactly $s_{i+1}$ blocks are received. We can see that ranks from the left half would therefore receive blocks $\{j\cdot s_{i+1}, \dots, (j + 1)\cdot s_{i+1}-1\}$ and combine them accordingly with their dense array. The right half does this for blocks $\{(j + 1)\cdot s_{i+1}, \dots, (j + 2)\cdot s_{i+1}-1\}$. We see that block ranges and rank IDs coincide. We can therefore state for both of the group halves that it holds
 326
\begin{align*}
 327
U_d[js_{i+1}, \cdots, (j+1)s_{i+1}-1] = \bigcup_{r \in \tilde{g}_j^{i+1}} I_d^r[js_{i+1}, \cdots, (j+1)s_{i+1}-1].
 328
\end{align*}
 329
When considering the case where communication happens between a rank in sparse format and using the dense one, we can argue quite similarly to the case before. The rank with the sparse array receives exactly the blocks that it needs to fulfill the invariant property. This is quite obvious as the calculation of the received blocks (see Algorithm \ref{helper:combineDenseSparse}) are exactly the same as before. We also know (as the invariant holds) that the sparse rank holds (at least) correct information at blocks $[js_{i+1}, \cdots, (j+1)s_{i+1}-1]$. The dense rank needs either the top or the bottom half of this. As the whole sparse array is send and build into their dense arrays $I_d$ one can see that the invariant holds for this case. \\
 330
The last case where both ranks holds sparse data is the easiest one to prove. Both ranks hold (at least) correct information for blocks $[js_{i+1}, \cdots, (j+1)s_{i+1}-1]$. Again only the half of it is needed for the other rank. As the whole sparse array is exchanged, both processes will hold data that will not violate the invariant. This proves the correctness of the invariant.\\
 331
So after $\log_2{p}$ iterations there are exactly $p$ group halves each containing only one process. $s_{\log_2{p}}=1$ so we can say for each of these group halves (or respective processes) that each holds only one correct block of the set union. We have
 332
\begin{align*}
 333
U_d[j] = I_d[r]
 334
\end{align*}
 335
where $j$ can be identified as $r$. So each rank holds a block of the correct dense union set array. As we showed before either all ranks are in dense representation after the last iteration or none of the processes is. Therefore all ranks start the procedure $\Call{Allgather}{ }$ where the blocks are collected, concatenated and distributed over all processes. After this every rank has a complete dense representation of the set union $U$. As we covered all cases this proves correctness for the whole algorithm.

\subsection{Runtime Estimation}
 338
We also want to estimate the execution time of this algorithm using the linear cost model. Compared to the algorithms presented in the introductory chapter we do not expect to estimate the run time for a general case. The message size and even the structure of the algorithm depend now on the sizes $\varphi_r = |S_r|$ of the submitted subsets. So we want to give an estimation for different setups.\\
 339
The first configuration we want to discuss is the case where the sum of all subset sizes $\Phi = \sum_r \varphi_r$ is smaller than the critical size. We also assume that each rank submitted its data in the sparse format. To keep things simple for run time estimation we assume that each ran submitted an array of same size $\varphi$. With this the condition arises that the critical size must be greater than $p\cdot \varphi$. So we expect that the algorithm terminates after the adapted Reducescatter phase and effectively an Allgather over all sparse arrays is performed. We also want to mention that the uniform distribution of the input elements is actually the best case for this scenario. In each iteration the each rank sends its whole sparse array and a foreign sparse added to its own $I_s$. So in each iteration the size of the sparse array is effectively doubled. So in iteration $i$ (counting from 0) we expect that each process sends $\varphi\cdot 2^i$ amount of elements. This makes it also clear why this is a best case scenario. If the input arrays had different sizes of data, each iteration needs the time to send the longest message. \\
 340
We expect therefore that each iteration takes $\alpha + \beta \cdot \varphi \cdot 32 \mathrm{bit}$ using the linear cost model. When summing over all iterations we get an estimate of
 341
\begin{align*}
 342
T_\mathrm{scen1} = \sum_{i=0}^{\log_2{p}-1}\alpha + \beta \cdot 2^i \cdot \varphi \cdot 32 \mathrm{bit}
 343
= \log_2(p) \alpha + (p-1)\varphi \beta \cdot 32 \mathrm{bit}.
 344
\end{align*}
 345
This is the exact same run time estimation for any optimal Allgather algorithm. One needs to keep in mind that the $\varphi$ describes the size of one input. In the algorithms from the introduction the message size refers to the output message. \\
 346
The next scenario we want to propose here is also kind of a best case. We require that all processes propose an array in dense format. Therefore a pure Reducescatter is performed. In iteration $i$ (counting from 1) are $p/2^i$ blocks of roughly the size $|\tilde{S}|/p$ are sent. $\tilde{S}$ is here the total possible finite set from which the subsets $S_r$ are selected ($S_r \subseteq \tilde{S}$). Moreover there are also $p/2^i$ blocks of data combined using the bitwise OR operator. We estimate the duration of each iteration $i$ as $\alpha + |\tilde{S}| 2^{-i} \cdot \beta + |\tilde{S}| 2^{-i} \cdot \gamma_d$. $\gamma_d$ is here the time per bit to apply the bitwise OR operator. So the Reducescatter phase needs therefore $\sum_{i=1}^{\log_2{p}} \alpha + |\tilde{S}| 2^{-i} \cdot (\beta +\gamma_d) = \log_2(p) \alpha + \frac{p-1}{p}|\tilde{S}| (\beta +\gamma_d)$ amount of time. We assume that standard library implemented $\Call{Allgather}{ }$ call uses also a Butterfly algorithm and therefore takes $\log_2(p) \alpha + \frac{p-1}{p}|\tilde{S}|\beta $ amount of time. In total we can estimate the runtime as being
 347
\begin{align*}
 348
T_\mathrm{scen2} = 2\log_2(p) \alpha + \frac{p-1}{p}|\tilde{S}| (2\beta +\gamma_d)
 349
\end{align*}
 350
which is on par with the pure butterfly Allreduce implementation shown in the introduction (Section \ref{sec:DisseminationAlgo}).\\
 351
As next scenario we want to propose a simple worst case situation in terms of communication cost. The worst case scenario is that in each iteration but the last of the Reducescatter phase a long sparse message is send and in the last iteration the sparse array size exceeds the critical size. The longest a sparse message can be is $(c-1)\cdot 32\text{bit}$ with $c$ being the critical size. It is possible to assign two processes with a sparse size of $c-1$ and to the other ranks an empty sparse array such that the critical size is only exceeded in the last iteration. Therefore the algorithm can not return early and must enter the Allgather phase. Therefore are in each iteration of the adapted Reducescatter phase $(c-1)\cdot 32\text{bit}$ bits sent and received. We also need to take into account that adding sparse data to a dense array takes time. Here is also a linear relationship expected and we define the constant $\gamma_s$ as the amount of time that is needed to add one element of an sparse array to a dense one. This done in the last iteration for $2(c-1)$ elements. So we can estimate the total runtime for the adapted Reducescatter phase as $\log_2(p)\alpha + \log_2(p)(c-1)\cdot 32\text{bit}\beta + 2(c-1) \gamma_s$. Adding the expected run time for the following Allgather phase we get an estimate of
 352
\begin{align*}
 353
T_\mathrm{scen3} = 2\log_2(p)\alpha
 354
+ \left(\frac{p-1}{p}|\tilde{S}| + \log_2(p)(c-1)\cdot 32\text{bit}\right)\beta
 355
+ 2(c-1) \gamma_s.
 356
\end{align*}
 357
When analyzing this run time, one can see that we have with the $\beta$-term part $\log_2(p)(c-1)$ a term that scales unbounded with the number of processors $p$. We can also see that the execution time can prolongate, if the critical size $c$ is set too high. But choosing $c$ as a very small number will reduce the possibility that scenario 1 occurs. So in the end there is a trade-off between the possibility of pure Allgather performance in the best case and the performance increase for the worst case. This is trade-off is tuned by the critical size.\\
 358
We looked here at very specific scenarios. It is apparent that the estimation of more complex configurations is not that easy anymore. It definitively possible that different ranks change representations in different iterations. Without specific information of the setup it is not possible to make accurate estimations using the linear cost model.

\section{An Algorithm for Arbitrary Number of Processes} \label{sec:irregularImpl}
 361
In this subsection we present an algorithm that works in a similar way, but is not confined to work only for a number of processes $p$ that is a power of two. Again we want to overlay an Allgather that uses a sparse representation of a subset $S_r$ over the Reducescatter phase of an Allreduce. The Allreduce basis is here given by the algorithm presented in Section \ref{sec:approxHalfRedScat}. Also in this section the approximate halfing sequence $(s_k)_{k\in \{0,\dots, q-1\}}$ is introduced and used. It is defined by the recursive property $s_k = \ceil{s_{k+1}/2}$ and the boundary conditions $s_q=p$ and $s_0=1$. This sequence has obviously $q=\ceil{\log_2{p}}$ terms. This sequence defines our communication scheme. In iteration $i$ (counting from 0) rank $r$ sends data to $\hat{r}_t=(r-\bar{s}_i + p)\mod{p}$ and receives data from rank $\hat{r}_f=(r+\bar{s}_i)\mod(p)$. The skips $\bar{s}_i$ correspond to elements of the approximate halfing sequence. It is important to keep in mind that in the Reducescatter phase (like it is shown in Algorithm \ref{algo:redScatterShift}) the skips are taken from the approximate halfing sequence in reverse order, meaning we have $\bar{s}_i = s_{q-1-i}$. Another important detail here is that this algorithm is not limited to the approximate halfing sequence. The only conditions such a sequence has to meet is $s_{k+1} - s_k \leq s_k$, $s_q=p$ and $s_0=1$. To adapt the Reducescatter phase to also be able to handle the sparse representation a Allgather is needed that uses the same communication pattern. It seems like the algorithm presented in Section \ref{sec:approxHalfAllgather} provides such an Allgather. The problem is here that the skips $\bar{s}_i$ are here used in the same order as they are listed in the sequence $(s_k)_{k\in \{0,\dots, q-1\}}$ (i.e. $\bar{s}_i = s_i$). In our research we did not find any Allgather algorithm that iterates such a sequence in reverse order to use the terms as skips. This is why we present in the next section an Allgather that uses this communication pattern.

\subsection{An Allgather using the reverse order of $(s_k)_{k\in \{0,\dots, q-1\}}$ as skips}
 364
As the problem statement to find an Allgather algorithm that uses skips $\bar{s}_i$ that are the reverse order terms of a sequence $(s_k)_{k\in \{0,\dots, q-1\}}$ with $s_{k+1} - s_k \leq s_k$, $s_q=p$ and $s_0=1$ is quite lengthy and complex, we firstly simplify this statement. We can define $\bar{s}_i$ directly by stating the properties $\bar{s}_{i+1} - \bar{s}_i \geq \bar{s}_i$, $\bar{s}_0=p$ and $\bar{s}_q=1$. Therefore these skips $\bar{s}_i$ indicate the distance to communication partners in iteration $i$ (counting from 1). \\
 365
We also impose some conditions that regard performance and also usability as adaptation in an Reducescatter phase. Firstly the should be at most $\ceil{\log_2(p)}$ communication rounds. Secondly there should be always contiguous data sent in each iteration. If memory is not ordered in a contiguous way there are two sends per iteration needed which degrades performance. Thirdly the total communication cost (total data send over all iterations) should not exceed $(p-1)m$ where $m$ describes the message size of a ranks input. For this all input arrays are assumed to be of same size. Fourthly and lastly in iteration $i$ the subresults a process has access to should span the same processors as the subresults at block $O[0]$ of the Reducescatter from Section $\ref{sec:approxHalfRedScat}$.\\
 366
The last condition gives a direct hint how such an Allgather could look like. For this we briefly recall the core idea of the Reducescatter from Section $\ref{sec:approxHalfRedScat}$. In this section it is shown that the problem is equivalent to summing up blocks of data of a single array. To show a a sub sum in each iteration of this algorithm the summation of blocks is represented as plugging a root node of a tree to the root of another tree. For example, if a block holds already the sum of block 1 and 5 and block 3 gets added to it, then node 3 is plugged into the root (node 1) of the tree $1\leftarrow 5$. To get a better understanding we show here the same example visualization from the Reducescatter from Section $\ref{sec:approxHalfRedScat}$ which is shown in Figure \ref{fig:arrayAddition}. We already argued in Section $\ref{sec:approxHalfRedScat}$ that the block indices correspond to the rank IDs that provided this block. We also argued that proving this behavior for one rank (in this example for rank 0) is sufficient to prove correctness for all ranks. This stems from the cyclical symmetry of the setup. By adding the rank ID $r$ (modulo $p$) to all indices one gets a description of what happens at rank $r$.\\
 464
Therefore we only use the perspective of rank 0 in this recap of the Reducescatter. Also we only use the representation of trees which correspond to subresults and plugging them together corresponds to summation of subresults. The goal is to have one tree with root 0 that spans all other nodes, but each node only once (i.e. no circles are formed). This is done by plugging the roots with high labels to roots with low labels. Precisely the roots $s_k, \dots, s_{k+1}-1$ get plugged into roots $0, \dots, s_{k+1}-s_k-1$. In the example from Figure $\ref{fig:arrayAddition}$ is a approximate halfing sequence used to find these $s_k$. But we will see that the condition $s_{k+1}-s_k \leq s_k$ is sufficient. Moreover one needs to keep in mind that the sequence is used in reverse order. One can see quite easily that after each iteration trees with roots $0,\dots, s_k-1$ span in total all nodes as all trees with a higher node than $s_k-1$ get plugged onto roots that are lower or equal to $s_k-1$. This is because of the maximum index a root gets plugged into is $s_{k+1}-s_k-1$ which can be estimated using the condition $s_{k+1}-s_k \leq s_k$ to $s_{k+1}-s_k-1\leq s_k-1$. This is also the reason why no node appears twice for roots up to index $s_k-1$. If the trees with roots up to $s_{k+1}$ hold distinct nodes after the iteration before, then trees with nodes up to $s_k$ will hold distinct nodes after the current iteration. This again due to the condition $s_{k+1}-s_k \leq s_k$ true as there is no overlap between the range of roots that are plugged and roots which trees are extended. \\

Such an action corresponds to an copying of a row, rotating it by $\bar{s_i}$ and putting it on top of the pile. This can be done in one iteration also for multiple rows. One needs to keep in mind that this can be done only for rows that are directly stacked up on each other as we only allow for sends of contiguous data. In this example the Allgather works just fine using a rather simple strategy. A helper array $H$ is added which counts how many blocks are correctly stacked on each rank. Therefore it is initialized with 1 at every entry. It is updated in each iteration by adding the values of $H[\bar{s}_i, \dots, \bar{s}_{i-1}-1]$ to $H[0,\dots, \bar{s}_{i-1}-\bar{s}_i-1]$ and after that setting values $H[\bar{s}_i, \dots, \bar{s}_{i-1}-1]$ to 0. Then it is possible to find the number of blocks that need to be sent in each iteration by simply looking at entry $H[\bar{s}_i]$. It is obvious that $H[0]-1$ counts for each iteration the total number of sent blocks. So the condition of the total amount data that is sent is met as in the last iteration $H[0]-1=p-1$. One can also see that this algorithm produces in each iteration subresults that span the same processors as the Reducescatter showed before. It is most apparent when the visual examples from Figure \ref{fig:arrayCopy} and Figure \ref{fig:blockConcat} are compared. One can also identify the property that in the Reducescatter trees with root $\bar{s}_i, \dots \bar{s}_{i-1}-1$ are plugged into roots $0, \dots, \bar{s}_{i-1} - \bar{s}_i-1$. In the Allgather proposal blocks from rank $\bar{s}_i, \dots \bar{s}_{i-1}-1$ gets stacked upon blocks $0, \dots, \bar{s}_{i-1} - \bar{s}_i-1$. Therefore both algorithms hold in iteration $i$ subresults from the same processors.\\

\subsubsection{An Allgather using the reverse order of a mostly halfing sequence as skips}
 772
The communication pattern of the algorithm we will provide here is based on a sequence we want to call a \emph{mostly halfing sequence} $(s_k)_{k\in \{0,\dots, q\}}$. We define this sequence by $s_q=p$, $s_{q-1}=2^{\floor{\log_2(p-1)}}$, $s_0=1$ and the recursive property $s_k = s_{k+1}/2$ for all $k=q-2, \dots, 0$. Moreover the number of processors $p$ must be greater than 1. One can see that $s_{q-1}$ is always next lowest power of two of the number processors $p$. If $p$ itself is already a power of two, it therefore holds $s_{q-1}=p/2$. After this first special step the next lowest sequence term can be found by exactly halfing until $s_0=1$. One can therefore see that $q=\ceil{\log_2(p)}$ which will correspond to the number of iterations that the proposed Allgather will take. Moreover it is apparent that this sequence fulfills the property $s_{k+1} - s_k \leq s_k$ for all $k=q-1, \dots, 0$ so this pattern works also for the Reducescatter algorithm mentioned before. Moreover we expect this sequence to minimize the number of row reordering of the pile representation from the subsection before. \\
 773
To be more precise a strategy is found where in each iteration there is at most one block hold back or one block copied back on top of the pile. So in each iteration there is at most one copy operation of the size of one block. This strategy results in the algorithm shown in Procedure \ref{algo:mostlyHalfingAllgather}.

This algorithm shows here simplified variant where all input blocks $I_r$ from the different ranks have the same size. Indexing of the array $O$ refers to these blocks.  815
There are three helper variables that hold information about the current state of the block pile. 'tail' holds information how many blocks are in the incomplete row of the pile. 'inBuff' tells, if the blocks of this tail are currently saved in the buffer array $B$ or stacked on top of the pile (saved as last block of $O$). Lastly there is 'size' which represents the current hight of the pile. The term height refers here the number of correctly stacked blocks of the right half of the pile. When considering the helper array $H$ discussed in the previous section it corresponds to the element $H[\bar{s}_i]$. There are two different main cases need to be considered. \\
 816

If this is not the case it is copied on top of $O$ and the height variable is adjusted to fit $H[\bar{s}_i]$. The first $\bar{s}_i$ blocks are now part of the solid part of the pile and the rest is now forming the new tail on top. Therefore the variable 'tail' is updated by subtracting $\bar{s}_i$ in this case. After the stacking the 'size' variable is doubled as the pile height also did.\\
 817
The second case describes the behavior, if the tail size is smaller or equal to the shift $\bar{s}_i$. In this case the tail is not cut and the right half of the pile has uniform height. The size is adjusted accordingly by subtracting 1, if the block is not already in the buffer to fit again $H[\bar{s}_i]$.

Instead there is only one copy needed (by putting the top blocks in the buffer) and new blocks are fitted directly on the correct positions in $O$. Moreover there may be another swapping avoided in the next iteration(s). If the tail is still smaller than $\bar{s}_i$ the tail blocks can be kept in the buffer.\\

As the execution of the algorithm is deterministic this can definitively be done, but as this Allgather is only used for an union set operation this reordering is not necessary. It will be omitted in the further usage and is therefore not explored.

\subsubsection{Correctness of the Mostly Halfing Allgather}

\begin{definition}[Pile representation of the Mostly Halfing Allgather]
 930
This pile representation is always done out of the perspective of rank 0. It shows for each iteration $i$ the distribution of the blocks that are needed by rank 0. Each rank has a slot where the needed blocks are stacked upon. A slot represents therefore the blocks that are saved in array $O$ of rank $r$ in iteration $i$ of the Mostly Halfing Algorithm. The slots have the same numbering as the ranks they correspond to.
 931
\end{definition}
 932
\begin{definition}[Pile representation of Algorithm \ref{algo:redScatterShift} (Reducescatter using approximate halfing)]
 933
This pile representation is always done out of the perspective of rank 0. It shows the state of the array $B$ for the adapted version, where no sends happen and memory is copied instead (see paragraph \ref{correctLabel}). It shows for each iteration $i$ which blocks are in the current sub sum at each block of the buffer $B$. In this pile representation each block has a slot where the current blocks that build the current value are stacked upon. The slots have the same numbering as the blocks they correspond to.
 934
\end{definition}

\begin{lemma}
 936
The pile representation of the Mostly Halfing Allgather is equivalent to a pile representation of Algorithm \ref{algo:redScatterShift} (Reducescatter) using the mostly halfing sequence as skips.
 937
\end{lemma}
 938
\begin{proof}
 939
Before the first iteration all ranks hold their own block in the Allgather and each block of the Reducescatter holds only their own block. After the first iteration the Reducescatter holds in each block at least their own value and the blocks [0,$\dots, p-2^{\floor{\log_2(p-1)}}-1$] have additionally the values from blocks [$2^{\floor{\log_2(p-1)}}, \dots, p-1$] added. The ranks $r$ send in the first iteration of the Allgather their input array to a rank with ID $(r-2^{\floor{\log_2(p-1)}}) \mod (p)$. So the blocks from ranks [$2^{\floor{\log_2(p-1)}}, \dots, p-1$] are appended to the input blocks of [0,$\dots, p-2^{\floor{\log_2(p-1)}}-1$]. The piles are therefore the same.\\
 940
Considering the other iterations: In the Reducescatter the blocks [s, \dots, s'-1] get added to the blocks [0, \dots, s'-s-1]. As the Mostly halfing sequence is used as skips $s$ the old skip $s'$ can be expressed as $s'=2\cdot s$. Moreover one can see that it therfore $s'-s-1= s-1$ holds. So the corresponding pile gets cut in half and the right half is put on top of the left half. In the Allgather the ranks [0, \dots, shift-1] receive some subresult from ranks [shift, \dots, $2\cdot$ shift-1]. If the top row (which size is indicated by 'tail') is greater than 'shift' the last element is included in the send. If this not the case all blocks but the last are sent. This results also in cutting the corresponding pile in half and and putting the right half on top of the left one. One can also see that 'shift' of the Allgather has always the same value as $s$ in the Reducescatter.\\
 941
As the pile representations have the same structure in the first iteration and are then transformed in the same way the representations are in each iteration equivalent.
 942
\end{proof}

\subsubsection{Expected performance of this reversely ordered Mostly Halfing Allgather} \label{sec:AllgatherShift performance}
 958
To estimate the execution time costs a uniformly filling of the input arrays is assumed. This guarantees that in each iteration each process sends and receives the same amount of data. If the total filling after the Allgather is $\Phi$, each processor is then filled with approximately $\varphi = \frac{\Phi}{p}$ elements. As this (Algorithm \ref{algo:mostlyHalfingAllgather}) round based algorithm takes $\ceil{\log_2(p)}$ iteration and in each iteration one send is performed the constant part from the linear cost model sums up to $\alpha\ceil{\log_2(p)}$. The total amount of data that is sent can also be easily calculated. When considering the pile representation rank 0 receives in each iteration only blocks that it needs (i.e. that it does not have already stacked in its array or buffer). As it does not have receive any duplicates, holds already one correct block in the beginning and holds all blocks at the end it received $p-1$ blocks. This gives a total communication cost for the $\beta$-term of $\beta\frac{p-1}{p}\Phi\cdot32\text{bit}$. This is of corse again a big simplification to model this behavior linearly, but this allows for a reasonable run time estimation. In each iteration there is at most one block copied to the "pile" buffer $O$ or to the side buffer $B$. \subsubsection{Further implementation details} \label{sec:reorderingMostlyHalfingAllgather}
1036
The pseudocode for the Mostly Halfing Allgather (Algorithm \ref{algo:mostlyHalfingAllgather}) assumes that the block sizes that are provided by each process are known by each rank. This will be not the case for the application the Allgather will be used for. As seen in the earlier proposed Union algorithm (Algorithm \ref{algo:SetUnionExactHalfing}) the concatenation of blocks of unknown size is possible by extracting the size information of a received block via the 'count' attribute of the 'status' object. The problem for the Mostly Halfing Allgather is that sometimes the last block of the output array $O$ needs to be buffered in the array $B$. So the size information of the last block is also needed. One idea is to use the 'tag' attribute of the 'status' object to transfer this information. The MPI standard \cite{mpi} only guarantees a maximum value of 32767 for the attribute 'tag'. So this idea can break for larger block sizes. So instead the size information of the last block is put into the buffer $O$ after the current last block element. In the sends are then not only the needed blocks send, but also the number of elements of the last block sent. The blocks are then also received one element behind the last element of the last block of the iteration before to avoid overwriting the size information of the last block. After it is checked that the send has completed the output array is rearranged such that elements in the blocks are contiguous in memory without being interrupted by some size information element.

\subsection{Concept and Explicit Implementation}

In this section the structure of the newly proposed Union algorithm \texttt{Union\_Shift} is described. The general idea is quite similar to the earlier proposed \texttt{Union\_Butterfly} algorithm (Algorithm \ref{algo:SetUnionExactHalfing}). The goal is to overlay an Allgather over the Reducescatter phase of an Allreduce. When it is preferred to use the sparse representation the \texttt{Union\_Shift} algorithm should work like an Allgather and switch to a Reducescatter, if the dense representation is seen as more efficient. As this algorithm needs to work correctly for an arbitrary number of processes $p$ the foundation for the Allreduce is chosen to be the recursive halfing Allreduce using a shift based communication pattern \ref{algo:redScatterAndAllgatherShift}. The corresponding Reducescatter (for the Reducscatter phase of this Allreduce) is described in Algorithm \ref{algo:redScatterShift}. A fitting Allgather implementation is described in the section before and its pseudocode can be found in Algorithm \ref{algo:mostlyHalfingAllgather}. \\

\subsubsection{Further implementation improvements}
1398
In the actual implementation is some small improvement done for the concatenation logic of two sparse arrays. The size information of the last block is only relevant, if the last block is eventually buffered. So if the sparse buffer $\Tilde{I}_s$ is already filled and 'inBuff' is true it is not necessary to send this information. Therefore it is only sent, if it is needed. A small benefit is here that the message size is one element (one 32-bit unsigned integer) shorter. The maybe more important improvement is that the receiver can append the message directly behind its sparse array $I_s$ as the size information of the last block of its old sparse array is not needed anymore (of course only relevant, if the receiver holds currently data in the sparse representation). So no rearrangement of sparse elements is needed and more importantly the receiver does not have to wait for its own send to complete as this rank itself does not send the size information of its last block.

\subsection{Proof of Correctness}
1405
This algorithm uses quite similar ideas as \texttt{Union\_Butterfly}. Therefore the ideas to prove that \texttt{Union\_Shift} also calculates a correct set union are also quite similar. For this firstly is only the case considered that only the sparse variant is used.
1406
\begin{lemma}
1407
Considering \texttt{Union\_Shift} (Algorithm \ref{algo:UnionShift}): If all ranks $r$ propose a sparse array and the sum over all set fillings $\sum_r\varphi_r=\Phi$ is less than the critical size 'sizeCrit', then each iteration $i$ of the Reducescatter phase is equivalent to the $i$-th iteration of the Mostly Halfing Allgather (Algorithm \ref{algo:mostlyHalfingAllgather}).
1408
\end{lemma}
1409
\begin{proof}
1410
Lets call the value 'sizeCrit' $c$, the value 'sizeBuff' $b$ and the value 'sizeSparse' $s$. One can quite easily see that, if only the sparse send is used and only $\Call{combineSparseSparse}{~}$ the union algorithm is exactly the same as the mostly Halfing Allgather. We therefore argue inductively that each iteration of these two Algorithms is equivalent.\\
1411
This is quite obvious for the first iteration as every rank proposed a sparse array and therefore every rank has set the flag 'isDense' to \textbf{false}. So the sparse send as well as the function to combine of two sparse arrays is executed. In $\Call{combineSparseSparse}{~}$ $s$ gets increased by the amount of received elements which corresponds to the amount of elements $\varphi_{\hat{r}}$ of the 'from'-rank $\hat{r}$. With the condition $\sum_j\varphi_j<c$ and $\varphi_j \geq 0$ one can see that the sparse size $s_r$ of rank $r$ is after the first iteration bounded by $c$ (using the estimation $s_r = \varphi_r + \varphi_{\hat{r}} \leq\sum_j\varphi_j<c$). Therefore the sparse representation is kept and 'isdense' is still set to \textbf{false}.\\
1412
The argument for the following iterations is quite the same using the assumption that the statement holds in the iteration before. As at the start of the iteration 'isdense' is set to \textbf{false} on all ranks the sparse send is executed for all of them. This leads to the combination of a received sparse array with the local sparse array. The total amount of saved sparse elements is the sum of $s$ with the number of buffered elements $b$. As the iterations before performed a subresult of an Allgather the total amount of buffered elements is bounded by the total sum of sizes of the proposed sparse arrays ($s+b\leq \sum_i \varphi_i$). So again the \textbf{if}-condition in line \ref{UnionShiftCombineSparseSparse:addSizeBuff} of $\Call{combineSparseSparse}{~}$ (Algorithm \ref{algo:UnionShiftCombineSparseSparse}) is fulfilled, because one can estimate $s+b\leq \sum_i \varphi_i < c$. The sparse format is therefore kept and 'isdense' is still set to \textbf{false}.
1413
\end{proof}

\begin{corollary}\label{coro:UnionSparse}
1415
If all ranks $r$ propose a sparse array and the sum over all set fillings $\sum_r\varphi_r=\Phi$ is less than the critical size 'sizeCrit' \texttt{Union\_Shift} performs an unordered Mostly Halfing Allgather.

\end{corollary}

\begin{proof}
1418
Under the condition $\Phi<c$ all iterations of the Mostly Halfing Algorithms are executed and the flag 'isDense' is still set to \textbf{false}. Therefore the \textbf{if}-statement in line \ref{UnionShift:sparseCompleted} is fulfilled and eventually buffered elements are put into the sparse array. At this point all steps of the Mostly Halfing Algorithms are performed, but the reordering. \texttt{Union\_Shift} returns after the copy of eventually buffered elements.

Consider that the sum over all set fillings $\sum_r\varphi_r=\Phi$ is as big or greater than the critical size 'sizeCrit'. The flag 'isDense' will be \textbf{true} for all ranks after all iterations are executed (line \ref{UnionShift:sparseCompleted}).

\end{corollary}

\begin{proof}
1424
Suppose not. Then there is one rank $r$ that is still using the sparse representation. Therefore it has never received an array in dense representation as this would lead to setting 'isDense' to true. Then in each iteration it holds a subresult of the Mostly Halfing Allgather. The total size of sparse elements $(s + b)$ has to be at some point at least $\Phi$. Therefore there is some iteration where $(s + b)\geq c$. This leads to a transformation into the dense format. \begin{lemma}
1427
Considering \texttt{Union\_Shift}: Suppose $I_d$ is empty, if the sparse representation is provided and $I_d$ is implicitly rotated, if the sparse representation is used. We define the reference Reducescatter as Algorithm \ref{algo:redScatterShift} performing an bitwise OR on the dense representation and using the same Mostly Halfing sequence as skips. Then for each rank the blocks $I_d[0,\dots, shift-1]$ of \texttt{Union\_Shift} are in iteration $i$ at least the same as the blocks $O[0,\dots, shift-1]$ of the reference Reducescatter, if rank $r$ uses the dense representation. "At least the same" means here that bits that are set to 1 for $O$ need also be set for $I_d$. If a rank uses the sparse representation this statement holds for a imaginary dense array $I_d$ after all elements of the sparse array $I_d$ are added using the implicit rotation.
1428
\end{lemma}
1429
\begin{proof}
1430
The statement is proved by induction. It holds before the first iteration. For the Reducescatter every rank holds only its provided input array. This is also true for \texttt{Union\_Shift} as every rank holds the whole information of the set in either the dense or the sparse representation.\\
1431
Assume the statement holds for the iteration before. We consider w.l.o.g some rank $r$. There are 3 different cases.
1432
\begin{enumerate}
1433
\item Receive dense array while holding the dense representation: \\
1434
Here the code is equivalent to the reference Reducescatter. If both (received and local) arrays hold "at least the same" subresults then the combination via the bitwise OR operator also results in an "at least the same" new dense bitarray $I_d$. The bitwise OR operation guarantees that if a bit in either of the arrays is set to 1 the corresponding bit in the resulting array will also be set to 1.
1435
1436
\item Receive sparse array while holding the sparse representation: \\
1437
As shown before rank $r$ has up until this iteration performed the Mostly Halfing Allgather. The Mostly Halfing Allgather is constructed in a way that its subresults span the same ranks as block $O[0]$ of the reference Reducescatter. As the blocks $O[j]$ with $j>0$ span the same or less ranks one can see that the Mostly Halfing Allgather subresult holds again "at least the same" elements as the reference Reducescatter does.
1438
1439
\item Combination of a sparse array with a dense representation:\\
1440
The sparse array holds "at least the same" subresult as the reference Reducescatter. The same is true for the sparse array. It does not matter which of the both arrays is received and which one is the local one. $I_d$ takes the dense array and the elements of the sparse are added using the implicit rotation. This is the same as transforming the sparse array to the dense representation first and then performing a bitwise OR with the dense array. The result is the same as the combination of two dense arrays which both fulfill the invariant in the iteration before. So the procedure is equivalent to a step of the reference Reducescatter and it is shown in the case analysis of the first case that this leads to a valid statement for the current iteration.
1441
\end{enumerate}
1442
The case analysis shows that the statement holds also for the current iteration which proves the statement for all iterations.

\end{proof}

\begin{proof}

These blocks are then concatenated and distributed in the Allgather phase. The resulting array at $I_d$ is has therefore at least all 1s set that an Allreduce would perform on just dense representations using the bitwise OR operator. The Allreduce would have calculated a union on all sets and setting extra bits to 1 only extends the resulting set.

\begin{lemma} \label{lemma:UnionSupset}
1451
If the total filling $\Phi$ is at least as big as 'sizeCrit' \texttt{Union\_Shift} calculates a set $R \subseteq \bigcup_r S_r = U$ with $U$ being the union on all provided sets $S_r$ from the different ranks.
1452
\end{lemma}
1453
\begin{proof}
1454
For each iteration one can state the following: If two dense arrays are combined the same blocks (of different ranks) get combined. If two sparse arrays are combined the resulting imaginary dense array holds also some subresult at each block from some ranks. If a sparse array is combined with a dense one the shifted setting of bits guarantees here also that only the same blocks get combined. This results in each rank $r$ holding after the Reducescatter phase at $I_d[0]$ that represents the set $R[r] = \bigcup_{i\in L} S_i[r]$. The notation $S_a[b]$ represents all elements of the provided set by rank $a$ that are in block $b$ of the not implicitly rotated dense representation. The index list $L$ holds some ranks and is allowed to hold some ranks multiple times. As the union operation is idempotent this index list equivalent to a set that only holds each rank at most once.\\
1455
As the result blocks $R[r]$ of the Reducescatter are then concatenated and distributed over all ranks via the Allgather phase one can see that the total result of \texttt{Union\_Shift} in $I_d$ represents a set that is at most the union of all sets provided by the ranks.
1456
\end{proof}

\texttt{Union\_Shift} calculates the union over all sets by the different ranks. I.e. each ranks holds a set representation of $U=\bigcup_{r=0}^{p-1} S_r$ with $S_r$ being the sets provided by the ranks and $p$ the number of ranks.

\end{theorem}

\begin{proof}
1461
Corollary \ref{coro:UnionSparse} states that an Allgather of all provided sparse arrays is performed, if the total set filling $\Phi$ is less than the critical size. This corresponds to an union over all provided sets. For $\Phi$ equal or greater than the critical size Corollary \ref{coro:UnionSubset} shows that \texttt{Union\_Shift} calculates a resulting set $R$ with $R\subseteq \cup_r S_r = U$ and Lemma \ref{lemma:UnionSupset} shows that $R\supseteq \cup_r S_r = U$. So in this case also the union over all provided sets is calculated.

\end{proof}

Here one can see that the strategy is selected beforehand and either an Allgather is executed on the sparse representation or the dense representation is used and then combined using an Allreduce. The selection is done by finding the set fillings $\varphi_r$ of all ranks $r$ by performing an Allgather on '$sizeSparse$' and then calculating the sum of all sizes. This is the same as the total set filling $\Phi$ which is then compared against the critical size. If the total set filling is smaller than the critical size the sparse variant is used and in the other case the dense Allreduce is executed. If one rank proposes a set represented in the dense format it sets its sparse size to 'critSize' so the total set filling $\Phi=\sum_{i=0}^{p-1}\varphi_i$ is guaranteed to be at least as big as the critical size and all ranks will use the dense format. Ranks holding the sparse format will need to transform to the dense one, if the Allreduce is used. This is indicated by the function $\Call{TransformToDense}{~}$.\\

The interface of the native MPI calls is for the pseudo code heavily simplified. The Allgather in line \ref{naiveMixed:algatherSize} returns a new array which holds the sparse sizes of all ranks. The original MPI-interface for the C language requires here actually an pointer to allocated memory that can be filled alongside with size information on the allocated output array, input array, datatype information and which ranks are going to participate (via a communicator struct). This additional information is technically also required for the later call on $\Call{MPI\_Allgatherv}{~}$ or $\Call{MPI\_Allreduce}$. On these calls the result of the Allgather/Allreduce is directly saved on the input array. \\

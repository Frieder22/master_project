\chapter{Introduction and Related Work}
Here we want to give an insight on what this thesis is build on. We want to give an description of what this thesis wants to achieve and what the motivation is for this project. In the later sections we then want to introduce and explain concepts, that are relevant for understanding the basis of this thesis.\\
The core idea of this thesis is, to optimize the set union operation of distributed subsets. The original motivation behind this is to make a implementation of a distributed \gls{bfs} algorithm faster. So we want to give a quick introduction, how this \gls{bfs} algorithm is build.
\section{BFS on distributed memory machines}
Breath First Search is a well-known algorithm \cite{standardBFS}, that explores a graph from a starting node (root node) by iteratively finding the neighborhood of the current explored region.
When having a graph $G(V, E)$ with a set of vertices $V$ and a set of edges $E$ connecting the vertices, the \gls{bfs} algorithm is described in procedure \ref{algo:BFSsequential}. Non-trivial syntax elements are described in section \ref{pseudocode}.
\begin{algorithm}
	\caption{Sequential implementation of BFS\\
	$n$: number of vertices\\
	$E$: set of edges\\
	$r$: root node}
	\label{algo:BFSsequential}
	\begin{algorithmic}[1]
		\Procedure{sequentialBFS}{$n, E, r$}
		\State pred[$n$] $\gets [-1, \dots, -1]$ \Comment{initialize pred array with $-1$ everywhere}
		\State frontier\_old $\gets$ \{$r$\}
		\While{frontier\_old $\not = \emptyset$}
			\State frontier\_new $\gets \emptyset$
			\ForAll{v $\in$ frontier\_old}
				\ForAll{neigh $\in$ \Call{getNeighbours}{$E$, $v$}}
				\If{pred[neigh] $\not=-1$}
					\State pred[neigh] $\gets$ v
					\State \Call{addVert}{frontier\_new, neigh}
 				\EndIf
				\EndFor
			\EndFor
			\State frontier\_old $\gets$ frontier\_new
		\EndWhile
		\State \Return pred
		\EndProcedure
	\end{algorithmic}
\end{algorithm}

We also have to add a little description of $\Call{getNeighbours}{E, v}$. It's job is obviously to return the set of neighbors of the vertex $v$ with respect to the set of edges $E$. But this can differ, on what $G$ represent. If we have a directed graph $G$ and a list of edges $E$, where each edge $e$ consists out of a tuple $(v_i, v_j)$ where $v_i$ is the origin vertex and $v_j$ is the vertex the edge points to, it is easy to find neighbors of this vertex $v$. We simply check for all edges.
If the first element of the tuple is the vertex of interest $v$, we add the second entry of this tuple to the output list. As this done lots of time, we can improve this sub-procedure by sorting the edgelist by its first entry in advance and keep track, which indices of this sorted list correspond to which vertices.
There also have to be some preparations done, if we want to represent an undirected graph. An easy and fast approach is to add the inverted edges (i.e. if $e=(v_i, v_j)\in E$ , then also add $\hat{e}=(v_j, v_i)$) to the edgelist.
To maximize efficiency later in the \gls{bfs} execution one needs to be careful to avoid adding duplicates.\\
We only look here in the base version of \gls{bfs} and therefore the return value of this algorithm is only the array \texttt{preds[]}. It contains the predecessor (or also called parent) of each vertex in \gls{bfs} tree. This variant is chosen as a challenge in one of the biggest data intensive benchmarks \cite{graph500}, but in real world applications there can be also some computations done after each exploration iteration. 

When adapting this sequential implementation to be parallelized on a distributed memory machine, there are many different approaches. There are different ideas how to partition and distribute on the different processes. For example the edges of the graph can also be written as an adjacency matrix. This adjacency matrix can then be partitioned in to rows (1D-partitioning) or in blocks (2D-partitioning).
So basically each process only maintains a subset of vertices for outgoing edges (1D-case) and/or even only a subset of vertices for ingoing edges (2D-case) \cite{graphPartitioning}. Both have their own (dis-)advantages. There are also ideas in adapting the algorithm itself.
One attempt is, instead of finding the neighbors of the current frontier, one can also iterate over the vertices, that don't have an predecessor set and look, if they have a neighbor in the frontier.
This can be advantageous, if the frontier is quite big and the set of left over vertices relatively small \cite{bottomUp}. 

But we focus here only on one (relatively simple) setting. We partition the graph by dividing the edgelist in equally size chunks and distribute them on the different processes.
A good argument for this partitioning compared to the before mentioned 1D- or 2D-partitioning is, that we want to avoid iterations, were some processes don't have any (or way less) work to do.
In our edge-centric partitioning we have in and outgoing edges for every vertex and can therefore expect a better load balance in each iteration. The given algorithm doesn't change much and is described in algorithm \ref{algo:BFSparallel}.

\begin{algorithm} [h]
	\caption{Our parallel implementation of BFS\\
	$n$: number of vertices\\
	$E$: set of edges\\
	$r$: root node}	
	\label{algo:BFSparallel}
	\begin{algorithmic}[1]
		\Procedure{parallelBFS}{$n, E, r$}
		\State pred[$n$] $\gets [-1, \dots, -1]$
		\State E\_local $\gets$ \Call{divideEdges}{$E$} 
			\Comment{Each process gets an subset of the edges}
		\State visited $\gets \emptyset$ 
			\Comment{Added to keep track of already visited vertices}
		\State frontier\_old $\gets$ \{$r$\}
		\While{frontier\_old $\not = \emptyset$}
			\State frontier\_new $\gets \emptyset$
			\State visited $\gets$ visited $\cup$ frontier\_old
			\Comment{update \texttt{vidited} set with new values}
			\ForAll{v $\in$ frontier\_old}
				\ForAll{neigh $\in$ \Call{getNeighbours}{E\_local, $v$}}
					\If{neigh $\not \in$ visited}
						\Comment{Check is now done using \texttt{visited} set}
						\State pred[neigh] $\gets$ v
						\State \Call{addVert}{frontier\_new, neigh}
					\EndIf
				\EndFor
			\EndFor
			\State frontier\_old $\gets$ \Call{unionAll}{frontier\_new}
				\Comment{Here the union of all subsets is calculated.}
		\EndWhile
		\State pred $\gets$ \Call{allReduce}{pred, MAX}
			\Comment{Choose a predecessor, if there is at least one proposed.}
		\State \Return pred
		\EndProcedure
	\end{algorithmic}
\end{algorithm}

The main changes here are, that we now divide the edges to the different processes, switch to another set structure \texttt{visited} and use the function \Call{unionAll}{ } to get a set union over all distributed subsets lying on the different processes. There is also another communication round added at the end of the procedure to unify the \texttt{pred} array.
Before this each process calculated a predecessor for each vertex of the graph (or left the corresponding entry set to $-1$). The call of \Call{allReduce}{pred, MAX} returns the maximum value for each entry of \texttt{pred}. This guarantees, that the same predecessor for each entry is chosen in each process and the entry is left at $-1$, if no process has found a predecessor. \\
The switch to using extra set \texttt{visited} is done to save the total amount of communication. We need some way to tell the other processes, which vertices are already visited, but the information, which the explicit predecessor for each vertex is chosen is obsolete in the \texttt{while}-loop.
A general idea here is to represent the frontier sets as bitmaps, where each entry is either set to 1, if a vertex is selected to be in the set, or set to 0 otherwise.
This safes a lot of space, when comparing it to an integer representation, where every positive number represents a selected vertex and a $-1$ stands for a non-selected one.
One needs to keep in mind, that in a bitmap, we need only one bit of memory for each vertex and an (large scale usable) integer would need 32 bits.
But there is still room for optimization possible. In each iteration of the \texttt{while}-loop we communicate the whole bitmap to the other process. But in the first iterations not a lot of the vertices are expected to be in the frontier. So most of the bitmap is set to zero.
We can use here a sparse format to represent the same set of vertices on a smaller memory footprint. Therefore amount of sent data can also be reduced.
Of course the function \Call{unionAll}{ } needs to be adapted to take care of dense and sparse representations. How this problem can be most efficiently solved is the key goal of this thesis.

The union set operation using only bitmaps is quite straight forward. A global reduction operation performing a bitwise OR on such bitmaps is exactly equivalent to the union set operation. The MPI standard defines this global reduction in the function \Call{MPI\_Allreduce}{ } using the tag \texttt{MPI\_BOR} \cite{mpi}. We borrow this nomenclature for this thesis and describe collective reductions an \textit{Allreduce}. In the later sections of this chapter are the basics of how these Allreduce algorithms implemented described. They are the foundation of the proposed optimized \Call{unionAll}{ } procedure.

\section{Cost Model} \label{costModel}
In this section we want to give a introduction on how to estimate runtimes for point to point communication and collective operations. As a starting point we motivate the LogP model \cite{LogP}. The idea of this model is to find an upper bound for the time, that is needed to send (rather small) messages from one processor to another. This is done by splitting the time in different components, that one can estimate by it's own. The $L$ stands for the latency, i.e. that's an upper bound of the time a message takes in the interconnect of the network to get from one processor to another. The $o$ represents the overhead a process takes to prepare the messages and is also assumed for the receiving process to make the data accessible. $g$ stands for the gap, the sending processor needs to send the next message. $P$ is here simply the number of processors. As an example when sending $k$ messages from one thread to another one, we can identify the different contributing parts and add the times together. The sending thread starts to send the fist message. Therefore one overhead $o$ is needed. Until the next message can be send the gap $g$ has to pass. So for the last message being send, it takes $(k-1)g$  amount of time. This last message enters the receiving process at least after the latency $L$ and takes another overhead $o$ to be ready for the receiving process. So in total we have an estimated time
\begin{align*}
	T_\textrm{LogP}(k) = 2 o + (k-1)g + L.
\end{align*}
This model can be extended to the LogGP model \cite{LogGP}. Here we considering also the sending of larger messages. The model is extended by the parameter $G$. It represents the gap that a sending process needs to send the next byte of the same message. So if we take the same example again and want to estimate it using the LogGP model, we have to add a term, that accounts for time each message takes to leave the sending processor. We assume each message has the same length $m$ for this example. So to send the second byte of a message, it takes $G$ amount of time. For $m$ bytes this sums up to $(m-1)G$. This is done for each of the $k$ messages. So the total missing term is $k(m-1)G$ and we can write the estimate of the LogGP model as
\begin{align*}
	T_\textrm{LogGP}(k,m) = 2 o + (k-1)g  + k(m-1)G + L .
\end{align*}
In general  we can't use the same parameter (i.e. $o, g, G, L$) for each pair of processors. In a distributed memory machine, which consists out of nodes, that are connected by some form of network, we can expect, that communication between the processors, that are physically at the same node, is faster than to processors that only can be reached by the interconnect. That means, that for these pairs we expect at least a lower latency $L$ and a higher bandwidth, which reduces the parameter $G$.
We simplify these models and assume a homogeneous network. This is of course a statement, that mostly never is reality, but it helps finding closed forms for estimated runtimes. Moreover in this thesis we take a look and adapt round based collective communication. Here one can argue, that for each round the execution time is dominated by the slowest pair of processors. Since this connection can be assumed as always the same, the argument of only using one set of parameters is nevertheless acceptable. \\
The round based structure of the considered algorithms further enables us to do a simplification. The LogP and LogGP model show their strength in estimating communication, that partially overlaps or in the case, that some processes participate more often in communication than others do. A good example would be a Broadcast on an unbalanced binary tree \cite{LogP}. As we expect our algorithms to use all processors in each communication round, we can introduce the linear cost model as an sufficient estimator of execution time. In this model, we reduce all the factors into two new parameter $\alpha$ and $\beta$. So we can estimate each communication round as
\begin{align}
	T_\mathrm{linear}(m) = \alpha + \beta m. \label{eq:linearCostModel}
\end{align}
When considering the LogGP model for only one message, we could identify $\alpha=2o + L - G$ and $\beta = G$. To make the estimation from equation \ref{eq:linearCostModel} work, we need to impose another two assumptions about the machine the algorithms are executed on. The first one is, that the interconnect is one-ported. This means, we can only send at most one message at once. The other condition is, that the network is bidirectional, meaning a two threads can send each other messages at the same time \cite{BroadcastWorkOpt}.\\
In this thesis reduce algorithms are considered. So there is not only the execution time of communication relevant. A considerable amount of data is also processed (in the sense of applying the reduction operator on received/stored data), which execution time we also want to model in a linear fashion. Typically the reduction operator is applied on each element of a received vector. This also holds in the applications for this thesis. By introducing a new parameter $\gamma$, the linear model
\begin{align*}
	T_\mathrm{reduce} = \gamma m
\end{align*}
can estimate the execution time to reduce a vector of size $m$ (in bytes) into another one. The parameter $\gamma$ is here dependent on the reduction operator (and of course on the machine it is executed on). With this we can model execution times of the algorithms proposed in the next sections.

\section{Important Allreduce Implementations}
The Allreduce operation is intuitively a direct choice for our problem of calculation a set union. Abstractly speaking, we can split up our problem of calculating the union of all processes by finding the union between two sets (of two processors) and then use this subresult without ever looking at the two original sets anymore. So we can find the total union in a recursive fashion. Two nice other properties are apparent: It doesn't matter, in which order the subresults are calculated and combined, as the union operation is commutative. Another nice property is, that calculating the union is an idempotent operator. So even if we would use a subresult twice in our calculation, we still get a correct result. \\
In this section we want to introduce a selection of Allreduce algorithms, that either are important to know or are the basis of the algorithms presented in this thesis. In general we look here only at non pipelined implementations. On the one hand we expect, that chunking up the message can destroy the benefit of using a sparse format, as a sparse message would need to 'compete' against smaller blocks. On the other hand a selection needed to be done, as not every variant could be considered as a base algorithm for our idea.
  
\subsection{Reduce combined with a Broadcast} \label{ReducePlusBroadcast}
One of the most direct approaches to get a Allreduce, is by performing an Reduce to a chosen root node and after that distribute this result to all processes. As we don't look at pipelined algorithms, we can easily estimate the runtime complexity. A naive approach \cite{AllreduceSummaryAll} is to create a communication pattern matching a binomial tree with the root node on top. This tree is used for the Reduce as well as for the Broadcast. During the Reduce phase all participating ranks send their array to their parents (of the binomial tree), where the reduce operation is executed. After $\log_2(p)$ iterations the reduction is complete and we perform the Broadcast in the same fashion, but in reverse. By estimating the complexity of the reduction with $T_\textrm{Red} = \log_2(p)(\alpha + m \beta + m \gamma) $ and for the broadcast $T_\textrm{Broad} = \log_2(p)(\alpha + m \beta) $, we get a total run time estimation of
\begin{align}
	T_\mathrm{Naive} = 2 \log(p) (\alpha + m \beta) + \log_2(p) \gamma. \label{eq:BroadcastNaive}
\end{align}
This can be improved, especially for large message sizes. For the Broadcast there are \textit{work-optimal} implementations, that switch to optimized algorithms for larger messages. These algorithms bring down the $\beta$-term, which usually scale the effect of the message size $m$. Such \textit{work-optimal} algorithms bring the $\beta$-term from $\log(p)m$ down to $2 m \frac{p-1}{p}$ \cite{BroadcastWorkOpt, BroadcastAlgos}. This is of course only beneficial for a relatively large amount of processors $p$. There are also strategies, like pipelining the Broadcast or using trees with different degrees \cite{pipelinedBroadcast, karyTrees}. The same ideas can be also applied for the Reduction part. These implementations are of course especially useful, if the underlying structure of the computing machine is also build in a tree-like fashion.


\subsection{Recursive Doubling Scheme} 
The recursive doubling scheme is an approach to get rid of the factor 2 appearing in equation \ref{eq:BroadcastNaive} by getting every process in each iteration involved and tackling the problem in a divide-and-conquer fashion. The key observation of this algorithm is, that when two processes send a copy of their data vector to each other and both perform a local reduce combining their own data with the received vector, they both posses identical data \cite{AllreduceSummaryAll}. This is beneficial, as in the next iteration both processes can send the same subresult to new participating processes, that are not the same.
By doing this we can recursively build a scheme, such that in each iteration $i$ a set of $2^i$ processes have the same subresult. So this approach works ideally for $2^k$ numbers of participating processors. To get a better understanding an implementation as pseudocode is shown in algorithm \ref{algo:recursiveAlgo}.\\
\begin{algorithm}
	\caption{– Recursive Doubling Scheme\\
	\textit{r}: rank Id\\
	\textit{p}: number of processes\\
	\text{I}: Input array\\
	\textit{O}: Output array} \label{algo:recursiveAlgo}
	\begin{algorithmic}[1]
	\Ensure $p=2^k$ for some $k$
	\Procedure{AllReduce}{$r, p, I, O$}
		\For{(shift $\gets 1$, shift $< p$, shift $\gets 2\cdot$shift)}
		\State commNeigh $\gets r $ XOR shift \Comment{Find communication partner}
		\State \Call{Send}{$I$, commNeigh} $||$ \Call{Recv}{$O$, commNeigh} \Comment{Send input, receive in output}
		\State $I \gets I\oplus O$ \Comment{Perform local reduction}
		\EndFor
		\State $O \gets I$
	\EndProcedure
	\end{algorithmic}
\end{algorithm}
As one can see, this works only for commutative reduction operators $\oplus$, because after each communication round each processor and its communication partner hold the same data, but in switched locations.  This can easily be avoided by switching $I$ and $O$ for some processes (in some iterations) \cite{NonComAllred}. Such adaptations are not relevant for this thesis, as the union operator for sets is commutative. \\
We can sketch a proof of correctness by induction. We want to show, that in each iteration $i$ blocks processes of size $2^i$ hold the reduction result of its block. E.g. in iteration $1$ process 0 and 1, 2 and 3, 4 and 5, $\dots$ should hold the same data. We can start the induction with $i=0$ and see, that each block is only the respective processes itself. Therefore each block holds a correct subresult in every process. Next we want to the induction step. We can see, that two blocks should be merged into one. Each processor communicates with a different processor from the neighboring block. The bitflip (XOR operation) of the $i$-th bit guarantees that. Therefore the processes receive all a correct subresult from the other block in the array $O$. Then the reduction operation $\oplus$ is applied between the current correct subresult of the own block and foreign correct subresult of the other block. Therefore the produced new subresult is also correct for all processes in the same block of size $2^{i+1}$.\\
There are $i=\log_2(p)$ iterations done and therefore all $p$ processors hold the same correct result of the reduction.\\
When estimating the execution time, we can see, that in each iteration a array of the whole size is send. So in each iteration we need $\alpha + \beta m$ time for communication and $\gamma m$ time for the local reduction. This setup is the same for each of the $\log_2(p)$ iterations so we get a total of
\begin{align*}
	T_\mathrm{recDoubling} = \log_2(p) \left( \alpha + \beta m + \gamma m \right).
\end{align*}
Comparing this to the estimate of the Broadcast+Gather variant (eq \ref{eq:BroadcastNaive}), we can see, that we lost a factor of 2 for the $\alpha$ term as well as for the $\beta$ term. One needs to keep in mind, that we assumed a hypercube interconnect setup, such that in each iteration each process has a direct connection to a different communication partner. This was not necessarily needed in the algorithms explained in the section before.\\

Moreover it is important to mention, that this is not the only communication scheme, to achieve a data distribution in $\log_2(p)$ communication rounds. The communication scheme we presented here, is called Butterfly scheme \cite{ButterflyVSDoublingHalfing}. This scheme can be identified by the fact, that we receive data from the same process as we send to (i.e. in each iteration we only have one communication partner). This resulted in the recursive property, that a set of $2^i$ processors have in iteration $i$ the same data. Another approach is, that a process $r$ sends in iteration $i$ its data to process $((r+2^i)\mod{p})$. Obviously each process expects therefore to receive data from $((r-2^i)\mod{p})$. To implement this strategy we only have to adapt communication IDs in pseudocode \ref{algo:recursiveAlgo}. The rest of the algorithm keeps unchanged.\\
In figure \ref{fig:communicationSchemes} we can see a visual comparison between both of these communication schemes. In the shift based approach, we can see, that a more regular tree pattern emerges. In fact, as we find our communication partners here with the same shifts in $\mod{p}$, one can argue, that each processor is the root of a tree with the exact same structure as the reference tree for $r=7$ shown in figure \ref{fig:shiftBased}. E.g. when looking at process $6$, we can put the nodes of process $7$ at the very front (while maintaining the arrow connections) and we would identify this new diagram as the exact same as the old one. The only difference in this new diagram would be, that the nodes of this new diagram are now labeled in order $7,0,1,2,3,4,5,6$. Therefore we can see now the exact same tree structure for process $6$ as we did for process $7$. This property simplifies now our sketch of proof for correctness. \\
We want to show, that each node received the data from each other node. As we indicated before, it is now sufficient to only show this for node $7$. We again solve this inductively. We want to argue for this case, that each node holds in iteration $i$ the data of the $2^i$ nodes left from it. More precisely we mean the $2^i-1$ nodes left to it and the node itself. It iteration $0$ each process holds its own data so the induction start is trivially true. In each iteration we get data from process $\hat{r}=(r-2^{i-1})$. Using our induction condition process $\hat{r}$ holds the data from rank $\hat{r}-2^{i-1} = r-2^{i-1} - 2^{i-1} = r-2^i$ to $\hat{r}=(r-2^{i-1})$. The process $r$ itself already holds data from $(r-2^{i-1})$ to $r$. We can see that the upper bound from $\hat{r}$ matches the lower bound from $r$ and therefore, we can write, that after the send $r$ holds the data from $r-2^i$ to $r$. This is indeed the data from the $2^i$ processors left from $r$ (with our definition of "left from it"). So after $log_2(p)$ iterations process $7$ has the data from the $2^{\log_2(p)}=p$ processes left from it and therefore all data.\\ 
As we also want to estimate the runtime using the linear cost model, we can see directly from the adapted pseudocode, that we expect the same run time as the Butterfly implementation. An important side note we want to mention here, is, that generalizations of the Butterfly scheme to a number of processes, that are not a power of two are not easily done. Here the shift/tree based approach is more suitable as we see later in this chapter.

\subsection{Combining Reduce\_Scatter and Allgather using recursive Doubling}\label{sec:DisseminationAlgo}
As next idea we want to propose the combination of a Reduce\_Scatter with an Allgather to create an Allreduce. The goal here is to send less data on the cost of introducing extra communication rounds. As a general communication pattern, we also want to use the Butterfly pattern from section \ref{ReducePlusBroadcast}. The new idea here is to divide the vector into $p$ blocks and send in each iteration only half of the blocks, that were sent in the round before. The result of this is, that each process holds after this procedure only a block of the correct reduced vector. This procedure is called a Reduce\_Scatter (in the MPI \cite{mpi} standard) and is the first phase of this algorithm. In the second phase these blocks needed to get distributed to all the other processors. This is done using the same communication pattern but in reverse.

\begin{algorithm}
	\caption{– Reduce\_Scatter and Allgather\\
		\textit{r}: rank Id\\
		\textit{p}: number of processes\\
		\text{I}: Input array\\
		\textit{O}: Output array} \label{algo:redScatterAndAllreduce}
\begin{algorithmic}[1]
	\Ensure $p=2^k$ for some $k$
	\Procedure{AllReduce}{$r, p, I, O$}
	\For{(shift $\gets p/2$, shift $\geq 1$, shift $\gets$ shift/$2$)}
	\Comment{ReduceScatter phase}
		\State commNeigh $\gets r $ XOR shift \Comment{Find communication partner}
		\State start $\gets $ (commNeigh/shift)*shift
		\Comment{rounding down to next multiple of shift}
		\State startR $\gets $ ($r$/shift)*shift
		\State \Call{Send}{$I[start, \dots, start + shift]$, commNeigh} $||$ \Call{Recv}{$O$, commNeigh}
		\\ \Comment{Send input, receive in output}
		\State $I[startR, \dots, startR + shift] \gets I[startR, \dots, startR + shift]\oplus O$
		\\ \Comment{Perform local reduction}
	\EndFor
	\For{(shift $\gets 1$, shift $< p$, shift $\gets 2\cdot$shift)}
	\Comment{Allgather phase}
		\State commNeigh $\gets r $ XOR shift 
		\State start $\gets $ ($r$/shift)*shift
		\State startR $\gets $ (commNeigh/shift)*shift
		\State \Call{Send}{$I[start, \dots, start + shift]$, commNeigh} $||$
		\State \Call{Recv}{$I[startR, \dots, startR + shift]$, commNeigh}
	\EndFor
	\State $O \gets I$
	\EndProcedure
\end{algorithmic}
\end{algorithm}

In listing \ref{algo:redScatterAndAllreduce} we see the pseudocode implementation of this algorithm. We also can sketch a proof of correctness of this algorithm. With the same inductively induced argument before, we can assure that the first part performs an reduction, but only for one block. This block is the $r$-th one in the vector with $r$ being the rank ID of the processor. We then can then identify, that the same communication pattern is applied in reverse to distribute the blocks to all processors. Here the same inductive argument can be applied.\\
For estimating the runtime of this algorithm, we can split it into the two phases. In the Reduce\_Scatter phase we send in each iteration \texttt{shift} blocks of data. Assuming the original vectors can be split equally, each block consists out of $m/p$ amount of data. On the same amount of data is also the reduction operator applied. There are $\log_2(p)$ iteration rounds and we can calculate \texttt{shift} as being $p\cdot 2^{-i}$, where $i$ the current iteration. We can calculate the runtime as being
\begin{align}
	T_\mathrm{ReduceScatter}
	&= \sum_{i=1}^{\log_2(p)} \alpha + \beta p 2^{-i} \frac{m}{p} + \gamma p 2^{-i} \frac{m}{p} \nonumber\\
	&= \sum_{i=1}^{\log_2(p)} \alpha + (\beta + \gamma) 2^{-i} m\nonumber \\
	&=\log_2(p)\alpha + (\beta + \gamma) (1-2^{-\log_2(p)}) m\nonumber\\
	&=\log_2(p)\alpha + (\beta + \gamma) \frac{p-1}{p}m. \label{eq:reduceScatter}
\end{align}
For calculating the execution of the Allgather phase nearly the same ansatz can be done. We have a different ordering of the summation terms (which doesn't influence the sum at all) and we can omit the $\gamma$ term. So Allgather time is with 
\begin{align*}
	T_\mathrm{Allgather}
	&=\log_2(p)\alpha + \beta \frac{p-1}{p}m. 
\end{align*}
nearly the same as equation \ref{eq:reduceScatter}. So the total runtime can be estimated as being 
\begin{align*}
	T_\mathrm{Allreduce}
	&=2\log_2(p)\alpha + (2\beta + \gamma) \frac{p-1}{p}m. 
\end{align*}
